# МедАрхив

Система учёта и перемещения медицинских карт между филиалами медицинской организации, центральным офисом и архивом.

## Текущая архитектура

- **Целевая БД:** PostgreSQL; схема управляется Alembic.
- **Приложение:** Python 3.11+, FastAPI, SQLAlchemy 2.x (async), Jinja2/HTMX.
- **Аутентификация:** PostgreSQL-пользователи и подписанные HTTP-only session cookies.
- **Эксплуатация:** systemd, отдельный ежечасный PostgreSQL backup service/timer.
- **SQLite:** только legacy-совместимость старого прототипа. Не использовать для новой production-установки и не вводить в эксплуатацию как целевую БД.

PostgreSQL-режим подключает PostgreSQL-маршруты операционного и административного контуров. Для подробностей реализации, схемы и тестов см. [руководство PostgreSQL](docs/development/postgresql.md).

## Основные бизнес-процессы

- Филиал регистрирует медицинские карты из QR-кода внешней медицинской системы или вручную по утверждённым правилам, формирует коробки и отправляет коробки в архив.
- ЦО оформляет коробочные отправления в архив; назначается обязательный курьер, передачу подтверждает автор отправления, архив принимает коробки.
- Архив размещает коробки на полках и обрабатывает заявки ЦО на получение медицинских карт. По одной заявке может выдаваться несколько карт и допускается частичная выдача.
- ЦО подтверждает фактическое получение каждой выданной карты; до такого подтверждения ответственность сохраняет архив. Массовое подтверждение нескольких фактически поступивших карт допускается одной атомарной операцией.
- Коробки при приёмке архивом не вскрываются для пересчёта карт; количество карт, пломбы и целостность упаковки не проверяются. Размещение после приёмки — отдельная операция.
- Для внешней передачи из центрального офиса фиксируется ответственное хранение с последующим возвратом на баланс ЦО.
- История перемещений и административных изменений сохраняется в журнале событий.

Маршруты филиал → ЦО и ЦО → филиал в целевой модели не предусматриваются. Коробки при выдаче отдельных карт в ЦО остаются в архиве.

## Роли

| Роль | Основная область работы |
|---|---|
| `branch` | Регистрация карт, коробки и отправления филиала |
| `central_office` | Приёмка, заявки в архив, логистика и внешнее ответственное хранение |
| `archive` | Приёмка, размещение, поиск и исполнение заявок ЦО |
| `admin` | Пользователи, филиалы, курьеры, архивные места и административный аудит |

Доступ к картам и журналам ограничивается серверной авторизацией и областью видимости роли.

## Локальная разработка

Требования: Python 3.11+, PostgreSQL (локально можно использовать Docker Compose).

```bash
git clone <repo-url> medarchive
cd medarchive
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
docker compose up -d postgres
export MEDARCHIVE_POSTGRES_ENABLED=true
export MEDARCHIVE_AUTH_BACKEND=postgresql
export MEDARCHIVE_DATABASE_URL='postgresql+asyncpg://medarchive:medarchive@localhost:5432/medarchive'
alembic upgrade head
```

Для локального запуска задайте секрет с достаточной случайностью:

```bash
export MEDARCHIVE_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
uvicorn medarchive.main:create_app --factory --reload
```

Локальные Docker-реквизиты предназначены только для разработки и не должны использоваться в production.

## Первый администратор PostgreSQL

Публичной регистрации и встроенного пароля по умолчанию нет. Первый администратор создаётся CLI-командой только когда таблица пользователей пуста. Команда запрашивает пароль интерактивно, проверяет повтор и требует не менее четырёх символов.

При production-установке сначала загрузите защищённый env-файл в текущую оболочку, чтобы CLI получил те же параметры подключения:

```bash
set -a
source /etc/medarchive/medarchive.env
set +a
medarchive-admin create-admin --username admin --full-name "Имя Фамилия"
```

Команда откажется создавать администратора, если в БД уже существует хотя бы один пользователь.

## Production-развёртывание

Подробная инструкция по установке PostgreSQL, настройке systemd, первому администратору, backup и восстановлению находится в [руководстве PostgreSQL](docs/development/postgresql.md).

Краткая последовательность:

1. Подготовить PostgreSQL и отдельную БД/роль приложения с минимально необходимыми правами.
2. Развернуть код в `/opt/medarchive`, создать виртуальное окружение и установить пакет.
3. Выполнить `sudo bash scripts/install.sh`, чтобы создать `/etc/medarchive/medarchive.env`; заполнить уникальный секрет и production URL PostgreSQL.
4. Установить PostgreSQL client tools той же основной версии, что и сервер, а также пакет `age`.
5. Создать age identity на отдельной доверенной машине; указать только публичный recipient в `MEDARCHIVE_BACKUP_AGE_RECIPIENT`, закрытый ключ хранить вне сервера. Повторно выполнить `sudo bash scripts/install.sh`, чтобы включить backup timer.
6. Выполнить Alembic migrations и создать первого администратора.
7. Включить и проверить `medarchive` и `medarchive-backup.timer`; провести пробное восстановление зашифрованной копии.
8. Настроить TLS reverse proxy перед приложением. Не публиковать порт приложения напрямую в Интернет; ограничить сетевой доступ к нему и к PostgreSQL.

Production-конфигурация требует `MEDARCHIVE_COOKIE_SECURE=true` и `MEDARCHIVE_SECRET_KEY` длиной не менее 32 символов. Секреты нельзя хранить в репозитории или передавать в тикетах/логах.

## Резервное копирование и восстановление

Production backup выполняется отдельным systemd timer/service. Скрипт `scripts/backup.sh`:

- создаёт PostgreSQL custom-format dump и проверяет его через `pg_restore --list`;
- шифрует архив публичным age recipient до публикации файла;
- хранит только зашифрованные `.dump.age` копии с правами `0600`;
- не допускает параллельного запуска и хранит последние 24 завершённых архива.

Проверка создания архива не заменяет проверку восстановления. Регулярно восстанавливайте копию в отдельную PostgreSQL-БД и проверяйте доступность схемы и прикладных данных.

**Важно:** сервер хранит только публичный age recipient; закрытый age identity должен находиться вне сервера и быть доступен для восстановления. Старые `.dump` архивы, созданные до включения age, остаются незашифрованными и требуют отдельной миграции или безопасного удаления. Дополнительную зашифрованную копию храните за пределами сервера. Локальные почасовые копии сами по себе не обеспечивают аварийное восстановление.

## Проверки

Тестовый набор включает PostgreSQL integration tests, проверки ограничений БД, сквозные бизнес-процессы, административные сценарии, а также создание и восстановление backup в CI. Перед выпуском проверяйте оба workflow GitHub Actions — Push и Pull Request — на одном и том же актуальном SHA.

```
scripts/                 # установка, systemd и backup

```
