# Миграция МедАрхива: SQLite → PostgreSQL

**Статус:** проект плана миграции  
**Версия:** 1.0  
**Дата:** 2026-11-11

## 1. Исходные условия

Текущий прототип использует SQLite и таблицы `branches`, `users`, `couriers`, `archive_sections`, `archive_shelves`, `cards`, `boxes`, `box_cards`, `shipments`, `box_placements`, `requests`, `card_movements`.

Целевая модель использует PostgreSQL, UUID, единые локации, универсальные отправления, отдельные составы отправлений, циклы коробок, заявки только центрального офиса и неизменяемый журнал событий.

Миграция не должна менять production SQLite и не должна автоматически запускаться при старте приложения.

## 2. Принципы

1. Исходная SQLite-БД сохраняется неизменной до завершения сверки и отдельного решения о переключении.
2. Перед выгрузкой создать согласованную резервную копию SQLite с учётом WAL (предпочтительно SQLite Backup API или остановка приложения и корректное checkpoint/копирование).
3. Миграционный скрипт идемпотентен по контрольному идентификатору запуска либо явно отказывается повторно загружать уже импортированный набор.
4. Переносить исходные целочисленные ID в отдельные legacy-поля или таблицы соответствий; целевые UUID генерировать отдельно.
5. Сохранять исходные временные значения как есть в staging/legacy-слое до определения часового пояса. Не трактовать SQLite localtime как UTC автоматически.
6. Ни одна карта, коробка, отправление или заявка не должны получать выдуманную историю.
7. Все неоднозначные записи попадают в отчёт сверки и не получают молча придуманное местонахождение.
8. Запускать импорт сначала на копии, затем сверять количественные и логические контрольные суммы.

## 3. Рекомендуемые этапы

### Этап A. Снимок и инвентаризация

- Остановить запись в исходную БД на время финального снимка либо использовать SQLite Backup API.
- Проверить целостность: `PRAGMA integrity_check`, `PRAGMA foreign_key_check`.
- Снять количество строк по каждой таблице.
- Выгрузить distinct статусы, роли, типы отправлений, значения `to_department`, NULL-поля и нарушения ссылочной целостности.
- Зафиксировать версию схемы и SHA-256 файла снимка.
- Сохранить неизменяемый исходный снимок и журнал запуска миграции.

### Этап B. Staging и таблицы соответствий

Создать временный staging schema или набор `legacy_*` таблиц с исходными столбцами и типами. Рекомендуемые таблицы соответствий:
- `legacy_branch_map(old_id, new_id)`;
- `legacy_user_map(old_id, new_id)`;
- `legacy_courier_map(old_id, new_id)`;
- `legacy_card_map(old_id, new_id)`;
- `legacy_box_map(old_id, new_id)`;
- `legacy_shipment_map(old_id, new_id)`;
- `legacy_request_map(old_id, new_id)`.

Для каждого перенесённого объекта сохранять исходный ID и источник. Не использовать старый integer ID как целевой UUID.

### Этап C. Справочники и пользователи

1. Перенести филиалы с сохранением `code` и названий.
2. Создать по одной location типа branch на каждый филиал.
3. Создать одну location central_office и одну archive.
4. Перенести курьеров; дубликаты по ФИО/телефону не объединять автоматически без подтверждения.
5. Перенести пользователей, сопоставив роли. Старые роли не расширять автоматически:
   - `branch` → branch;
   - `archive` → archive;
   - `viewer` → viewer;
   - `admin` → admin.
6. Новую роль central_office назначать только после определения конкретных сотрудников ЦО и их полномочий.
7. Пользователей филиала сопоставить с филиалом. Некорректные/пустые привязки — в отчёт.

### Этап D. Карты

Старая таблица `cards` содержит только `id`, `full_name`, `status`, `created_at`. В ней нет номера карты внешней медицинской системы, даты рождения, телефона и филиала происхождения.

Следовательно:
- нельзя автоматически заполнить `card_number`, `date_of_birth` или `origin_branch_id` достоверными значениями;
- нельзя придумывать внешний номер или использовать ФИО как уникальный идентификатор;
- старые карты должны попасть в staging/legacy-контур до обогащения данными;
- для production-целевой таблицы требуется отдельное решение: импортировать такие записи в таблицу legacy_cards с ограниченным функционалом до сверки либо согласовать временный nullable legacy-режим с последующим закрытием;
- связывать старую карту с новой записью по ФИО можно только как кандидат на ручное сопоставление, не как автоматическое объединение.

Статус карты не переносить напрямую как местонахождение. Местонахождение восстанавливать из актуального состояния коробки, активного отправления, размещения и согласованной сверки.

### Этап E. Коробки и состав

- Перенести коробки, номера, автора и даты.
- Старое `origin_branch_id` сохранить как legacy-поле/исторический атрибут; не использовать его как текущее местонахождение.
- Каждую коробку перенести в целевой объект и создать первый цикл использования.
- Из `box_cards` перенести все интервалы добавления/изъятия.
- Если у карты несколько незакрытых членств, не выбирать одно автоматически: запись в отчёт конфликтов.
- Текущее членство определить только после проверки временных интервалов и фактического состава.

### Этап F. Отправления и заявки

Старая таблица `shipments` содержит один из `box_id/card_id`, филиальные поля `from_branch_id/to_branch_id`, `to_department`, курьера, инициатора, даты, получателя и статус. Новая модель поддерживает локации branch/central_office/archive и отдельные таблицы состава.

- Для каждой строки определить тип объекта и единственную пару локаций.
- `from_branch_id` и `to_branch_id` сами по себе не описывают архив и ЦО. `to_department` нельзя интерпретировать без проверки всех мест использования в коде и фактических данных.
- Значения статусов `issued/received/lost/damaged` сопоставлять с целевыми только после анализа конкретных строк и связанных движений.
- Отправления без курьера, отправителя, адресата или однозначного состава — в отчёт.
- Старые записи, которые не соответствуют новой матрице маршрутов, сохранять как legacy-историю; не переписывать им маршрут.
- Заявки из старой модели могли создаваться филиалами и иметь target_branch_id. Они не становятся автоматически заявками ЦО. Нужна классификация по пользователю-инициатору, статусу и связанным отправлениям.
- Нельзя автоматически помечать заявку выполненной только по факту выдачи курьеру.

### Этап G. Архивные размещения и история

- Перенести секции и полки, сохраняя связи.
- Перенести интервалы `box_placements`; конфликтующие активные размещения вынести на разбор.
- `card_movements` сохранить как legacy-журнал. Поля `from_location/to_location` — текстовые, поэтому нормализовать их в location IDs можно только при однозначном словаре соответствий.
- Не генерировать недостающие события на основании догадок.
- Целевой журнал событий может содержать событие `legacy_imported` со ссылкой на исходную запись, но оно не должно выдавать импортированную реконструкцию за исходное историческое событие.

## 4. Отчёт сверки

Миграция должна сформировать машинно-читаемый отчёт и человекочитаемую сводку:
- строки по таблицам: источник / перенесено / отложено / ошибка;
- дубли номеров карт после внешнего обогащения;
- карты без подтверждённого номера, филиала происхождения или текущего местонахождения;
- коробки с конфликтующим составом;
- отправления с неопределённым маршрутом/составом/получением;
- заявки с неоднозначным инициатором или состоянием;
- конфликты размещения на полках;
- потерянные ссылки и неизвестные значения статусов;
- объекты, требующие ручного сопоставления.

Миграция считается успешной не только при совпадении количества строк, но и при согласованности текущих остатков, составов коробок, активных отправлений и истории.

## 5. Переключение

1. Провести пробную миграцию на копии production-БД.
2. Сверить отчёт с ответственными сотрудниками филиала, ЦО и архива.
3. Выполнить функциональные тесты на PostgreSQL.
4. Согласовать окно остановки записи.
5. Создать финальный SQLite snapshot и повторить миграцию.
6. Выполнить контрольные сверки и принять результат.
7. Переключить приложение на PostgreSQL.
8. Сохранить SQLite snapshot в защищённом режиме как источник для аудита/отката согласно утверждённой политике хранения.
9. Проверить резервное копирование и восстановление PostgreSQL.
10. Не удалять старую БД до формального завершения периода стабилизации и отдельного решения владельца системы.

## 6. Блокирующие вопросы до production

- Как обогащать legacy-карты номером, датой рождения и филиалом происхождения?
- Какой часовой пояс использовался при записи SQLite datetime('now','localtime') на сервере?
- Как трактовать старые `to_department` и значения статусов на основании фактического кода?
- Какие старые заявки относятся к филиальной модели возврата и как сохранить их как legacy?
- Как разрешать конфликты местонахождения, членства и архивных размещений?
- Какой режим целевой схемы использовать до обогащения legacy-карт: отдельная legacy_cards или nullable-поля с явным флагом неполноты?

До решения этих вопросов нельзя запускать автоматическую миграцию production-данных.
