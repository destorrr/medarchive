# МедАрхив — Дизайн-документ

> Утверждён: 2026-08-05 | Версия: 1.0.0 | Статус: дизайн завершён, переход к прототипу

## Контекст

Система управления архивом медицинских карт для организации с несколькими филиалами и центральным архивом. Карты упаковываются в коробки в филиалах, передаются курьером в архив, размещаются на секциях/полках. Обратный поток — возврат карт по заявкам.

**Базовые решения (зафиксированы в brainstorming):**

| Параметр | Решение |
|----------|---------|
| Развёртывание | Центральный сервер в локалке, веб-приложение |
| Стек | Python (FastAPI) + Jinja2/HTMX + SQLite |
| Архитектура | Монолит с луковыми слоями (домен → сервисы → репозитории → SQLite-адаптер) |
| Интеграция с ArchiMed+ | Первая версия автономна, слой данных预留 под будущую интеграцию |
| QR на карте | Только ФИО пациента |
| Сканеры | USB, клавиатурная эмуляция → `<input autofocus>` |
| Печать | Обычный принтер A4 (сетка QR-наклеек, режутся вручную) |
| Наклейка места на коробку | НЕ клеится — секция+полка только в программе |
| Роли | Филиал, Архив, Просмотр, Админ (курьер без доступа) |
| Приёмка/размещение | Два отдельных шага (статусы «принята» → «размещена») |
| Выбор места | Гибрид: сканирование QR полки + ручной выбор из списка |
| Возврат карт | По заявкам (филиал/медотдел → очередь → архив выполняет), одиночная карта или коробка возврата |
| Пользователей | 5–20 |
| Масштаб | Десятки отправок в неделю |

## Секция 1 — Архитектура и компоненты

### Обзор

Один сервер в локалке, один процесс FastAPI, одна SQLite-БД, монолит с луковыми слоями.

```
┌─────────────────────────────────────────────────┐
│              WEB (браузер)                       │
│   Филиал │ Архив │ Просмотр │ Админ             │
└────────────────────┬────────────────────────────┘
                     │ HTTP
┌────────────────────▼────────────────────────────┐
│              FastAPI-приложение                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────┐  │
│  │  Роутеры  │ │ Сервисы   │ │  Домен (чистый)  │  │
│  │ (HTMX)   │→│ (use     │→│  статусы,        │  │
│  │ Jinja2   │ │  cases)  │ │  бизнес-правила  │  │
│  └──────────┘ └────┬─────┘ └──────────────────┘  │
│                    │ интерфейсы репозиториев     │
│  ┌─────────────────▼─────┐                       │
│  │  SQLite-адаптер        │  ← смена БД =        │
│  │  (единственный, кто    │    замена этого      │
│  │   знает SQL)           │    модуля            │
│  └─────────────────┬─────┘                       │
└────────────────────┼────────────────────────────┘
                     │
        ┌────────────▼────────────┐
        │  SQLite (файл .db)      │
        │  + бэкап копией файла   │
        └─────────────────────────┘
```

### Слои и ответственность

| Слой | Что делает | Знает о SQL |
|------|-----------|-------------|
| **Роутеры** | HTTP-обработка, рендер HTML (Jinja2), HTMX-ответы | нет |
| **Сервисы** | Use cases: «упаковать коробку», «передать курьеру», «принять», «разместить», «оформить выдачу» | нет |
| **Домен** | Чистые правила: допустимые переходы статусов, валидация, вычисления | нет |
| **Репозитории** | Интерфейсы `CardRepository`, `BoxRepository`... | нет |
| **SQLite-адаптер** | Реализация репозиториев, SQL, схемы, миграции | да, единственный |

### Ключевые свойства

- Бизнес-логика не знает про БД → будущий ArchiMed+ (или PostgreSQL/MSSQL) подключается как новый адаптер, домен и сервисы не трогаются
- Сканеры = USB → просто `<input autofocus>` на каждой экранной форме; Enter от сканера = отправка формы
- Печать: сервер генерирует PDF/A4 с сеткой QR (например, 3×8 = 24 наклейки на листе), браузер отправляет на печать
- Аутентификация: сессии + пароли, роли проверяются в роутерах (декоратором)

## Секция 2 — Модель данных

### Таблицы SQLite

```
branches            филиалы (id, name, code)
users               пользователи (id, username, password_hash, role,
                    branch_id → branches, для роли Филиал)
couriers            справочник курьеров (id, name, phone?)
archive_sections    секции архива (id, name)
archive_shelves     полки (id, section_id → archive_sections, name,
                    qr_code — например "S1-P3")
cards               медкарты (id, full_name, status, created_at)
boxes               коробки (id, box_number, origin_branch_id → branches,
                    status, created_by)
box_cards           состав коробки (box_id, card_id, added_at, removed_at NULL)
                    ← карта может быть изъята при возврате, коробка живёт дальше
shipments           передачи (id, kind: box|card, box_id NULL, card_id NULL,
                    from_branch_id NULL, to_branch_id NULL, to_department BOOL,
                    courier_id → couriers, issued_by → users, issued_at,
                    received_by → users NULL, received_at NULL, status)
box_placements      размещения (box_id, shelf_id, placed_at, removed_at NULL)
                    ← история: коробку можно переставить на другую полку
requests            заявки на выдачу (id, card_id, requested_by → users,
                    target: branch_id NULL | department BOOL, status,
                    created_at, completed_at NULL, fulfilled_by NULL)
card_movements      журнал движений карты (card_id, action, from/to,
                    user_id, timestamp) — для роли «Просмотр» и аудита
```

### Как это работает для ключевых сценариев

- **Упаковка:** оператор создаёт коробку (получает номер) → сканирует карту → `cards.status = in_box`, строка в `box_cards`. QR коробки содержит просто номер коробки.
- **Передача:** `shipments(kind=box, box_id, courier_id, issued_by, issued_at)` → статусы карт в коробке = `in_transit`.
- **Приёмка:** архив сканирует номер коробки → программа показывает состав (`box_cards`) → подтверждение → `received_by/received_at` проставлены, карты = `in_archive`.
- **Размещение:** выбор/сканирование полки → `box_placements(box_id, shelf_id)`, карты = `placed`. **Никакой наклейки на коробку** — место только в программе.
- **Возврат по заявке:** `requests` (из филиала или медотдела) → архивариус изымает карту (`box_cards.removed_at`, статус = `pending_return`) → `shipments(kind=card, card_id, ...)` → получатель подтверждает → карта = `in_branch` / `in_department`.
- **Возврат коробкой:** если карт много — новая коробка с нумерацией, едет как обычная отправка, только `to_branch_id` заполнен.

### Статусы карты (жизненный цикл)

```
in_branch → in_box → in_transit → in_archive → placed
                              ↘ (возврат) pending_return → in_transit → in_branch / in_department
```

### Дубли ФИО

Карта идентифицируется по ФИО; при сканировании программа ищет по ФИО — если найдено несколько, показывает список, и оператор выбирает существующую или создаёт новую (карта физически в руках — визуальное подтверждение).

## Секция 3 — Экраны и UX-потоки

### Общие принципы

- Каждая форма со сканером = одно `<input autofocus>` — USB-сканер «печатает» код и жмёт Enter → мгновенная обработка, руки свободны
- После каждого скана поле очищается и снова в фокусе — можно сканировать подряд
- При дублях ФИО — модалка со списком совпадений (выбрать/создать новую)
- HTMX: обновление списков и модалки без перезагрузки страницы

### Экраны по ролям

**Филиал:**
1. **Упаковка коробки** — «Создать коробку» (получает номер, печать QR номера) → поле сканера: сканируешь карты подряд, список наполняется → «Закрыть коробку»
2. **Передача курьеру** — выбор коробки (скан) → выбор курьера из списка → подтверждение → печать/повторная печать QR коробки. Фиксируется issued_by/issued_at
3. **Мои отправки** — список отправленных коробок и их статус (в пути / принят / размещён)
4. **Заявки на возврат** (подать) — выбрать карту → куда (мой филиал / медотдел) → отслеживать статус заявки
5. **Приём возврата** — скан карты, подтверждение получения (received_by)

**Архив:**
6. **Приёмка** — скан коробки → состав → подтвердить приёмку (пересчёт опционален)
7. **Размещение** — скан коробки → выбор полки (скан QR полки ИЛИ список Секция→Полка) → подтвердить
8. **Очередь заявок** — список заявок на выдачу → «Выполнить»: скан карты → выбрать способ (одиночная / коробка возврата) → создать передачу курьеру
9. **Поиск карты/коробки** — по ФИО / номеру коробки: где находится (полка, статус, история из card_movements)
10. **Перестановка** — если коробку переносят на другую полку: скан коробки → новая полка → обновить размещение

**Просмотр (руководство/медотдел):**
11. **Дашборд** — статистика: сколько карт в архиве/филиалах/в пути, последние перемещения, открытые заявки
12. **Просмотр** — поиск, история движений, отчёты (без изменений)

**Админ:**
13. **Справочники** — филиалы, пользователи+роли, курьеры, секции/полки (с генерацией QR полок для печати)
14. **Всё из ролей выше** (полный доступ)

### Навигация

Единое меню, пункты фильтруются по роли. Логин-страница с сессиями.

### Печать

- Карта: QR с ФИО + подпись «ФАМИЛИЯ Имя Отчество»
- Коробка (филиал): QR с номером + «КОРОБКА №N»
- Полка: QR `S1-P3` + название (печатается один раз при создании полки, клеится на физическую полку)
- **Формат:** PDF/A4 с сеткой наклеек (например 3×8), режутся вручную
- Генерация на сервере (библиотека qrcode + reportlab/weasyprint), вывод на печать через браузер
- **Важно:** при размещении коробки на полку QR места НЕ печатается и НЕ клеится на коробку — информация о месте только в программе

## Секция 4 — Обработка ошибок и крайние случаи

### 4.1 Дубли ФИО

При сканировании карты ищется по `full_name`. Если найдено несколько:
- Модалка со списком совпадений (ФИО + последнее известное местонахождение)
- Оператор выбирает существующую или «Создать новую карту»
- **Правило:** создание новой карты с дублирующимся ФИО разрешено (пациенты-тёзки существуют), но с предупреждением

### 4.2 Сканер: неверный формат / отсутствие карты

- **QR не распознан / повреждён:** поле сканера подсвечивается красным, сообщение «Код не распознан — проверьте наклейку или введите ФИО вручную» + поле ручного ввода рядом
- **ФИО не найдено в БД:** предложение «Создать новую карту: <ФИО>» с автозаполнением (Enter = создать)
- **Одиночный скан карты, которая уже в другой коробке:** «Карта <ФИО> уже находится в коробке №X (филиал Y). Изъять из предыдущей коробки и добавить сюда?» — да/нет

### 4.3 Коробка: крайние случаи

| Ситуация | Поведение |
|----------|-----------|
| **Пустая коробка (0 карт)** | Нельзя «Закрыть» и передать курьеру. Кнопка заблокирована: «Добавьте хотя бы одну карту» |
| **Повторное сканирование той же карты в ту же коробку** | Игнорируется: «Карта <ФИО> уже в этой коробке» |
| **Отмена передачи курьеру** | Перевод коробки обратно в «упаковывается» (ручная, только если курьер ещё не принял) |
| **Курьер потерял / повредил коробку** | `shipments.status = lost/damaged`. Карты → «статус неизвестен», разбор через экран «Инциденты» |
| **Приёмка: несовпадение состава** | Расхождение: «Заявлено N, отсканировано M.» → «Принять как есть» (с записью в аудит) или «Отклонить» |

### 4.4 Заявки на выдачу

| Ситуация | Поведение |
|----------|-----------|
| **Карта не найдена в архиве** | Статус `not_found`, инициатор получает уведомление |
| **Карту уже вернули по другой заявке** | Конфликт: «Карта возвращена по заявке №Y. Отменить текущую?» |
| **Заявка просрочена (> N дней)** | Подсветка: жёлтый → красный по сроку |
| **Отмена заявки инициатором** | Возможна в статусах `new`/`in_progress`. После `completed` — через админа |

### 4.5 Размещение: конфликты

- **Несуществующий QR полки:** «Полка не найдена. Добавить новую?» (админ) / «Обратитесь к администратору»
- **Полка занята другой коробкой:** предупреждение с предложением переставить занятую коробку
- **Коробка уже размещена:** «Переставить на новое место?» — да/нет

### 4.6 Сетевые и системные ошибки

- **Потеря соединения:** HTMX-индикатор + таймаут 5 сек → «Сервер недоступен. Проверьте сеть»
- **SQLite блокировка:** WAL-режим, конкурентные чтения + один писатель. При блокировке: повтор через 200 мс, после 3 попыток — ошибка
- **Файл БД повреждён:** восстановление из последнего бэкапа

### 4.7 Бэкап и восстановление

- **Автоматический:** systemd timer — копия `.db` каждый час + daily, хранение 7 daily + 24 hourly
- **Ручной:** кнопка в админке «Создать бэкап сейчас»
- **Восстановление:** админ загружает `.db` через админку с подтверждением

## Секция 5 — Стратегия тестирования

### Пирамида тестов

```
         ┌──────┐
         │ E2E  │  ~5%  — критические пользовательские сценарии
         ├──────┤
         │ Инт. │  ~20% — репозитории + БД, роутеры + HTMX
         ├──────┤
         │ Юнит │  ~75% — доменная логика, валидация, статусные переходы
         └──────┘
```

### Юнит-тесты (домен)

- **Статусные переходы:** параметризованные тесты на все разрешённые/запрещённые переходы (`BoxStateMachine`, `CardStateMachine`)
- **Валидация:** `test_empty_box_cannot_be_closed`, `test_duplicate_card_in_same_box_ignored`

### Интеграционные тесты

- **Тестовая БД:** `:memory:` или `test.db`, миграции перед тестами
- **Репозитории:** CRUD для каждой сущности, дубли ФИО, жизненный цикл коробки
- **Роутеры (TestClient):** рендер экранов, HTMX-ответы на сканирование, 403 для неавторизованных, просмотр не может писать

### E2E (два сквозных сценария)

1. **Отправка карты в архив:** создать коробку → 3 карты → закрыть → курьер → приёмка → размещение на полке. Карты = `placed`
2. **Возврат по заявке:** заявка → выполнение (одиночная карта) → передача → подтверждение. Карта = `in_branch`

### Порог покрытия

- 80% доменного слоя, 60% сервисов
- `pytest --cov` при каждом запуске

## Секция 6 — План реализации (роадмап)

### Принцип

Инкрементальная поставка: каждый этап — работающий срез. Никакого «большого взрыва».

### Этапы

```
Этап 0  ▸  Каркас (1–2 дня)
Этап 1  ▸  Ядро: упаковка → передача → приёмка → размещение (3–4 дня)
Этап 2  ▸  Возвраты и заявки (2–3 дня)
Этап 3  ▸  Поиск, аудит, дашборд (1–2 дня)
Этап 4  ▸  Справочники, админка, бэкап (1–2 дня)
Этап 5  ▸  Полировка, документация, развёртывание (1 день)
```

### Этап 0 — Каркас и инфраструктура

| Задача | На выходе |
|--------|----------|
| Инициализация проекта | `pyproject.toml`, зависимости: FastAPI, Jinja2, aiosqlite, pytest, qrcode, weasyprint/reportlab |
| Луковая структура | `domain/`, `services/`, `repositories/`, `adapters/sqlite/`, `routers/`, `templates/` |
| Миграции | Скрипт создания всех таблиц (секция 2), `init_db.py`, фикстура для тестов |
| Аутентификация | Регистрация/логин, декоратор `@require_role(...)`, 4 роли |
| Макет (layout) | Jinja2-шаблон: сайдбар (ролевая фильтрация), шапка (роль/пользователь/выход) |
| Пустой дашборд | Заглушка «Добро пожаловать» для каждой роли |

### Этап 1 — Ядро: прямой поток

| Экран | Ключевые действия |
|-------|------------------|
| **Упаковка коробки** | Новая коробка → номер → поле сканера (autofocus, Enter) → список (htmx) → «Закрыть» (статус `ready`, печать QR на A4) |
| **Передача курьеру** | Скан/выбор коробки → выбор курьера → подтверждение → `shipments(issued_by, issued_at)` |
| **Приёмка** | Скан коробки → состав → «Подтвердить» → кнопка «Расхождение» (аудит) |
| **Размещение** | Скан коробки → выбор полки (QR или дерево) → «Разместить» → `placed` |
| **Мои отправки** | Таблица: номер, дата, курьер, статус |

### Этап 2 — Возвраты и заявки

| Экран | Ключевые действия |
|-------|------------------|
| **Подать заявку** | Поиск карты по ФИО → цель (филиал/медотдел) → создать → отслеживать |
| **Очередь заявок** | Список (новые → в работе → просроченные). «Выполнить»: скан → способ (одиночная/коробка) → `shipments(kind=card)` |
| **Приём возврата** | Скан карты → подтверждение → карта = `in_branch` |
| **Коробка возврата** | Новая коробка с нумерацией, обратное направление |
| **Аудит заявок** | История всех заявок |

### Этап 3 — Поиск, аудит, дашборд

| Экран | Ключевые действия |
|-------|------------------|
| **Поиск карты** | По ФИО/номеру коробки → местонахождение + история (`card_movements`) |
| **Поиск коробки** | По номеру → состав, хронология |
| **Журнал движений** | Фильтруемая таблица всех перемещений |
| **Дашборд** | Карточки статистики, последние движения, открытые заявки |

### Этап 4 — Справочники, админка, бэкап

| Экран | Ключевые действия |
|-------|------------------|
| **Филиалы, Пользователи, Курьеры** | CRUD |
| **Секции и полки** | CRUD + генерация QR полок → печать A4 для наклейки |
