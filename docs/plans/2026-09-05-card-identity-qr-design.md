# Концепция: идентификация карт по QR (номер карты из ArchiMed+)

Дата: 2026-09-05
Статус: концепция (brainstorm) — код НЕ меняется до утверждения
Проект: МедАрхив
Связано: приёмочное тестирование Этапа 1, п.1.12 (/search)

## 1. Проблема

При приёмке п.1.12 (/search по ФИО) всплыли «карты, числящиеся в нескольких коробках
сразу» (Иванов — в 10 активных коробках). Разбор показал: это не дефект отображения,
а **два независимых источника дублей в данных**, которые надо закрывать на входе.

### Вид 1 — дубли-записи `cards` (одна физическая карта = несколько строк БД)

- Единственный идентификатор записи — `full_name`, поиск при сканировании — точное
  равенство (`CardRepositoryImpl.find_by_name`: `WHERE full_name = ?`).
- Разные написания ФИО («Голубев Артём» / «Artyom Golubev» / «Голубев Артём Сергеевич»),
  опечатки → точное совпадение не находится → создаётся **новая** запись
  (`BoxService.scan_card`: `cards[0]` или `card_repo.create`).
- Два разных пациента-тёзки с одинаковым ФИО → берётся первый попавшийся
  (в коде комментарий: «operator should resolve duplicates in UI» — но UI резолва нет).
- Схема `cards` минимальна: `id, full_name, status, created_at` — нет ни номера карты,
  ни даты рождения, ни телефона.

### Вид 2 — дубли-размещения (одна запись карты в N активных коробках)

- `BoxRepositoryImpl.add_card` проверяет дубль **только внутри той же коробки**
  (`WHERE box_id = ? AND card_id = ? AND removed_at IS NULL`).
- Запрета «карта уже числится в другой активной коробке» при добавлении НЕТ.
- Метод `BoxRepositoryImpl.card_in_other_boxes` существует, но используется только в
  `BoxService.remove_card` (решить, возвращать ли статус `in_branch`) — как guard на
  добавление он не вызывается.
- Итог: оператор укладывает карту в новую коробку, не выписав из старой → «остаток».

## 2. Ключевой факт (решение пользователя)

Физическая карта пациента уже имеет **номер карты из ArchiMed+**; там же есть ФИО и
дата рождения. ArchiMed+ может **сгенерировать QR** с этим содержимым, QR печатается
на титульном листе медицинской карты.

Вывод: появляется стабильный внешний ключ карты, не зависящий от ручного ввода имени.

## 3. Целевая модель идентификации

### 3.1 QR на титуле карты

Содержимое QR (пайлоад): `номер карты + ФИО + дата рождения`.
- **Номер карты** — первичный ключ поиска (точное попадание, ноль неоднозначности).
- **ФИО + ДР** — для подтверждения оператором и для ручного поиска, когда QR не читается
  (старые карты без наклейки, повреждённый QR).
- Телефон в QR — НЕ включаем по умолчанию (изменчив; в ArchiMed+ может отсутствовать;
  решается отдельно, см. «Открытые вопросы»).

### 3.2 Схема `cards` (миграция)

```
cards:
  id            INTEGER PK            (внутренний, как сейчас)
  card_number   TEXT UNIQUE           -- номер карты из ArchiMed+ (nullable для legacy)
  full_name     TEXT NOT NULL
  date_of_birth TEXT                  -- YYYY-MM-DD, nullable для legacy
  phone         TEXT                  -- опционально (см. открытые вопросы)
  status        TEXT NOT NULL
  created_at    TEXT NOT NULL
```

- `card_number UNIQUE` — гарантия: одна физическая карта = одна запись.
- Legacy-строки без номера: `card_number IS NULL` + фолбэк поиска по ФИО+ДР.

### 3.3 Поток упаковки (скан QR) — `BoxService.scan_card`

1. Считываем QR → `card_number`, `full_name`, `date_of_birth`.
2. `find_by_card_number(card_number)`:
   - найдена → используем её (проверка ФИО/ДР на расхождение — предупреждение);
   - не найдена → экран подтверждения: «В системе нет карты № N. ФИО: …, ДР: … —
     завести карту?» (паттерн уже есть в `/requests/new`: поиск → список совпадений →
     создание).
3. Добавление в коробку — с guard «карта в другой активной коробке» (см. п.4).

### 3.4 Ручной ввод (без QR)

Поиск по ФИО **+ дате рождения** (не точный `full_name`):
- нормализация: регистр, «Ё/Е», лишние пробелы;
- совпадения по ФИО+ДР показываются списком → оператор выбирает или создаёт новую
  (с полями card_number / ФИО / ДР / телефон).

## 4. Guard «карта уже в другой активной коробке» (независим от QR)

`BoxService.scan_card` перед `add_card`:
```
if await box_repo.card_in_other_boxes(card.id, box_id):
    → ошибка/подтверждение: «Карта числится в коробке B-0003.
      Убрать оттуда и положить сюда?» (автовыписка из старой = remove_card)
```
- Останавливает накопление «остатков» Вида 2 на новых данных.
- Требует разовой чистки уже накопленных остатков в демо-БД
  (Иванов и др.: снять карту со всех коробок, кроме актуальной — по цепочке переходов
  или вручную; либо пересоздать демо-данные под новую модель).
- Отдельный маленький TDD-фикс; не зависит от QR-этапа.

## 5. Влияние на /search (п.1.12) и другие экраны

- /search: после закрытия дублей на входе «карта в N коробках» становится редким
  edge-case (только legacy-остатки до чистки). Дизайн можно брать **простой** —
  вариант C (имя + статус + крупное место актуальной коробки), а остатки показывать
  одной серой строкой «не выписана из коробок: …» (правило B-1), без зелёных мест у
  остатков.
- Показ номера карты и ДР полезен в результатах поиска (уточнение личности) —
  решается на этапе дизайна /search.
- /requests/new (заявки) — тот же поиск/создание переводится на ФИО+ДР + card_number.

## 6. Миграция и обратная совместимость

- SQLite-миграция: `ALTER TABLE cards ADD COLUMN card_number TEXT`,
  `ADD COLUMN date_of_birth TEXT`, уникальный индекс на `card_number` (после дедупликации).
- Дедупликация legacy: найти записи-дубли по нормализованному ФИО (+ДР, если есть) →
  объединить `box_cards`/историю на каноническую запись (или пометить и не трогать до
  ручной сверки).
- Заполнение `card_number` для legacy — отдельной процедурой/импортом из ArchiMed+
  (или вручную при следующем обращении к карте).

## 7. Открытые вопросы (нужны ответы до плана)

1. Формат пайлоада QR и способ его генерации в ArchiMed+ (какой текст кодируем —
   разделители, порядок полей; есть ли образец).
2. Есть ли у ArchiMed+ API/выгрузка реестра карт (номер+ФИО+ДР) для первичного
   наполнения МедАрхива, или записи заводятся только сканированием по мере работы?
3. Включать ли телефон (нужен ли в МедАрхиве вообще)?
4. Считывание QR в МедАрхиве: камера (веб/моб.), USB-сканер (эмуляция клавиатуры) —
   какой сценарий у оператора упаковки?
5. Судьба накопленных «остатков» Вида 2 в демо/боевых данных: чистка скриптом или
   пересоздание демо.

### Ответы пользователя (2026-09-05)

1. **Формат QR** — образца пока нет, будет позднее. Контракт пайлоада фиксируем,
   когда появится; реализацию скана не начинать до утверждения формата.
2. **Наполнение** — только сканированием, API/выгрузки реестра из ArchiMed+ НЕТ.
   Первичная регистрация карты = первое сканирование в МедАрхиве с подтверждением
   оператором (создание по данным QR).
3. **Телефон** — НЕ нужен, исключить из модели (поля `phone` не вводить).
4. **Считывание** — USB-сканер, эмуляция клавиатуры (строка ввода + Enter).
   Камера/мобильный сценарий не нужен.
5. **Остатки в демо** — чистка разовым скриптом (снять карту со всех активных коробок,
   кроме актуальной по цепочке переходов; перед записью — select-preview + бэкап БД).
