# Дизайн: редизайн контура возврата (этап 2) — единый стиль, авто-филиал, русские статусы

Дата: 2026-09-05 · Проект: МедАрхив · Статус: согласован с пользователем (макет v3 + вопрос по курьеру)

## 1. Контекст

Приёмочное тестирование этапа 2 (обратный поток) дошло до п.2.1/2.2 — функционально работает,
но пользователь дал замечания:

1. После «Запросить» нет сообщения об успехе — сразу редирект на /requests/my.
2. Дизайн страниц контура возврата не соответствует остальным страницам
   (этап-2 страницы не проходили макет-редизайн, в отличие от /receive, /placement, /search).
3. Статусы показываются сырыми английскими значениями (`placed`, `new`, `cancelled`),
   нужны русские подписи-бейджи, как везде.
4. Непонятно, к какому филиалу привязан пользователь: в шапке «Филиал» (роль),
   в заявке можно выбрать «Филиал_2». Пользователь не должен выбирать филиал —
   он подставляется автоматически из учётной записи, и филиал должен быть виден в интерфейсе.

Решения пользователя (зафиксированы в чате):
- Объём: **весь контур возврата** — /requests/new, /requests/my, /requests (очередь), /receive-return.
- Филиал пользователя показывать **глобально в сайдбаре** (правка base.html).
- Передача карты курьеру (п.2.4): **селект курьера остаётся в строке очереди** (единый стиль),
  поведение п.2.3/2.4 не меняется.
- Макет утверждён: `canvas/documents/medarchive/return_flow_redesign_mockup_v3.html`.

## 2. Цели

- Единый язык дизайна контура возврата с уже принятыми страницами (/receive, /placement, /search):
  карточки, таблицы `.data`, бейджи статусов, крупные поля ввода, кнопки `.btn`.
- Филиал текущего пользователя виден в сайдбаре на всех страницах.
- Авто-филиал: заявка создаётся с филиалом из учётной записи пользователя; выбора нет.
- Статусы заявок и карт — русские бейджи.
- Одноразовые флеш-сообщения после действий (создание, отмена, выполнение).
- Даты в человеческом виде `ДД.ММ.ГГГГ ЧЧ:ММ`.

Вне объёма: глобальный редизайн всего приложения (отдельный этап), логика заявок/возврата
(меняются только представление и авто-филиал при создании), доработка статусной машины.

## 3. Изменения по страницам

### 3.1 base.html (глобально)

**Сайдбар — блок пользователя** вместо `role-badge`:
- Первая строка (крупно, белым): имя филиала пользователя, если он есть (`users.branch_id`
  → `branches.name`); иначе — роль («Архив», «Администратор», «Просмотр»).
- Вторая строка (мелко, серым): логин (`user.username`).
- Примеры: `Филиал_2 / filial`, `Архив / arhiv`.

Реализация: `get_current_user` тянет `users` с `LEFT JOIN branches` и кладёт на объект
`User` динамический атрибут `branch_name`; `_menu_context` отдаёт `user_branch`
(имя филиала или роль) и `user_login`; шаблон рендерит блок `.who`.

**Общие стили (вынести в base.html):**
- таблицы `.data` (ширина 100%, `border-collapse`, фиксированные колонки через `colgroup`,
  th/td с паддингами, `white-space: nowrap` у ФИО и дат) — единый вид всех таблиц контура;
- бейджи статусов заявок: `.badge-new` (голубой), `.badge-in_progress` (жёлтый),
  `.badge-completed` (зелёный), `.badge-cancelled`/`.badge-not_found` (серый) —
  рядом с уже существующими карточными `.badge-*`;
- компактный селект в строке таблицы `.row-sel`;
- флеш-блок из контекста `flash` (`flash-success` / `flash-error` CSS уже есть).

### 3.2 /requests/new — новая заявка (роль: Филиал)

- Поиск: крупный input (стиль /search) + кнопка «Найти» (btn-primary, без эмодзи).
- Результаты поиска: таблица `.data`: колонки **ФИО | Статус | (действие)**.
  Статус карты — русский бейдж (`CARD_STATUS_LABELS`, классы `.badge-<status>` уже в base).
  В колонке действия — одна кнопка **«Запросить»** (без подписи «→ Филиал_2»).
- Под таблицей подсказка: «Филиал возврата — \<имя филиала\> (ваш, из учётной записи).
  Поле выбора филиала убрано.»
- Создание: POST принимает `card_id`; `target_branch_id` **берётся из `user.branch_id`**.
  Если у пользователя нет филиала — ошибка-флеш «К вашей учётной записи не привязан филиал».
- После создания — 303 на `/requests/my` с флешем
  «Заявка на возврат создана. Карта будет доставлена в «\<филиал\>» (уточнить формулировку — см. 3.3).
- HTML-форма: убрать `<select name="target_branch_id">` и ветку «branches» из контекста поиска.

### 3.3 /requests/my — мои заявки (роль: Филиал)

- Таблица `.data`: **Карта | Статус | Дата | (действие)**.
- Статус заявки — русский бейдж (`REQUEST_STATUS_LABELS`: Новая / В работе / Выполнена /
  Отменена / Не найдена).
- Дата — `ДД.ММ.ГГГГ ЧЧ:ММ` (парсинг `created_at`).
- Действие — кнопка **«Отменить»** (`.btn-danger-ghost`) только для `new`/`in_progress`;
  POST /requests/cancel → 303 на /requests/my + флеш «Заявка отменена».
- Вверху страницы — флеш-блок (создание/отмена).
- Пустое состояние: «Нет заявок. Создать новую» (ссылка на /requests/new).

### 3.4 /requests — очередь заявок (роль: Архив)

- Таблица `.data`: **Карта | Филиал | Статус | Дата | (действие)**.
  - «Филиал» — имя филиала-получателя (`target_branch_id` → `branches.name`, JOIN в выборке очереди).
  - Статус — русский бейдж.
  - Дата — `ДД.ММ.ГГГГ ЧЧ:ММ`.
  - Действие — компактный селект курьера (`.row-sel`) + кнопка **«Выполнить»**
    (поведение сохраняется: выполнить заявку, при выбранном курьере — создать возвратную отправку).
- «Запросил» (сырое `user#id`) заменяется на колонку «Филиал» — оператору архива важнее,
  куда возвращать карту.
- После выполнения — 303 на /requests + флеш «Заявка выполнена»; ошибки — флеш-error
  (сохранить текущую обработку ValueError).
- Пустое состояние: «Нет активных заявок».

### 3.5 /receive-return — приём возврата (роль: Филиал)

Приводится к двухшаговому паттерну /receive:
1. Карточка сканера: input «Сканер (QR-код или ID карты)» + кнопка **«Проверить»** (btn-primary).
2. POST `/receive-return/check` (htmx, target = #scan-result): фрагмент с превью карты:
   таблица `.data` **Карта | Статус | Назначение**, где:
   - Карта — ФИО (бейдж статуса: ожидаем «В пути» `in_transit`);
   - Назначение — филиал из активной card-отправки (`to_branch_id`), без подписи «ваш филиал»;
   - если карта не в `in_transit` / нет активной отправки — флеш-error с текстом ошибки сервиса.
3. Кнопка **«Подтвердить получение»** — под таблицей (`.table-footer`, справа),
   без эмодзи, того же размера, что «Проверить». POST `/receive-return/confirm` (как сейчас),
   успех → 303 (существующий редирект сохранить), ошибки — флеш-error во фрагменте/на странице.

Примечание: существующий POST /receive-return/confirm остаётся рабочим «как есть»
(обратная совместимость с E2E-тестом); добавляется только GET-страница с превью-фрагментом.

## 4. Сквозные изменения

- `domain/statuses.py`: словарь `REQUEST_STATUS_LABELS` для `RequestStatus`.
- `routers/dashboard.py`:
  - `get_current_user` (в `dependencies.py`): JOIN `branches` → `branch_name` на User;
  - `_menu_context`: поля `user_branch`, `user_login`;
  - подготовка строк таблиц (label/badge/дата) — по образцу `_prepare_search_rows` (/search);
  - флеш-хелпер: POST → `set_cookie("ma_flash", …)` + 303; GET-страницы контура читают
    cookie в контекст `flash` и удаляют её в ответе (одноразовость).
  - `/requests/new` create: `target_branch_id = user.branch_id`, убрать селект и список филиалов.
- `services/request_service.py`: выборка очереди — JOIN `branches` (имя филиала-получателя);
  выборка «моих заявок» — без изменений (филиал один, свой).
- Шаблоны: `base.html`, `request_new.html`, `requests_my.html`, `request_queue.html`,
  `receive_return.html` (+ фрагмент результата проверки приёма возврата).
- Тесты: обновить существующие (создание заявки теперь без target_branch_id → филиал юзера,
  даты, русские подписи, флеш) + новые на превью приёма возврата.

## 5. Технические риски / границы

- Не менять статусную машину заявок/карт и маршруты отправки — только вид и авто-филиал.
- E2E-тест обратного потока (`tests/test_stage2_smoke.py`) должен остаться зелёным
  (confirm-эндпоинт приёма возврата не ломаем).
- Флеш — одноразовый через cookie; страницы, не относящиеся к контуру, cookie не читают
  (глобальный вид не меняется).
