# МедАрхив: матрица маршрутов и полномочий

**Статус:** проект для согласования  
**Версия:** 1.0  
**Дата:** 2026-11-11  
**Связанные документы:** `target-data-model.md`, `technical-specification.md`

## 1. Назначение

Документ фиксирует допустимые направления физического перемещения медицинских карт и коробок, полномочия ролей и условия изменения текущего местонахождения. Матрица является нормативной для реализации: интерфейс, API, сервисный слой и ограничения БД не должны допускать запрещённые маршруты.

Термины:
- **Филиал** — конкретная локация подразделения организации.
- **Центральный офис (ЦО)** — отдельная логистическая локация.
- **Архив** — единственная физическая архивная локация.
- **Отправление** — единая физическая передача от одного отправителя одному адресату, с обязательным курьером.
- **Заявка** — запрос ЦО на получение конкретной карты из архива; сама по себе не перемещает карту.

## 2. Матрица допустимых маршрутов

| Откуда | Куда | Допустимость | Кто создаёт отправление | Условие / назначение |
|---|---|---|---|---|
| Филиал A | Центральный офис | Да | Сотрудник филиала A | Передача карт и/или коробок в ЦО |
| Филиал A | Архив | Да | Сотрудник филиала A | Прямое архивирование; заявка ЦО не требуется |
| Филиал A | Филиал B | Нет в базовом объёме | — | Прямые межфилиальные отправления не согласованы |
| Центральный офис | Филиал A | Да | Сотрудник ЦО | Возврат/передача карт и коробок в филиал |
| Центральный офис | Архив | Да | Сотрудник ЦО | Возврат карт/коробок в архив; в частности возврат карты, ранее выданной по заявке ЦО |
| Центральный офис | Центральный офис | Нет | — | Перемещение внутри одной локации оформляется операцией хранения/перекомплектации, а не отправлением |
| Архив | Центральный офис | Да, только по заявке ЦО | Сотрудник архива | Выдача одной или нескольких запрошенных карт по соответствующим заявкам |
| Архив | Филиал | Нет | — | Архив не отправляет карты напрямую в филиалы |
| Архив | Архив | Нет как отправление | — | Внутреннее перемещение оформляется размещением/перемещением в архивных зонах |

Правила:
1. В каждом отправлении ровно одна локация-отправитель и одна локация-получатель.
2. Получатель не выбирается произвольно: сервер проверяет маршрут по этой матрице и контексту операции.
3. Архив → ЦО разрешён только при наличии активной заявки ЦО на каждую выдаваемую карту.
4. Возврат ЦО → Архив не требует новой заявки на выдачу; это самостоятельное обратное перемещение.
5. Архив не инициирует отправления по собственной инициативе.
6. Межфилиальные отправления не входят в согласованный базовый объём. Добавлять их можно только отдельным решением.
7. Отправление с одинаковыми отправителем и получателем запрещено.

## 3. Полномочия ролей

Обозначения: **Да** — разрешено в рамках назначенной локации и серверных проверок; **Нет** — запрещено; **Ограниченно** — разрешено только при указанных условиях.

| Операция | Филиал | Центральный офис | Архив | Администратор |
|---|---:|---:|---:|---:|
| Просматривать карты своей локации | Да | Да | Да | Да |
| Просматривать карты других филиалов | Нет | Да | Ограниченно | Да |
| Регистрировать новую карту по QR | Да | Нет | Нет | Нет |
| Изменять идентификационные данные карты | Ограниченно | Ограниченно | Ограниченно | Ограниченно |
| Создавать коробку | Да | Да | Да, только для комплектации выдачи по заявке ЦО | Нет |
| Добавлять/изымать карты из коробки в своей локации | Да | Да | Ограниченно | Нет |
| Перекладывать карты между коробками в своей локации | Да | Да | Ограниченно | Нет |
| Создавать отправление | Да | Да | Нет | Нет |
| Выбирать курьера для отправления | Да | Да | Нет | Нет |
| Передавать отправление курьеру | Да | Да | Нет | Нет |
| Подтверждать получение отправления | Если филиал — адресат | Если ЦО — адресат | Если архив — адресат | Нет |
| Создавать заявку на получение карты из архива | Нет | Да | Нет | Нет |
| Обрабатывать заявку и готовить выдачу | Нет | Нет | Да | Нет |
| Отмечать карту как не найденную при обработке заявки | Нет | Нет | Да | Нет |
| Размещать/перемещать коробки в архивных зонах | Нет | Нет | Да | Нет |
| Списывать пустую коробку в своей локации | Да | Да | Ограниченно | Нет |
| Управлять пользователями и справочниками | Нет | Нет | Нет | Да |
| Исправлять ошибку через корректирующее событие | По своим операциям | По своим операциям | По своим операциям | Ограниченно |

Уточнения к полномочиям:
- «В своей локации» означает, что пользователь филиала действует только от имени своего филиала; пользователь ЦО — от имени ЦО; пользователь архива — от имени архива.
- Архивные операции с коробками разрешены только для коробок, физически принятых архивом.
- Администратор не должен использовать административную роль для обычной логистики или подтверждения приёмки. Исправление выполняется специальной корректирующей операцией с обязательной причиной и аудитом.
- Изменение ФИО, даты рождения и телефона не должно быть обычным свободным редактированием. Нужны проверка полномочий, причина, аудит и защита от незаметной перезаписи. Точный процесс уточняется отдельно.
- Роль просмотра не получает права на изменяющие операции. Если она назначается, её область видимости задаётся отдельно.

## 4. Жизненный цикл отправления

### 4.1 Создание
1. Пользователь выбирает допустимого получателя.
2. Система проверяет допустимость маршрута.
3. Пользователь добавляет отдельные карты и/или коробки, которые физически находятся в локации отправителя.
4. Система проверяет, что ни один объект не находится в другом активном отправлении и не включён в состав отправления повторно.
5. Пользователь выбирает активного курьера из справочника. Курьер обязателен.
6. Система фиксирует состав отправления. После отправки состав не редактируется обычным способом.

Создание черновика отправления не должно менять местонахождение объектов.

### 4.2 Передача курьеру
1. Отправитель подтверждает фактическую передачу курьеру.
2. В одной транзакции отправление переходит в состояние «в пути».
3. Все включённые объекты получают местонахождение через ссылку на это конкретное отправление: постоянная локация очищается, `current_shipment_id` устанавливается.
4. Записывается событие передачи с пользователем и временем.

Передача курьеру не является приёмкой и не завершает отправление.

### 4.3 Приёмка адресатом
1. Получатель открывает отправление, адресованное его локации.
2. Система показывает ожидаемый состав.
3. Получатель подтверждает физическое получение всего отправления.
4. До подтверждения система проверяет соответствие фактического результата правилам приёмки.
5. В одной транзакции все объекты перемещаются в локацию получателя, ссылка на активное отправление очищается, отправление получает состояние «получено», создаётся событие приёмки.

Только пользователь локации-получателя может подтвердить приёмку. Администратор не подменяет получателя.

### 4.4 Расхождение и отмена
- Частичная приёмка запрещена.
- При недостаче, излишке, повреждении или несоответствии состава обычная приёмка блокируется.
- Система сохраняет отправление в состоянии, позволяющем расследовать расхождение; фиксируются автор, время и описание проблемы.
- Нельзя просто удалить строку состава или вручную переписать текущее местонахождение.
- Разрешение расхождения выполняется отдельным регламентированным действием с аудитом. Конкретные статусы и полномочия для такого действия следует утвердить до реализации.
- Отмена допустима только до передачи курьеру. После передачи курьеру отмена не должна возвращать объекты отправителю автоматически: требуется отдельная операция возвратного перемещения или расследования.

## 5. Жизненный цикл заявки ЦО на карту из архива

1. Пользователь ЦО находит карту, текущее местонахождение которой — архив.
2. ЦО создаёт заявку на конкретную карту. Создание заявки не меняет местонахождение карты.
3. Архив видит заявку в очереди и проверяет физическое наличие карты.
4. Если карты найдены, архив готовит их к выдаче по соответствующим активным заявкам. Он может отправить одну карту отдельно, несколько карт отдельными позициями либо сформировать новую коробку и поместить в неё выбранные карты. Для каждой карты должна существовать активная заявка; новая коробка создаётся в рамках подготовки этого отправления.
5. Архив выбирает курьера и передаёт отправление курьеру.
6. Карта находится в пути до подтверждения получения ЦО.
7. Пользователь ЦО подтверждает получение целого отправления.
8. В одной транзакции карта получает текущее местонахождение ЦО, а заявка — состояние «выполнена».
9. Если карта не найдена, архив фиксирует результат «не найдена» с комментарием. Заявка не считается выполненной; её дальнейшее состояние определяется отдельным решением ЦО.
10. Если полученную карту нужно вернуть, ЦО создаёт отправление ЦО → Архив. После приёмки архивом карта снова находится в архиве.

Ограничения:
- Заявки создаёт только ЦО.
- Одна карта не может иметь более одной активной заявки на выдачу.
- Нельзя включить в выдачу карту, не находящуюся в архиве, или карту без активной заявки.
- Отправление Архив → ЦО не может быть направлено в филиал.
- Выполнение заявки привязано к подтверждённой приёмке ЦО, а не к передаче курьеру.
- Заявка и отправление — разные сущности с отдельными жизненными циклами.

## 6. Коробки и состав отправления

1. Коробки создают филиалы и ЦО. Архив вправе создать новую коробку только для комплектации одной или нескольких карт, запрошенных ЦО, и отправки их в ЦО. Архив не создаёт самостоятельные отправления и не комплектует коробки по собственной инициативе.
2. Коробка принадлежит текущей локации по фактическому местонахождению, а не навсегда филиалу происхождения.
3. При отправке коробки её состав фиксируется в манифесте отправления. Нельзя менять состав коробки, находящейся в пути.
4. Если отправляется коробка, карты внутри неё физически перемещаются вместе с коробкой. Система должна однозначно отражать местонахождение и состав всех карт.
5. Если отправляются отдельные карты, они включаются в отправление непосредственно.
6. Одна и та же карта не может одновременно попасть в манифест отдельно и через отправляемую коробку.
7. После приёмки коробка и содержащиеся в ней карты получают локацию получателя.
8. Изменение состава коробки в локации фиксируется историей членства. Пустая коробка может быть оставлена для повторного использования или списана.
9. Списать можно только пустую коробку, не находящуюся в пути и не задействованную в активной операции.

## 7. Локальные операции без отправления

Следующие действия не являются физическим перемещением между локациями и не должны создавать отправления:
- регистрация карты филиалом по QR;
- создание коробки в филиале или ЦО;
- добавление/изъятие карты из коробки при нахождении объектов в одной локации;
- перекладывание карты между коробками в одной локации;
- размещение принятой коробки в секции/на полке архива;
- перемещение коробки между зонами/полками архива;
- списание пустой коробки.

Каждая операция всё равно журналируется.

## 8. Обязательные серверные инварианты

Реализация должна обеспечивать эти проверки не только в интерфейсе, но и на уровне сервисов/БД, где это возможно:

1. У карты и коробки ровно одно текущее состояние местонахождения: постоянная локация либо конкретное активное отправление.
2. Отправить можно только объект, который сейчас находится у отправителя.
3. Объект не может одновременно участвовать в двух активных отправлениях.
4. У отправления ровно один получатель и обязательный курьер.
5. Маршрут проверяется по матрице раздела 2.
6. Архив → ЦО требует активной заявки на каждую карту.
7. Архив не создаёт отправления самостоятельно.
8. Приёмку подтверждает только пользователь локации-получателя.
9. Приёмка целого отправления атомарна.
10. Частичная приёмка не допускается.
11. Состав отправления после передачи курьеру неизменяем.
12. Коробка в пути не может быть вскрыта/перекомплектована в системе.
13. Карта не может одновременно входить в две активные коробки.
14. История событий не редактируется и не удаляется прикладными операциями.
15. Повтор запроса/двойной клик не должен создавать повторные отправления, приёмки или события.
16. Любая корректировка состояния сопровождается причиной, автором, временем и ссылкой на исправляемое событие, если оно есть.

## 9. Сценарии, обязательные для тестирования

1. Филиал отправляет коробку напрямую в архив; архив принимает; коробка размещается на полке.
2. Филиал отправляет отдельную карту в ЦО; ЦО принимает.
3. ЦО отправляет коробку в филиал; филиал принимает.
4. ЦО создаёт заявку на архивную карту; архив отправляет её в ЦО; ЦО принимает; заявка становится выполненной.
5. ЦО возвращает полученную карту в архив; архив принимает.
6. Филиал пытается создать заявку на архивную карту — отказ и на уровне API.
7. Архив пытается отправить карту непосредственно в филиал — отказ.
8. Архив пытается создать отправление без заявки ЦО — отказ.
9. Пользователь филиала пытается отправить карту, которая фактически находится в другом филиале, ЦО, архиве или в пути — отказ.
10. Пользователь не из локации-получателя пытается подтвердить приёмку — отказ.
11. В манифесте обнаружено расхождение — обычная приёмка не выполняется и местонахождение не меняется.
12. Двойная отправка или повторная приёмка — второе изменение не создаёт новых событий.
13. Попытка изменить состав коробки или отправления в пути — отказ.
14. Попытка списать непустую коробку или коробку в пути — отказ.
15. Архив перемещает коробку между полками — местонахождение архивной локации остаётся прежним, история размещений пополняется.

## 10. Решения, требующие отдельного подтверждения

Следующие вопросы намеренно не закрепляются как уже согласованные:
- точные статусы и порядок разбора расхождений при приёмке;
- допускается ли отмена заявки ЦО после того, как архив начал её обработку или отправил карту;
- кто и по какому регламенту выполняет корректирующие операции после передачи курьеру;
- разрешено ли отправление одновременно нескольких коробок и отдельных карт в одном манифесте (текущая модель допускает это при отсутствии дублей);
- точный регламент изменения идентификационных данных карты.

До принятия решений по этим вопросам реализация должна блокировать неоднозначные действия, а не выбирать поведение автоматически.
