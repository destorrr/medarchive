# PRODUCT-DECISIONS-DB-SECURITY — решения по архитектуре PostgreSQL

Дата согласования: 2026-11-18  
Этап: UX-06 — архитектура безопасности БД и транзакций  
Статус: **все четыре решения приняты владельцем продукта**

## DB-SEC-01. Доверие к идентичности actor

**Решение — принято:** для первой целевой версии используется модель `application-authenticated actor`; отдельный identity broker не вводится.

- HTTP/application layer аутентифицирует пользователя и проверяет актуальность его учётной записи.
- Application layer выполняет проверку роли и scope.
- Use case передаёт в защищённую DB-команду UUID аутентифицированного пользователя и идентификаторы команды/корреляции.
- DB-команда проверяет существование пользователя, его активность и соответствие роли требуемой операции; actor сохраняется в доменном событии.
- Эта модель обеспечивает прослеживаемость действий, но **не является независимым криптографическим доказательством личности со стороны БД** и не защищает от полного компрометирования доверенного application layer.
- Не называть actor UUID «подтверждённым самой БД пользователем». Усиление через identity broker возможно только отдельным решением после пересмотра threat model.

## DB-SEC-02. Защищённые DB-команды

**Решение — принято:** критические бизнес-переходы выполняются через защищённые DB-команды; прямой runtime DML для соответствующих критичных workflow-таблиц запрещается после завершения миграционного перехода.

- Команды образуют явный allowlist бизнес-операций.
- Runtime получает только необходимые права чтения и вызова разрешённых команд.
- Runtime не получает произвольные INSERT/UPDATE/DELETE права на критичные workflow-таблицы.
- Проверки роли, состояния, принадлежности объектов, состава, handover и иных бизнес-предусловий выполняются на серверной/DB границе, а не только в UI.
- Отзыв legacy DML прав выполняется только после инвентаризации всех ORM paths, фоновых задач, скриптов, health checks и инфраструктурных процедур и после поэтапного перевода workflows.
- Конкретная реализация команд, функций, grants и безопасного `SECURITY DEFINER` остаётся предметом технической спецификации и проверки фактических PostgreSQL privileges.

## DB-SEC-03. Общая модель DomainEvent

**Решение — принято:** сохраняется общий append-only `DomainEvent` с типизированным и версионируемым контрактом событий. Отдельная таблица `RequestEvent` не вводится.

- События заявки используют общий механизм и стабильные event types с версией payload.
- Для событий фиксируются aggregate owner, actor, время БД, command/correlation identifiers и минимально необходимый payload.
- События нескольких агрегатов, относящиеся к одной бизнес-команде, записываются в одной транзакции.
- Не дублировать персональные данные пациента в payload без доказанной необходимости.
- Административный/безопасностный аудит остаётся отдельным контуром доступа и не смешивается с операционной историей объектов.
- Перед реализацией проверить существующих consumers, фактическую схему `DomainEvent` и обратную совместимость старых payload.

## DB-SEC-04. Разделение PostgreSQL principals

**Решение — принято:** используются три отдельные PostgreSQL-роли с разными назначениями и учётными данными.

| Principal | Тип | Назначение |
|---|---|---|
| `medarchive_owner` | NOLOGIN | Владелец схем и объектов БД; не используется приложением |
| `medarchive_migrator` | LOGIN | Отдельная идентичность миграционного runner; контролируемое получение прав владельца для DDL |
| `medarchive_runtime` | LOGIN | Приложение; минимальные права чтения и вызова DB-команд, без DDL и прямого DML критичных таблиц |

- Runtime и migration connection URLs разделены; credentials migrator не доступны web workers.
- Bootstrap principals, membership и grants выполняются контролируемой инфраструктурной/DBA процедурой, не обычной runtime-инициализацией приложения.
- Backup/restore и иные инфраструктурные задачи при необходимости получают отдельные principals; их нельзя автоматически совмещать с runtime или migrator.
- Реальные owners, grants и default privileges целевого окружения должны быть инвентаризированы до изменения прав.

## Граница утверждения

Утверждены архитектурные принципы и целевые ограничения. Это **не разрешение на реализацию**. До отдельного согласования реализации не менять исходники приложения, SQL/DDL, Alembic revisions, тесты, deployment templates, секреты или конфигурацию PostgreSQL.

## Следующие технические действия

1. Детализировать контракт каждой DB-команды: actor, входные параметры, предусловия, блокировки, изменения, события, идемпотентность и ошибки.
2. Сопоставить команды с текущими ORM-моделями, таблицами, workflow services и существующими event consumers.
3. Подготовить матрицу grants по схемам/таблицам/sequence/functions и сценариям runtime/migrator.
4. Сформировать поэтапный rollout и preflight checklist для целевого PostgreSQL окружения.
5. Отдельно определить минимальные права чтения и сохранение application ACL/scope; DB grants не заменяют ролевую фильтрацию данных.
