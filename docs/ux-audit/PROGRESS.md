- Не менять код приложения до согласования всех бизнес-процессов, маршрутов движения карт/коробок и целевой UX-модели.

## 2026-11-17 — старт аудита

### Подтверждено по исходникам PostgreSQL

- Панель, поиск и журнал движений доступны всем пяти ролям через общие endpoints.
- В меню филиала присутствуют поиск, журнал, приёмка, упаковка и передача курьеру.
- В меню ЦО присутствуют поиск, журнал, запрос карт из архива, приёмка, упаковка и отправка; предусмотрен отдельный экран внешнего ответственного хранения.
- В меню архива присутствуют поиск, журнал, приёмка, размещение и заявки ЦО.
- В меню администратора присутствуют панель, поиск, журнал и администрирование.
- В меню viewer присутствуют панель, поиск и журнал.
- Для операций архива используются серверные ограничения `archive_only`; для операций ЦО — `central_only`; для административных страниц и действий — `admin_only`.
- Административные страницы охватывают филиалы, пользователей, курьеров, места хранения, аудит и инциденты.
- В текущей реализации есть отдельные страницы для реестра отправлений и приёмки. Это возможная точка лишних переходов, требующая проверки полного пользовательского сценария.

### Предварительные UX-наблюдения — требуют дальнейшей проверки

1. Глобальный журнал движений доступен всем ролям, хотя его полезность для повседневной работы операционных ролей сомнительна.
2. Приёмка отправления в текущих формах предполагает подтверждение отправления как целого; необходимо выяснить, допустима ли частичная приёмка и как должны обрабатываться расхождения.
3. Реестр отправлений и экраны приёмки разделены; необходимо проверить, можно ли сократить переходы, не нарушив контрольные процедуры.
4. Меню частично формируется по роли в коде общей панели; автоматическое добавление ссылки на отправления создаёт дополнительную логику навигации, которую следует унифицировать.

### Важные ограничения достоверности

- Проверка меню и зависимостей маршрутов — ещё не полная проверка всех действий и прав на уровне бизнес-операций.
- Список FastAPI endpoints не равен полной карте экранов и переходов.
- Ни один из описанных выше маршрутов движения не утверждён как целевой процесс.
- Физическая вместимость мест хранения и корректность метрик загрузки ещё не проверены.
- Инвентаризация SQLite пока предварительная; удаления и миграции не выполнялись.

- В общей навигации ссылка на отправления может добавляться шаблоном автоматически для филиала, ЦО и архива.

## 2026-11-17 — аудит филиального и административного интерфейсов

Создан документ `UX-01-branch-and-admin-audit.md` (коммит `12090b3fb45068bdb4d326274973f9dbf0fde4ba`).

### Подтверждено по филиалу

- Упаковка выполняется в контексте одной коробки: создание → проверка QR → подтверждение новой карты при необходимости → состав → извлечение/списание пустой коробки.
- QR-данные вводятся как JSON; для новой карты предусмотрен отдельный экран/шаг сверки до регистрации.
- Выбор коробки ограничивается активной коробкой филиала; сервер проверяет принадлежность локации и роль branch.
- Передача вынесена в отдельную страницу; филиал выбирает одну коробку, получателя из активных локаций ЦО/архива и активного курьера.
- Передача серверно создаёт отправление, добавляет коробку и выполняет handover в одной транзакции.

### Подтверждено по администрированию

- Административная панель содержит шесть модулей: пользователи/роли, филиалы, курьеры, секции/полки, инциденты, журнал админ-действий.
- Все проверенные административные страницы и действия защищены `admin_only`.
- Пользователи: создание, изменение роли/филиала, активация и отключение, смена пароля; собственную учётную запись нельзя отключить или лишить роли admin.
- Филиалы: создание, изменение реквизитов, включение/отключение.
- Курьеры: создание с необязательным телефоном, активация/отключение.
- Полки: создание, редактирование, активация/отключение; интерфейс предупреждает о запрете отключения занятой полки.
- Журнал админ-действий — отдельный read-only экран с фильтрами и пагинацией по 50; сервер ограничивает его событиями `admin.%`.
- Инциденты доступны администратору для просмотра, без изменения груза из этой карточки.

### Гипотезы/вопросы

- Возможность продолжения упаковки другим сотрудником филиала: сейчас автоматический выбор коробки без ID ориентирован на создателя.
- Реальный формат QR и сценарий сканера.
- Отличие допустимого состава отправления филиала и ЦО.
- Редактирование ФИО пользователя отсутствует в видимой форме редактирования.
- Удобство повторного ввода названия секции при создании каждой полки.
- Полномочия и ответственность по разрешению инцидентов.

## 2026-11-17 — проверка сервисных инвариантов движения

Создан документ `UX-01-domain-invariants-audit.md` (коммит `8c6609bbcc25974227421859614d709e13b4e239`).

### Подтверждено по workflow и PostgreSQL-моделям

- Backend разрешает пять направлений: филиал→ЦО, филиал→архив, ЦО→филиал, ЦО→архив, архив→ЦО.
- В отправление допускаются коробки и/или отдельные карты; пустое отправление и пустая коробка запрещены.
- Коробки и карты проверяются на принадлежность исходной локации, активность, текущие размещения, внешнее хранение, повторное включение и согласованность состава.
- Архив→ЦО ограничен отдельными картами, каждая с активной заявкой ЦО.
- Инцидент можно зарегистрировать только для отправления в пути; регистрирующий должен быть сотрудником исходной или целевой локации. Само событие инцидента не перемещает груз.
- Разрешение инцидента реализовано как полная приёмка после повторной проверки полного манифеста.
- PostgreSQL-модель отправления ограничивает статусы и согласованность временных/авторских полей; состав связан FK и уникальными ограничениями.
- Регистрация карты через QR требует предварительной проверки и отдельного подтверждения; сервис проверяет роль branch, активную локацию и совпадение идентификационных данных.
- В сервисе администрирования филиал обязателен только для роли branch; для остальных ролей он должен отсутствовать. Последнего активного администратора нельзя отключить/понизить.

### Важное расхождение интерфейса и модели

Backend допускает несколько коробок в отправлении и сочетание коробок с отдельными картами. Просмотренные формы филиала и ЦО позволяют выбрать только одну коробку (форма ЦО дополнительно поддерживает отдельные карты). Это различие требует решения владельца процесса; пока не называем его ошибкой.

## 2026-11-17 — матрица ролей и первичная SQLite-инвентаризация

Созданы документы:
- `UX-01-roles-and-permissions.md` — матрица пяти существующих ролей, PostgreSQL HTML-страниц, операционных POST guards, административных API и тестового покрытия (коммит `7609333643e543d013c23ce0303e34f2b4ceaed4`).
- `SQLITE-INVENTORY.md` — первичный реестр конфигурационных, runtime, dependency, адаптерных и тестовых точек SQLite (коммит `a890cf9147cd6ebc4a278ae679f8cec3c1d6bad1`).

### Новые подтверждённые факты по ролям

- `shipment_reader` разрешает только `branch`, `central_office`, `archive`; admin и viewer не имеют доступа к реестру и карточке отправления.
- QR-этикетка коробки доступна admin и операционному пользователю только для коробки его текущей локации; viewer и другие локации запрещены. Это покрыто role-matrix тестом.
- Интеграционный тест административной матрицы проверяет отказ четырём не-admin ролям на HTML-страницах, API чтения/записи и основных семействах мутаций.
- Тест интерфейсной матрицы проверяет GET-доступ и навигацию для всех пяти ролей. Он не доказывает положительный доступ каждой роли ко всем POST-операциям.
- Внешнее хранение ЦО имеет отдельный интеграционный тест: архив и viewer получают 403; повторная отметка/возврат не создают дублирующие события; карта остаётся на балансе ЦО и исключается из обычной упаковки/отправки до физического возврата.
- Полный сценарий заявки ЦО покрыт тестом: архив выдаёт только карты с активными заявками без транспортной коробки; заявка становится выполненной после приёмки отправления ЦО.

### Новые факты по SQLite

- По умолчанию `MEDARCHIVE_AUTH_BACKEND=sqlite`; PostgreSQL-режим требует `MEDARCHIVE_POSTGRES_ENABLED=true`.
- `main.py` выбирает отдельный набор PostgreSQL или legacy SQLite роутеров; SQLite startup init выполняется только в SQLite-режиме.
- Общий `dependencies.py` всё ещё импортирует SQLite Database и legacy AuthService; `init_dependencies` создаёт SQLite Database даже при PostgreSQL-конфигурации, хотя PG startup не вызывает её инициализацию.
- `aiosqlite` остаётся обязательной зависимостью проекта; отдельные SQLite adapters и tests присутствуют в дереве.

### Важные границы

- Матрица отражает текущую реализацию, не целевые полномочия. Вопросы о видимости viewer, административном read-only доступе и глобальном журнале остаются открытыми.
- Наличие тестов в репозитории не означает, что они запускались в этой проверке. PostgreSQL integration tests зависят от `MEDARCHIVE_DATABASE_URL`.

## 31. AdminSecurityAudit — fail-closed outage policy approved (2026-11-18)
