# UX-01 — аудит внешнего хранения, администрирования и ограничений PostgreSQL

Дата: 2026-11-17  
Ветка: `docs/ux-audit-project`  
Статус: фактическая реализация PostgreSQL; не утверждённый регламент.

## 1. Внешнее ответственное хранение ЦО

Проверены `postgresql_central_office.py`, `postgresql_card_custody.py`, модель `Card`, шаблон и `test_postgresql_central_custody.py`.

### Фактический процесс

- Экран `GET /central/custody` доступен только `central_office`. В список попадают активные карты на балансе ЦО, не в отправлении и не в активной коробке.
- `POST /central/custody/mark` принимает карту, тип внешнего хранения, название организации и комментарий.
- Поддерживаемые типы: `at_court`, `at_insurance`, `at_external_organization`. Название организации обязательно.
- Workflow проверяет активного пользователя с ролью central_office, блокирует строку карты, проверяет активность карты и то, что она находится на балансе локации ЦО; запрещает активную коробку и активное отправление.
- При передаче меняются `custody_status`, `external_organization`, `external_comment`, `external_since`; `current_location_id` остаётся ЦО, `current_shipment_id` остаётся NULL. Создаётся событие `card.external_custody_started`.
- `POST /central/custody/return` требует, чтобы карта ранее была отмечена внешней; сохраняет прежние сведения в payload события `card.external_custody_returned`, очищает внешнюю организацию/дату, устанавливает `available`. Учётная локация остаётся ЦО.
- Повторная передача и повторный возврат отклоняются. Пока карта находится во внешнем хранении, она исключена из обычной упаковки и отправки.
- Роутерный guard `central_only` и сервисная проверка активного central_office пользователя дополняют друг друга.

### Тестовое подтверждение

`test_postgresql_central_custody.py` параметризован по трём типам внешнего хранения и проверяет полный цикл: передачу, сохранение баланса ЦО, запрет повторной передачи, исключение из упаковки/отправки, отказ ролям archive/branch/viewer, возврат, запрет повторного возврата и повторную доступность карты после возврата.

### Нерешённые вопросы процесса

- Кто физически передаёт карту и получает её обратно, если действие в системе выполняет сотрудник ЦО?
- Нужны ли номер акта/договора, дата ожидаемого возврата, контакт принимающей организации и подтверждающий документ?
- Нужны ли напоминания/просрочка и кто отвечает за контроль?
- Следует ли различать юридическое основание, организацию и тип внешнего хранения?
- Достаточно ли комментария и события либо необходима отдельная сущность/реестр передачи?

Текущий workflow — учётный статус, а не подтверждение фактической передачи третьей стороне документом.

## 2. Администрирование PostgreSQL

Проверены `postgresql_admin.py`, `postgresql_admin_pages.py`, `postgresql_admin_service.py` и `test_postgresql_admin_service.py`.

### Филиалы и локации

- Создание филиала создаёт связанную логистическую локацию branch; код/название обязательны, изменения филиала синхронизируют имя локации.
- Деактивация запрещена, пока у филиала есть активные пользователи, карты на балансе, активные коробки или отправления в статусах draft/in_transit/exception.
- При проверке деактивации блокируется строка локации; комментарий в сервисе указывает на общий lock protocol с workflow движения инвентаря.
- Активация/деактивация синхронизирует `Branch.is_active` и `Location.is_active`.
- Важно: наличие карт на балансе препятствует отключению филиала независимо от статуса карты; коробки учитываются только со статусом active.

### Курьеры

- Создание требует ФИО; телефон необязателен.
- Деактивация запрещена, если за курьером закреплены draft/in_transit/exception отправления.
- При отсутствии активных отправлений курьера можно деактивировать; исторические отправления не удаляются.

### Полки

- Создание/изменение требует секцию и номер полки; пара `section_name + shelf_name` уникальна.
- Деактивация запрещена, пока на полке есть активные размещения коробок или отдельных карт.
- В модели нет вместимости, размеров, числа мест или измерения физической ёмкости. Поэтому проценты заполненности архива не могут быть выведены из этих полей.

### Пользователи

- Существуют только пять допустимых ролей: branch, central_office, archive, admin, viewer.
- Роль branch требует branch_id; остальные роли не должны иметь branch_id. Проверка выполняется сервисом и CHECK constraint модели.
- Логин нормализуется в lowercase; обязательны логин и ФИО; создание проверяет уникальность логина и активность филиала для branch.
- Изменение пользователя поддерживает необязательную смену пароля и сохранение текущего active, если поле не передано.
- Advisory transaction lock сериализует изменения пользователей; нельзя лишить роли/деактивировать последнего активного admin. API также запрещает администратору отключить себя или снять с себя admin.
- События администрирования записываются в DomainEvent с типами `admin.*`.

### Тесты и пробелы

`test_postgresql_admin_service.py` проверяет в основном валидацию входных данных, привязку ролей к branch_id, регистрацию маршрутов и правила длины пароля. В изученном файле нет полноценной БД-интеграционной матрицы жизненного цикла филиала/курьера/полки/пользователя, конкурирующей деактивации или сохранения последнего admin. Отдельные ограничения видны в коде сервиса, но их фактическая устойчивость требует тестов на PostgreSQL.

## 3. Ограничения и модель PostgreSQL

Проверена `src/medarchive/adapters/postgresql/models.py`.

### Структурные ограничения

- `locations.kind` ограничен branch/central_office/archive; branch_id обязателен только для branch. Частичные уникальные индексы ограничивают одну локацию на филиал и по одной локации ЦО/архива.
- `users.role` ограничен пятью ролями; CHECK требует branch_id только для branch.
- `cards.status`, `boxes.status`, `cards.custody_status` имеют CHECK по разрешённым значениям.
- Для карты и коробки CHECK требует ровно одно текущее состояние: постоянная локация или активное отправление.
- У карты CHECK связывает поля внешнего хранения: available означает отсутствие даты/организации; внешний статус требует даты и непустой организации.
- Коробка имеет уникальный номер; цикл — уникальный номер в пределах коробки, положительный номер и не более одного открытого цикла на коробку.
- Активное членство карты в коробке ограничено уникальным частичным индексом на card_id.
- Отправление проверяет разные локации, допустимые статусы и согласованность handover/receive/exception/cancelled полей.
- ShipmentBox/ShipmentCard используют FK и уникальные ограничения для связей манифеста; текущая карта/коробка ссылается на пару объект+отправление через отложенный FK.
- ArchiveRequest ограничивает статусы и связь с отправлением; частичный уникальный индекс запрещает более одной активной заявки на карту.
- Для коробки/карты допускается только одно активное размещение; даты снятия не могут предшествовать размещению.
- Полка уникальна по секции и номеру, но вместимость не моделируется.

### Что БД не доказывает сама по себе

- CHECK/unique/FK не заменяют сервисную проверку полномочий пользователя и локации.
- В модели `ShipmentCard` уникальность пары card_id/shipment_id не равна уникальности активной карты между всеми отправлениями; активное состояние дополнительно обеспечивается workflow и ссылкой текущего местонахождения.
- Нельзя заключать, что каждое бизнес-правило защищено БД, только по наличию ORM-модели. Требуется сопоставить миграции Alembic и фактическую схему PostgreSQL, включая partial indexes, deferrable FKs и CHECK constraints.
- В этом блоке не выполнялось подключение к БД и не запускались миграции/тесты; вывод основан на исходниках модели и просмотренных тестах.

## 6. Дополнительная проверка административного HTML-интерфейса

Проверены все handlers `postgresql_admin_pages.py` и шаблон `admin/postgresql_users.html`.

- Все HTML GET/POST операции филиалов, пользователей, курьеров, полок, административного аудита и инцидентов используют `admin_only`.
- HTML-формы вызывают тот же `PostgreSQLAdminService`, что и JSON API; изменения завершаются commit, ожидаемые ошибки — rollback.
- HTML-форма редактирования пользователя отправляет checkbox `is_active=true` только при включённом флажке; отсутствие значения трактуется как false. Это соответствует интерактивному смыслу переключателя. JSON API отдельно использует nullable `is_active`, поэтому отсутствие поля сохраняет текущее состояние.
- Для текущего администратора HTML-шаблон передаёт скрытое `is_active=true` и не показывает переключатель статуса; handler дополнительно запрещает снять роль admin или отключить себя.
- Административный журнал — read-only, фильтруется по `admin.%`, имеет пагинацию по 50 записей и фильтры по типу события, объекту, исполнителю и датам. Он не является общим журналом клинических событий.
- Глобальные страницы инцидентов доступны только admin; список строится по отправлениям с заполненными exception timestamp/note, карточка возвращает 404, если инцидентная запись не найдена.
- В просмотренном `test_postgresql_admin_service.py` нет HTTP role matrix для всех HTML POST routes; ролевые проверки административных GET/инцидентов покрываются другими тестами частично. Не найдена исчерпывающая матрица всех admin HTML POST × чужие IDs/состояния.
