## 1. Существующие роли

## 4. Администрирование и API

- HTML-администрирование: все проверенные GET/POST страницы защищены `admin_only`.
- JSON API: `GET/POST /api/admin/branches`, `PUT /api/admin/branches/{branch_id}`, действия активации/деактивации; `GET/POST /api/admin/users`, `PUT /api/admin/users/{user_id}` — защищены `admin_only`.
- Тест `test_non_admin_roles_cannot_open_postgresql_admin_pages_or_api` проверяет отказ всем четырём неадминистративным ролям для HTML-страниц, API чтения/записи и набора HTML/API мутаций.
- Административные API и HTML-формы частично дублируют управление справочниками и пользователями. Это отдельный вопрос архитектуры интерфейса, не нарушение доступа само по себе.

## 5. Навигация по ролям

Тестовая матрица фиксирует текущую навигацию:

- **branch:** панель, поиск, журнал движений, отправления, приёмка, упаковка, передача курьеру.
- **central_office:** панель, поиск, журнал движений, отправления, запрос карт из архива, приёмка, упаковка, отправка, внешнее хранение.
- **archive:** панель, поиск, журнал движений, отправления, приёмка, размещение, заявки ЦО.
- **admin:** панель, поиск, журнал движений, административный раздел; внутри него — справочники, пользователи, аудит, инциденты.
- **viewer:** панель, поиск, журнал движений.

Текущая навигация не доказывает, что каждый пункт необходим пользователю в ежедневной работе. Целевая навигация — предмет UX-02/UX-04.

## 7. Наблюдения и вопросы для согласования

### Подтверждённые факты

1. `admin` не имеет доступа к реестру отправлений через `shipment_reader`; это согласуется с отдельной административной областью, но бизнес-необходимость просмотра отправлений администратором не подтверждена.
2. `viewer` видит общие панель, поиск и журнал, но не видит реестр отправлений, этикетки коробок и операционные разделы.
3. QR-этикетка разрешена администратору и операционным пользователям только для коробки своей локации; viewer и пользователь другой локации получают отказ.
4. Общие страницы панели/поиска/истории доступны всем пяти ролям.
5. Внешнее хранение доступно только ЦО; интеграционный тест отдельно проверяет отказ архива и viewer.

### Не установлено / требует решения владельца продукта

- Должен ли admin иметь read-only доступ к отправлениям и истории конкретных объектов?
- Должен ли viewer видеть все филиалы/локации или только назначенную область? Текущая тестовая матрица проверяет доступ к страницам, но не полную семантику фильтрации данных viewer.
- Нужен ли глобальный журнал всем пяти ролям или только отдельным уполномоченным ролям?
- Должен ли пользователь филиала иметь доступ к QR-этикеткам коробок своей локации? Сейчас это разрешено.
- Должны ли права на отдельные корректирующие действия отличаться от права выполнять обычную операцию? Текущая модель использует те же ролевые guards для разрешения инцидента.

## 8. Что ещё нужно проверить

- Объектные проверки: принадлежность карты/коробки/отправления локации, активность локации, права на изменение чужих объектов.

## 9. Уточнение семантики данных для admin и viewer (2026-11-17)

Повторно прочитаны PostgreSQL handlers поиска/панели, тесты branch scope и интерфейсная role matrix.

### Фактическое поведение кода

- В postgresql_dashboard.py функция _search_context применяет location predicate только для branch, archive и central_office. Для admin и viewer location_id остаётся None, поэтому SQL-запросы поиска карт и коробок не ограничиваются текущей локацией.
- В postgresql_dashboard.py обработчик /dashboard для ролей вне branch/central_office/archive (то есть admin и viewer) считает общие показатели по всей БД: общее число карт, коробок, карт в архиве/филиалах/пути и открытые заявки. Для них же не применяется фильтр ленты последних DomainEvent по локации.
- Следовательно, на текущем уровне кода admin и viewer получают глобальный обзор данных через панель и глобальный поиск. Это описание реализации, а не утверждение, что такой объём доступа согласован или допустим.
- Для branch есть отдельный интеграционный тест, доказывающий фильтрацию поиска и истории по своей локации и отсутствие карточек другого филиала.
- test_postgresql_dashboard.py и test_postgresql_interface_role_matrix.py подтверждают доступ viewer к страницам, но не проверяют, что viewer должен/не должен видеть данные других локаций. Комментарий в role matrix тесте явно исключает viewer из доступа к QR-этикеткам, но это не доказывает ограничение поиска/панели.
- Для admin глобальный обзор может быть намеренным, но это тоже следует подтвердить как отдельное полномочие, а не выводить из наличия роли admin.

### Риск и вопрос владельцу

Так как в системе обрабатываются персональные данные пациентов (включая ФИО и сведения о медицинских картах), глобальный доступ viewer/admin к поиску и сводкам — вопрос разграничения данных, а не только удобства интерфейса. До решения владельца продукта нельзя считать эту семантику утверждённой.

**Требует решения:** viewer видит все локации, одну назначенную область или только обезличенные/агрегированные данные? Какие конкретно поля пациента доступны viewer? Должен ли admin иметь глобальный поиск по ФИО/номеру карты и просмотр глобальной ленты событий, или административная роль должна быть отделена от доступа к медицинским данным?

**Статус:** фактическое поведение подтверждено чтением кода; требуемый объём доступа не согласован. Рекомендуется отдельный положительный/отрицательный тест на межлокационную видимость для viewer и admin после принятия решения.

## 10. Проверка отображаемых полей и панели admin/viewer (2026-11-17)

Дополнительно прочитаны `search_fragment.html` и `dashboard.html`, чтобы проверить не только SQL scope, но и фактически выводимые поля.

### Подтверждённое отображение

- Результат поиска карт выводит `full_name`, статус, коробку и место хранения; номер карты используется для поиска, но в карточке результата шаблон его не показывает.
- Результат поиска коробок выводит номер, статус, место и количество карт.
- Для admin/viewer эти результаты формируются без location predicate; следовательно, глобальная выдача поиска включает ФИО пациентов и контекст хранения по всем локациям.
- Панель выводит агрегаты «Карт всего», «В архиве», «В филиалах», «В пути», «Коробок всего», «Открытых заявок» и последние события. Для admin/viewer эти показатели глобальные.
- В ленте последних событий поле `card_name` заполняется ФИО карты, если событие относится к карте; поэтому глобальная лента также может раскрывать ФИО.

### Граница проверки

Подтверждено чтением SQL-условий, сборки контекста и Jinja-шаблонов. В этом блоке не выполнялся новый запуск интеграционных тестов; наличие PostgreSQL тестов в репозитории не считается доказательством их фактического прохождения.

### Рекомендуемое тестовое покрытие после решения политики

Создать фикстуры с картами и коробками минимум в двух филиалах, архиве и ЦО; затем отдельно проверить для admin и viewer:
1. какие объекты возвращает поиск;
2. какие персональные поля видны;
3. какие агрегаты и события попадают на панель;
4. доступ к истории объектов и глобальному журналу;
5. отсутствие данных за пределами согласованного scope.

Тесты должны фиксировать утверждённую матрицу доступа, а не автоматически воспроизводить нынешнее поведение.

**Статус:** подтверждённая реализация; политика доступа и ожидаемые результаты тестов не согласованы.


## 10. Уточнение области данных журнала и панели по ролям (2026-11-17)

Повторно проверены полный обработчик `/history`, последние события панели и поиск в `postgresql_dashboard.py`.

### Подтверждённое поведение

- Для `admin` и `viewer` `/history` не получает event-фильтр: запрос выбирает глобальные `DomainEvent`. В представлении события дополнительно раскрываются в номер карты и ФИО пациента, номер коробки/отправления, имя исполнителя и направления движения.
- Для `branch`, `central_office` и `archive` журнал ограничен подзапросами по объектам/отправлениям доступной области. Для branch есть специальное правило: в журнале сохраняется история карт, зарегистрированных этим филиалом (`Card.origin_branch_id`), даже после ухода карты из его текущей локации. Это явно отражено комментарием в коде.
- При этом поиск филиала ограничен текущей локацией и отправлениями в пути, а не всем набором карт, когда-либо зарегистрированных филиалом. Следовательно, поиск и история branch имеют разные, но намеренно/фактически реализованные области видимости.
- Лента панели операционных ролей фильтруется по текущей локации и отправлениям, связанным с ней; для admin/viewer фильтра нет. В ленте для card-событий отображается `Card.full_name`.
- Текущая матрица GET-доступа не проверяет ни содержимое глобального журнала admin/viewer, ни особое правило истории origin-branch.

### Следствие для проверки полномочий

Проблема шире глобального поиска: глобальный журнал раскрывает исторические события и персональные сведения; область аудита branch отличается от области оперативного поиска. До согласования нельзя автоматически считать это дефектом или целевым правилом. Требуется определить отдельно: (1) scope поиска, (2) scope истории объекта/журнала, (3) доступ к ФИО и другим полям, (4) допустимость истории после перемещения карты из филиала.

**Статус:** фактическое поведение подтверждено кодом; целевая семантика доступа не согласована. Тесты на положительную/отрицательную видимость для viewer/admin и на историю origin-branch не найдены в проверенной матрице.


## 11. Административные экраны: объектная область и персональные данные

Проверены `postgresql_box_labels.py`, `postgresql_admin_pages.py` и `postgresql_admin.py`.

- `GET /boxes/{box_id}/label` использует аутентификацию, требует активную коробку с текущей локацией и проверяет объектную область: admin разрешён для любой локации; branch — только для филиала своего `branch_id`; central_office/archive — только для соответствующей локации; viewer запрещён. Это отдельное объектное правило, а не только проверка роли.
- `GET /admin/audit` защищён `admin_only` и фильтрует события по префиксу `admin.%`; это отдельный административный журнал, не весь журнал движения.
- `GET /admin/incidents` и `GET /admin/incidents/{shipment_id}` защищены `admin_only`, но не ограничивают выборку локацией. Карточка инцидента раскрывает состав отправления, включая номера карт и ФИО пациентов, а также отправителя, получателя, курьера, заявителя и сведения о разрешении.
- Следовательно, admin имеет глобальный read-only доступ к инцидентам и связанным персональным данным, хотя в реестр обычных отправлений через `shipment_reader` не допущен. Это ещё одно различие полномочий, которое следует согласовать явно.
- JSON API `/api/admin/*` также защищён `admin_only`; просмотренные операции справочников и пользователей используют сервисный слой и транзакционные commit/rollback. Полная проверка всех бизнес-инвариантов сервиса остаётся отдельной задачей.

**Вопрос для владельца:** должен ли admin видеть ФИО и полный манифест всех инцидентных отправлений, или достаточно обезличенной/агрегированной информации и операционного доступа по запросу? Факт глобальной выборки подтверждён кодом; целевое полномочие не согласовано.
