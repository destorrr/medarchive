# UX-01 — инвентаризация маршрутов и переходов архивного интерфейса

Дата: 2026-11-17  
Ветка: `docs/ux-audit-project`  
Статус: инвентаризация текущего PostgreSQL UI; не целевая схема.

## 1. Основные страницы архива

| Страница | GET | Назначение |
|---|---|---|
| Приёмка | `/receive` | Входящие отправления в архив, состав, сверка, подтверждение, разрешение инцидента |
| Размещение | `/placement` | Внутренние коробки, состав коробок, размещение коробок/отдельных карт на полках, снятие, списание |
| Заявки ЦО | `/requests` | Очередь заявок, состояние карты, извлечение карты из внутренней коробки, подготовка к выдаче, отметка «не найдена», формирование отправления |
| Этикетка коробки | `/boxes/{box_id}/label` | Печать/просмотр QR-этикетки при выполнении проверки области доступа |

| Исходная страница | POST | Результат |

| Приёмка | `/receive/confirm` | 303 обратно на `/receive`; подтверждение полного состава |

| Размещение | `/placement/new-internal-box` | 303 на `/placement`; создать внутреннюю коробку, опционально из выбранных карт |
| Размещение | `/placement/add-card` | 303 на `/placement`; добавить отдельную карту во внутреннюю коробку |
| Размещение | `/placement/remove-card-from-box` | 303 на `/placement`; извлечь карту из внутренней коробки |
| Размещение | `/placement/box` | 303 на `/placement`; назначить коробке полку |
| Размещение | `/placement/card` | 303 на `/placement`; назначить отдельной карте полку |
| Размещение | `/placement/remove-box` | 303 на `/placement`; снять коробку с полки |
| Размещение | `/placement/remove-card` | 303 на `/placement`; снять карту с полки |
| Размещение | `/placement/write-off-box` | 303 на `/placement`; списать пустую коробку |
| Заявки | `/requests/not-found` | 303 на `/requests`; отметить карту не найденной с пояснением |

| ЦО — создание заявки | `/requests/create` | 303 обратно в контекст создания заявки; создать заявку по выбранным картам |

## 3. Фактические переходы в шаблонах

### Размещение

- Операции над составом коробки выполняются inline в строке/карточке коробки: добавить карту, извлечь карту, назначить полку.
- Размещение отдельной карты на полке также выполняется inline в строке карты.
- Снятие коробки/карты с полки выполняется inline в соответствующей таблице.
- QR-этикетка открывается отдельной вкладкой.
- Создание внутренней коробки — отдельная форма в верхней части страницы и отдельная форма для набора отмеченных карт.
- При отсутствии полок интерфейс предлагает перейти в административный раздел для настройки секций/полок.

### Заявки

- Очередь содержит заявки в разных состояниях; выбор к исполнению доступен для новых заявок, когда карта не в коробке и не размещена отдельно на полке.
- Если карта находится во внутренней коробке, строка предлагает действие «Извлечь из коробки»; POST возвращает пользователя в очередь.
- Если карта размещена на полке, строка предлагает переход на `/placement`; фактическое снятие с полки выполняется уже на другой странице.
- Исполнение нескольких заявок объединяется в одну форму с выбором доступных карт и получателем/курьером.
- Отметка «не найдена» выполняется из строки заявки и требует пояснения.
- После POST пользователь возвращается на страницу списка, а не на отдельную карточку заявки.

## 5. Наблюдения для UX-02/UX-04

1. Очередь заявок уже содержит действия над картой и коробкой, но операция снятия с полки уводит в отдельный раздел. Возможность выполнить это действие прямо в очереди требует проверки сценария и согласования.
2. Состояния «карта в коробке» и «карта на полке» дают разные действия в строке заявки; их нужно визуально различать, иначе пользователю сложно понять, почему одна карта готова к выдаче, а другая нет.
3. Создание отправления по заявкам — групповое действие, но отдельные карты сначала должны стать физически доступными. Стоит оценить единый сценарий «подготовить выбранные заявки», не меняя бизнес-правила до согласования.
4. Переход в административный раздел при отсутствии полок — межрольная зависимость рабочего процесса; возможно, требуется диагностическое сообщение/запрос администратору, а не ссылка на чужую операционную задачу.
5. Возврат всех POST на список упрощает поток, но пользователь может потерять контекст конкретной строки/фильтра/прокрутки. Нужно проверить query parameters, flash messages и фокус после обновления.

**Не утверждено:** объединение страниц, изменение переходов, inline-снятие с полки, новые статусы или действия.


## 6. Резервное копирование и административная поверхность

- Legacy SQLite router `routers/admin.py` содержит `GET /admin/backup`, `POST /admin/backup/create`, `POST /admin/backup/restore` и использует `BackupService` для файловой SQLite базы.
- Эти маршруты подключаются только при `auth_backend=sqlite`; PostgreSQL admin router не содержит backup/restore UI.
- PostgreSQL backup реализован эксплуатационно через `scripts/backup.sh`, systemd service и timer; это не веб-маршруты.
- Поэтому в текущем PostgreSQL интерфейсе нет экранов backup/restore. Это наблюдение требует продуктового/эксплуатационного решения, но не следует автоматически добавлять UI в UX-переработку.


## 7. Маршруты логистики PostgreSQL и объектная видимость отправлений

Дополнительно проверены `postgresql_transfer.py`, `postgresql_branch.py`, `postgresql_central_office.py`, `postgresql_shipments.py`, `postgresql_shipment_workflow.py`, `postgresql_receive_queries.py` и интеграционные тесты.

### Передача филиалом

- `GET /transfer` и `POST /transfer/confirm` доступны только роли `branch`.
- Форма предлагает активные коробки текущего филиала, активные локации ЦО/архива и активных курьеров. В форме выбирается одна коробка.
- POST не создаёт отдельный долгоживущий черновик: в одной транзакции создаётся отправление, в него добавляется коробка, выполняется handover; затем один commit. Ошибка workflow откатывает транзакцию.
- Серверный workflow повторно проверяет роль и исходную локацию, допустимость направления, активность получателя/курьера, фактическое местонахождение коробки, состав и отсутствие конфликтующего активного отправления. Нельзя отправить пустую коробку.

### Приёмка и инциденты

- Очереди обычной приёмки выбирают только `in_transit` отправления, где `to_location_id` совпадает с активной локацией текущей роли.
- Очереди инцидентов выбирают `exception` отправления только для точной локации-получателя.
- Workflow приёмки дополнительно проверяет роль/локацию получателя, состояние всех коробок и карт, совпадение фактического состава коробок с манифестом. Разрешение инцидента требует непустого результата проверки и проходит через тот же полный receive workflow.
- Регистрация инцидента разрешена только активному сотруднику одной из двух участвующих локаций (отправитель или получатель), причина обязательна; сама регистрация не меняет местонахождение груза.

### Реестр и карточка отправления

- `GET /shipments` и `GET /shipments/{shipment_id}` доступны только branch/central_office/archive.
- Область видимости — отправления, где активная локация пользователя является отправителем **или** получателем. Карточка дополнительно ограничивает выборку тем же условием; чужой объект возвращает 404.
- Карточка показывает манифест, ФИО/номера карт, курьера и телефон курьера, направления, статус и хронологию событий с именами исполнителей и payload событий.
- Список ограничен последними 200 отправлениями; доступен фильтр статуса.

### Подтверждение тестами и оставшиеся ограничения

- `test_postgresql_transfer_integration.py` подтверждает доступ branch и archive к отправлению branch → archive, отсутствие такого отправления в списке ЦО, 404 для ЦО при прямом открытии чужой карточки и 403 для viewer.
- `test_postgresql_incident_pages.py` подтверждает административный просмотр манифеста/ФИО, запрет viewer, запрет постороннего филиала на разрешение инцидента и то, что пустое пояснение не меняет статус инцидента.
- `test_postgresql_interface_role_matrix.py` покрывает GET-матрицу HTML-страниц и QR-этикетки, но не является исчерпывающей матрицей всех POST действий.
- Проверенные тесты не дают полной комбинационной проверки каждой пары ролей/локаций, каждого POST и каждой разновидности объекта. Это ограничение тестового покрытия, а не доказательство отсутствия серверных проверок.

**Не утверждено:** расширение прав admin/viewer, частичная приёмка, изменение маршрутов или состава отправления.


## 8. Операции с картами и коробками: серверные ограничения

Дополнительно проверены `postgresql_packing.py`, архивные POST handlers и методы `PostgreSQLShipmentWorkflow` для создания коробки, изменения состава и списания.

- Филиальная упаковка: `POST /packing/new-box`, `/packing/scan-card`, `/packing/confirm-card`, `/packing/remove-card`, `/packing/write-off-box`; все endpoints защищены `branch_only`.
- Архивные операции: `POST /placement/new-internal-box`, `/placement/add-card`, `/placement/remove-card-from-box`, `/placement/box`, `/placement/card`, `/placement/remove-box`, `/placement/write-off-box`, `/placement/remove-card`; endpoints защищены `archive_only`.
- ЦО: `POST /central/packing/new-box`, `/central/packing/add-card`, `/central/packing/remove-card`, `/central/packing/write-off-box`; endpoints защищены `central_only`.
- Workflow дополнительно проверяет активного пользователя, роль и доступ к конкретной локации; для филиала проверяет совпадение `branch_id`. Подмена UUID чужой коробки/карты не должна обходить эти проверки.
- Создание коробки допускает необязательный начальный состав; пустые коробки могут существовать, но их отправка запрещена отдельными правилами handover.
- Добавление/извлечение карт сохраняет историю членства через циклы коробки. Нельзя менять состав коробки, размещённой на полке или включённой в активное отправление; карта не должна быть в другой коробке, на полке, в пути или во внешнем хранении.
- Списание разрешено только для пустой активной стационарной коробки, не размещённой на полке и не зарезервированной активным отправлением; событие списания сохраняется.

Подробные инварианты, тестовые подтверждения и пробелы вынесены в `UX-01-card-box-operations-audit.md`.

**Ограничение тестов:** найденные packing/archive integration tests покрывают отдельные сквозные сценарии, но не полную комбинацию POST × пять ролей × чужая локация/объект. Не считать это доказательством отсутствия сервисных guards.
