# UX-02 — endpoint-level ACL и ownership audit

Дата: 2026-11-17  
Проверенный HEAD до документирования: `d3e3615bfd19fcfd93e09861e3d18192416b8023`  
Ветка: `docs/ux-audit-project`

## 1. Цель и метод

Проверены изменяющие PostgreSQL HTTP handlers и вызываемые сервисные методы. Для каждой группы действий сопоставлены:
1. роль на уровне FastAPI dependency;
2. повторная авторизация в service/workflow;
3. проверка принадлежности объекта локации пользователя;
4. проверка состояния объекта и блокирующих связей;
5. найденное тестовое подтверждение.

Это статический аудит исходников и тестов. Тесты и CI в этом проходе не запускались. Отсутствие отдельного теста в просмотренной выборке не доказывает отсутствие любой косвенной проверки в другом тестовом модуле.

## 2. Выводы по модели авторизации

### 2.1 Два уровня контроля

Операционные PostgreSQL handlers используют role dependencies:
- `branch_only` — филиальные операции;
- `central_only` — операции ЦО;
- `archive_only` — архивные операции;
- `admin_only` — административные операции.

Для критичных операций над картами, коробками и отправлениями сервисы повторно загружают активного пользователя и проверяют соответствующую локацию. `PostgreSQLShipmentWorkflow._authorize_location` сверяет тип роли с типом локации, а для branch дополнительно сравнивает `user.branch_id` и `location.branch_id`. `_location` блокирует строку локации и отклоняет неактивную локацию.

Это сильнее, чем полагаться только на скрытие кнопки или URL guard. Но полное покрытие всех endpoint и всех объектов не доказано одной общей матрицей тестов.

## 3. Существенные проверки сервисного слоя

### 3.1 Упаковка и коробки

`add_card_to_box`:
- блокирует коробку и карту;
- требует активную коробку в постоянной локации;
- авторизует actor на локацию коробки;
- запрещает размещённую коробку и коробку в активном манифесте;
- требует активную карту в той же локации и доступный custody status;
- запрещает карту в другой активной коробке, на полке или в активном манифесте;
- добавляет карту в открытый цикл либо создаёт следующий цикл.

`remove_card_from_box` повторно проверяет actor/location, placement, shipment, открытый цикл и фактическое членство. История членства не удаляется: membership закрывается timestamp/actor.

`write_off_box` требует активную коробку, постоянную локацию, авторизованного actor, отсутствие активного манифеста, пустой состав и отсутствие активного размещения.

### 3.2 Передача

`create_draft`:
- проверяет активного actor, активность/существование обеих локаций;
- запрещает одинаковые source и target;
- ограничивает маршрут пятью разрешёнными парами;
- авторизует source location;
- блокирует и проверяет активного курьера.

`hand_over` повторно авторизует source и блокирует shipment/коробки/карты. Проверяет непустой состав, актуальное местонахождение, активные циклы коробок, состав и отсутствие placement. Для архива → ЦО запрещает коробки и связывает каждую карту с активной заявкой ЦО в той же транзакции. После валидации записывает манифест и меняет pointers объектов и статус shipment на `in_transit`.

### 3.3 Приёмка

Общий `_receive`:
- блокирует shipment;
- проверяет ожидаемый статус (`in_transit` либо `exception`);
- авторизует actor на target location;
- проверяет, что отправление непустое;
- сверяет pointers коробок и карт с shipment;
- восстанавливает фактический состав каждого отправляемого цикла;
- проверяет соответствие манифеста содержимому коробок и отсутствие ошибочной отдельной позиции карты из коробки;
- только после проверок меняет location pointers и ставит `received`.

Частичная приёмка не реализована в просмотренном workflow: весь shipment принимается одним действием.

### 3.4 Инциденты

`register_exception` требует активного пользователя, shipment в статусе `in_transit`, непустую причину до 2000 символов. Отправить инцидент может actor соответствующей роли в source либо target location; для branch дополнительно сверяется branch_id. Регистрация инцидента не меняет location pointers груза.

`resolve_exception` требует заметку и делегирует полную приёмку с ожидаемым статусом `exception`. Это не отдельный частичный процесс восстановления.

## 4. Административные инварианты

В `PostgreSQLAdminService` подтверждены:
- Деактивация филиала блокируется при активных пользователях, картах/активных коробках на балансе или незавершённых отправлениях.
- Для сериализации деактивации филиала блокируется logistics Location; workflows используют ту же строку локации как точку сериализации.
- Деактивация курьера блокируется при shipment в `draft`, `in_transit` или `exception`.
- Деактивация полки блокируется при активных placements коробок или карт.
- Для изменений пользователей применяется PostgreSQL advisory transaction lock; роль branch требует branch_id, остальные роли branch_id не имеют.
- Нельзя отключить/понизить последнего активного администратора.
- Admin HTML и API вызывают общий service layer.

Тесты покрывают перечисленные инварианты отдельными интеграционными сценариями. Это не формальная проверка всех конкурентных расписаний и не доказательство отсутствия гонок вне исследованных сценариев.

## 5. Отмена отправления — отдельный результат

Проверены:
- все методы `PostgreSQLShipmentWorkflow` по объявлениям и упоминаниям `cancel`/`cancelled`;
- пользовательский router `postgresql_shipments.py`;
- изменяющие handlers transfer/branch/central/archive;
- административные routers.

Результат:
- статус `cancelled` присутствует в отображении статусов реестра;
- в проверенном `PostgreSQLShipmentWorkflow` нет метода отмены;
- в проверенных PostgreSQL routers нет пользовательского POST handler отмены;
- в просмотренной выборке тестов нет теста пользовательской отмены.

Следовательно, `cancelled` — значение модели/представления, но работающий пользовательский процесс отмены не подтверждён. Нельзя предполагать, что draft можно отменить без отдельного правила о судьбе манифеста, блокировок объектов и аудита. Нельзя также считать отмену невозможной на уровне всей системы без отдельной проверки прямых DB/admin инструментов.

| ID | Наблюдение | Значимость | Статус |
|---|---|---|---|
| ACL-01 | Нет единой тестовой матрицы всех изменяющих endpoints × пять ролей × собственный/чужой объект × состояния | Высокая | Подтверждён пробел тестового доказательства |

## 7. Предлагаемый следующий шаг аудита

Не менять приложение. Составить исполняемую тестовую матрицу (как аудиторский артефакт, не как новые тесты приложения):
- endpoint и HTTP method;
- dependency/role;
- service method;
- actor active/inactive;
- source/target ownership;
- own vs foreign card/box/shipment/request/shelf;
- object status;
- expected allow/deny;
- существующий тест и недостающее покрытие.

После инвентаризации согласовать с владельцем продукта допустимые роли и процессы. Только затем отдельно решать, какие недостающие тесты и изменения кода нужны.

## 8. Ограничения

Проверялись исходники и тесты в рабочей ветке на указанном HEAD. Тесты/CI не запускались. Ручная проверка UI не выполнялась. В ходе этапа не менялись исходники приложения, тесты, миграции, workflow, конфигурация SQLite и базовая ветка. Документ не утверждает, что бизнес-процессы согласованы.
