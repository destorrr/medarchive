## 1. Назначение и метод

Документ фиксирует не наличие тестового файла вообще, а конкретные доказанные сценарии: успешную операцию, отказ по роли, отказ по чужому объекту, отказ по состоянию или защиту целостности. Это статический анализ исходников тестов на указанном HEAD. Тесты в рамках прохода не запускались; результат не является подтверждением текущего CI.

Уровни доказательности:

- **Покрыто** — найден конкретный тест с проверкой результата или отказа для указанного сценария.
- **Частично** — есть близкий/сквозной тест, но не проверена вся комбинация условий.
- **Не подтверждено** — в просмотренной выборке конкретного теста не найдено. Это не доказательство отсутствия теста во всём репозитории.
- **Не реализовано в просмотренном пути** — соответствующий пользовательский handler/service path не обнаружен; требуется отдельное продуктовое решение, если функция нужна.

## 4. Что подтверждено особенно хорошо

1. **Сквозная логистика.** Есть один длинный HTTP integration test, проходящий через все три операционные роли и несколько разрешённых направлений движения.
2. **Полная приёмка и инциденты.** Проверены wrong recipient, пустое пояснение, immutable manifest, несогласованное состояние одной карты, успешное разрешение и защита от повторного resolve.
3. **Внешнее хранение.** Проверен полный цикл, отказ трёх других ролей и запрет обычных операций до возврата.
4. **Администрирование.** Существенный набор конкретных инвариантов и конкурентный сценарий последнего активного администратора/деактивации филиала.
5. **Архив.** Проверены inactive shelf, duplicate placement и требование снять карту с полки до отправки.
6. **Область отправлений.** Проверены ролевой запрет и сокрытие чужой карточки отправления через 404.

## 6. Отмена отправления: отдельный результат

В проверенных ранее PostgreSQL routers и workflow статус `cancelled` присутствует в модели/представлении, но пользовательский handler и метод отмены не обнаружены. В проверенных тестовых модулях также не найден тест пользовательской отмены.

Это не следует автоматически трактовать как дефект: сначала владелец продукта должен определить, допустима ли отмена, на каких стадиях, кем, с какими последствиями для карт/коробок/курьера и аудита. До такого решения статус `cancelled` остаётся неподтверждённой частью пользовательского процесса.

## 7. Рекомендуемый следующий шаг

Не добавлять тесты вслепую и не менять код. Сначала завершить endpoint inventory: извлечь полный список POST/PUT/PATCH/DELETE из PostgreSQL routers, связать каждый путь с guard/service method, а затем сопоставить его с конкретными тестовыми функциями. Результатом должна стать таблица отсутствующих проверок с приоритетом по риску: object ownership, неправильный адресат, inactive object, повторная операция, конкурентное изменение, необратимое списание.

После согласования продуктовых правил отдельным решением утвердить тестовую матрицу и только затем добавлять недостающие тесты.
