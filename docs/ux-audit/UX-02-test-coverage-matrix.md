# UX-02 — матрица тестового покрытия изменяющих PostgreSQL endpoints

Дата проверки: 2026-11-17  
Проверенная ветка: `docs/ux-audit-project`  
Проверенный HEAD исходников и тестов: `a3526ed9c9823a58b1436851e2e9db6fa2e8d97e`

## 1. Назначение и метод

Документ фиксирует, что именно доказывают существующие PostgreSQL-тесты для изменяющих HTTP-операций. Это статический аудит исходников тестов, а не отчёт о запуске тестового набора.

Для каждого семейства проверялись:
- HTTP method/path, вызываемые тестом;
- роль пользователя, от имени которой выполняется запрос;
- позитивный сценарий и проверяемое изменение состояния;
- негативный сценарий: роль, принадлежность объекта, состояние объекта или повтор операции;
- границы доказательства.

Термины:
- **Есть позитивный тест** — тест вызывает endpoint под предназначенной ролью и проверяет ожидаемый результат.
- **Есть негативный тест** — тест проверяет конкретный отказ (403/404/валидационная ошибка/исключение/неизменность БД).
- **Частично** — покрыта отдельная комбинация, но не полная матрица.
- **Не доказано** — в просмотренной выборке прямого теста на комбинацию не найдено. Это не утверждение, что такого теста нет во всём репозитории.

## 2. Сводная оценка

| Контур | Позитивный путь | Негативный путь | Основной остаточный пробел |
|---|---|---|---|
| Branch: QR intake и упаковка | Есть | Есть для неизвестной/повторной карты, чужой QR label | Нет полной матрицы ролей и чужих карт/коробок для каждого POST |
| Branch: передача курьеру | Есть в сквозном цикле | Ролевые GET-отказы есть | Transfer integration преимущественно проверяет GET; POST denial × роли/ownership не систематизирован |
| Branch: приёмка | Есть в incident/full-cycle сценариях | Есть отказ неправильному получателю в incident test | Не найдена полная матрица по всем типам отправлений и объектным состояниям |
| Central Office: приёмка/упаковка/отправка | Есть в сквозном цикле и custody | Есть ограничения custody; отдельные недоступные объекты | Нет полной отрицательной матрицы центральных POST endpoints |
| Central Office: заявки в архив | Есть | Есть дубли активных заявок/неподходящие карты на уровне workflow | Ролевые и foreign-object комбинации покрыты частично |
| Archive: размещение/снятие | Есть | Есть неактивная полка, повторное размещение, попытка движения без снятия | Не доказаны все чужие shelf/card/box комбинации через HTTP |
| Archive: заявки/исполнение | Есть | Есть повторная заявка, обязательное пояснение «не найдена», неподходящие карты | Неполная POST role/ownership matrix |
| Admin: HTML/API mutations | Есть | Сильное покрытие отказа четырём не-admin ролям | Позитивный/негативный набор не полностью cross-product по каждому endpoint и объекту |
| External custody | Есть | Есть чужие роли, повторные действия, блокировка обычного движения | Не подтверждена исчерпывающая матрица всех object states и race conditions |
| Incidents | Есть | Неправильный получатель, пустое решение, повторное разрешение | Нет полной матрицы ролей/отправителя/получателя/состояний |
| Viewer/read-only | GET role matrix | Операционные страницы запрещены по GET | Не всякое запрещённое POST действие напрямую проверено viewer-тестом |

**Общий вывод:** тесты содержат существенные позитивные сквозные сценарии и отдельные сильные негативные проверки. Они не образуют полную матрицу `изменяющий endpoint × 5 ролей × своя/чужая локация × состояние объекта`. По этой причине нельзя формулировать общий вывод «все операции безопасны» только на основании текущего набора тестов.

## 4. Что тесты подтверждают на уровне БД и сервисов

В `tests/adapters/test_postgresql_shipment_workflow.py` проверены, среди прочего:
- атомарная передача коробки/карты в shipment и приёмка с восстановлением location;
- archive → ЦО только по заявке и только отдельными картами;
- запрет admin выполнять обычную логистику;
- блокировка изменения состава и маршрута после handover на уровне БД;
- запрет движения размещённой коробки/карты без снятия с полки;
- отметка not-found только с пояснением;
- внешнее хранение ЦО блокирует внутреннее движение.

Это важные доменные/DB проверки, но они не заменяют HTTP role matrix: тест сервиса не доказывает, что каждый HTTP handler корректно подключил guard и передал правильный actor/object.

## 6. Условия запуска и ограничения достоверности

Просмотренные PostgreSQL integration tests используют `MEDARCHIVE_DATABASE_URL` и явно делают `pytest.skip`, если переменная не задана. Поэтому наличие теста в репозитории не гарантирует, что он выполнялся в конкретном запуске. В этом проходе GitHub workflow и CI runs не запускались и не инспектировались.

Все выводы ограничены кодом тестов на HEAD `a3526ed9c9823a58b1436851e2e9db6fa2e8d97e`. В частности:
- не заявляется полная безопасность приложения;
- не заявляется 100% покрытие endpoint-ов;
- не заявляется, что все негативные комбинации отсутствуют во всём наборе;
- не делается вывод о корректности бизнес-регламента;
- тесты не менялись и не запускались.

## 7. Следующий шаг

Следующий проход — построить машинно-сверяемый inventory всех изменяющих маршрутов из PostgreSQL routers и привязать к каждому существующий тестовый вызов. Для оставшихся пустых ячеек сформировать точечный список недостающих тестов по трём независимым осям: роль, ownership, состояние объекта. До согласования процессов новые тесты и продуктовый код не добавлять.
