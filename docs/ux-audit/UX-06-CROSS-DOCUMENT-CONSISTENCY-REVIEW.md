## 3. Исправленный конфликт BoxPlacement

Техническая модель ранее содержала безусловный инвариант «активное BoxPlacement только для непустой коробки». Он прямо противоречил D-11/P-03, DB-12 и соседнему описанию regroup, по которым пустая коробка после перегруппировки остаётся на полке до решения пользователя. Исправлены §4.2 и инвариант 4: разрешено только это контекстное исключение; после extraction последней карты по заявке placement обязательно закрывается. Общий trigger автоматического снятия пустых коробок не допускается.

## 4. Уточнения, которые следует внести до реализации

1. **not_found comment policy — закрыто 2026-11-18.** Владелец продукта выбрал вариант Б: комментарий/обоснование необязателен; обязательны финальный результат, actor и timestamp. Контракты, техническая модель и DB-15 обновлены.
2. **Удаление позиции ЦО.** В технической схеме можно хранить audit tombstone, но текущая выборка/манифест заявки должны исключать такую позицию. История изменения состава — отдельный audit/event projection.
3. **Audit ownership.** Зафиксировать для каждого класса событий, что является authoritative записью: DomainEvent или отдельный admin/security audit. Не создавать дублирующие источники истины.
4. **Command ledger.** До проектирования SQL API выбрать уникальность command_id, input hash, хранение typed result, retention и поведение при повторе после успешного commit.
5. **Box/BoxCycle.** Связь подтверждена текущей ORM и integration test; до DDL проверить сохранение Box UUID, unique box_number и нумерации циклов. Новое бизнес-решение по связи не требуется.

Пункт 1 закрыт решением владельца продукта; пункт 3 остаётся открытым. Пункты 2, 4 и 5 могут быть закрыты техническим проектированием с последующей проверкой владельцем продукта там, где меняется пользовательское поведение.

## 7. Решение владельца продукта по `not_found` (2026-11-18)

Владелец продукта выбрал вариант Б: комментарий/обоснование при фиксации `not_found` не обязателен. Обязательны только результат «не найдена», пользователь (`actor`) и время события (`timestamp`). Необязательный комментарий допускается сохранить, если он предоставлен. Это не затрагивает обязательный комментарий при первой фиксации `removed_by_archive` и обязательную причину отмены заявки; при повторной фиксации `removed_by_archive` после исправления новый комментарий необязателен. Соответствующие command contract, technical data model и DB-15 обновлены; продуктовый вопрос закрыт.

## 10. Сверка неизменяемости состава P-09 (2026-11-20)

Ранее найденные формулировки в P-09, технической модели и DB command contracts допускали изменение состава после отправки заявки. Они противоречат принятому владельцем продукта правилу от 2026-11-20 и заменены. Автор ЦО редактирует только draft; отправка фиксирует неизменяемый набор карт. После отправки архив может менять только результат обработки каждой существующей позиции (например, `not_found`, `removed_by_archive`), но не состав/идентичность позиций. Отмена draft автором не требует причины; отмена submitted/processing архивом требует причины.

## 11. Рабочая очередь архива и отменённые P-09 (2026-11-20)

Согласовано владельцем продукта: отменённая после отправки P-09 исключается из текущей рабочей очереди архива, поскольку дальнейшие операционные действия по ней не требуются. Запись, причина отмены, actor/time и история сохраняются для аудита и последующего просмотра уполномоченными сотрудниками. Черновики ЦО не входят в очередь архива; завершённые заявки также не являются рабочими.


## 12. Завершённые P-09 не входят в рабочую очередь архива (2026-11-20)

Согласовано владельцем продукта: после перехода в `completed` P-09 исключается из рабочей очереди архива, поскольку операционные действия завершены. Запись заявки, состав, результаты обработки, сведения о fulfillment-отправлении и история событий сохраняются для исторического просмотра уполномоченными сотрудниками. Таким образом, рабочая очередь P-09 содержит только отправленные заявки, по которым архиву ещё требуется выполнить действия; отменённые и завершённые заявки в неё не входят.


## 13. Рабочая очередь P-09 и счётчик новых заявок архива (2026-11-20)

Владелец продукта согласовал, что рабочая очередь P-09 архива включает заявки в обоих родительских состояниях `submitted` и `processing`, пока заявка не завершена и не отменена. Переход `submitted → processing` убирает заявку только из общего счётчика новых заявок на навигации, но не из рабочей очереди. Заявка остаётся в рабочей очереди и после создания fulfillment-отправления, пока не перейдёт в `completed` или `cancelled`; отдельная очередь исходящих отправлений отслеживает физическую перевозку и не заменяет очередь P-09. `completed` и `cancelled` исключаются из рабочей очереди и доступны в истории.

Счётчик новых заявок остаётся общим для активных сотрудников архива с доступом к очереди и считает только `submitted`. Это отдельная метрика ожидания начала обработки, а не количество всех открытых P-09.


## 14. Сверка дашбордов с текущим scope маршрутов (2026-11-20)

Проверены UX-04 и UX-05 относительно действующего scope UX-06. UX-04 уже отражает согласованные направления: филиал — только отправитель по маршруту филиал → архив; ЦО — отправитель по ЦО → архив и получатель по архив → ЦО; архив — получатель по филиал/ЦО → архив и отправитель по архив → ЦО. В UX-05 обнаружены устаревшие формулировки, включавшие отложенные маршруты филиал → ЦО и ЦО → филиал, а также входящую приёмку филиалом. Они исправлены в целях дашбордов, приоритетных блоках и формулах очередей. Текущий scope не расширен.

| Роль | Входящие в текущем scope | Исходящие в текущем scope |
|---|---|---|
| Филиал | Нет | Филиал → архив (коробки) |
| ЦО | Архив → ЦО (отдельные карты по P-09) | ЦО → архив (коробки) |
| Архив | Филиал → архив и ЦО → архив (коробки) | Архив → ЦО (отдельные карты по P-09) |

Маршруты филиал → ЦО и ЦО → филиал остаются будущим расширением и не проектируются в текущем UX. Формулы счётчиков должны ограничиваться указанными парными локациями отправителя/получателя, а не только from_location_id или to_location_id, чтобы исключить посторонние или отложенные направления.

## 16. Разделение создания fulfillment-черновика и фактической передачи (2026-11-20)

При повторной сверке обнаружено, что §2.8 DB command contracts ошибочно объединял создание fulfillment-отправления и фактическую передачу в одну команду `request_handover`. Это противоречило уже согласованному двухэтапному процессу и §§5.4–5.5 технической модели. Исправлено:

- `request_create_fulfillment_draft` создаёт единственный shipment в `draft`, полный неизменяемый manifest и snapshot истории, а также устанавливает `ArchiveRequest.fulfillment_shipment_id` атомарно. Карты остаются в ответственности архива; `current_shipment_id` не устанавливается, item остаётся `extracted`.
- `shipment_confirm_handover` — отдельная команда, доступная только автору черновика, если он активен и имеет необходимые полномочия. Она атомарно переводит shipment в `in_transit`, карты — в shipment custody, позиции — в `in_shipment`, фиксирует actor/time без повторного snapshot.
- Отмена до фактической передачи остаётся атомарной с отменой parent P-09 и возвратом извлечённых карт; после фактической передачи отмена запрещена.
- Если передавать нечего, shipment не создаётся; P-09 завершается после окончательных результатов всех позиций.

Техническая модель уже содержала корректное разделение; синхронизированы DB command contracts, инварианты и эта cross-document review. Реализация не выполнялась.

Синхронизировать это правило с ранее согласованным контрактом обычных отправлений, не смешивая историю курьерских назначений с историей бизнес-событий handover.

## 2026-11-20 — резервирование карты до завершения P-09

Владелец продукта согласовал, что возврат карты в коробку с результатом `removed_by_archive` не освобождает её для новой заявки, пока исходная P-09 остаётся `processing`. ## 2026-11-20 — сквозная сверка пользовательских маршрутов branch и P-09

При сопоставлении UX-04 с активным route allowlist и двухэтапным fulfillment найдены ещё два устаревших описания пользовательского потока:

1. В маршруте филиала предлагалось выбрать получателя «ЦО или архив», хотя филиал в текущем scope отправляет только в архив. Маршруты филиал → ЦО и ЦО → филиал отложены.
2. Поток обработки P-09 описывал включение карт в отправление и передачу одной последовательностью, не показывая отдельное создание fulfillment-черновика и последующее подтверждение фактической передачи. Это могло создать впечатление одной операции.

UX-04 исправлен: филиал создаёт черновик только по маршруту филиал → архив, редактирует коробки/курьера и отдельно подтверждает фактическую передачу. Для P-09 явно показаны создание единственного fulfillment-черновика с обязательным курьером и отдельная передача только автором активного черновика; если карт к передаче не осталось, отправление не создаётся, P-09 завершается completed.

Исправления следуют из уже согласованных D-01/D-18/P-09 и не требуют нового продуктового решения. Изменена только Markdown-документация; исходники, ORM, SQL/DDL, миграции и тесты не менялись. PostgreSQL, pytest и CI не запускались.

## 2026-11-20 — область PII в манифесте по типу отправления

Проверка доступа к манифестам выявила слишком широкую формулировку в общем разделе UX-06 object detail: она могла читаться так, будто любой манифест отправления содержит номера карт и ФИО пациентов. Это не соответствует разделению D-01 и технической модели: обычные маршруты branch/CO → archive перевозят коробки (`ShipmentBox`), а fulfillment P-09 archive → CO — отдельные карты (`ShipmentCard`). Уточнён общий контракт: участники видят полный манифест своего отправления, но состав полей зависит от типа; обычный манифест содержит только коробки, P-09 fulfillment — отдельные карты с номером и ФИО. Участие в обычной доставке не открывает независимую карточку или историю карты; для них действует отдельная авторизация. В карточке обычной доставки архив не видит содержимое коробок.

Это уточнение согласованных типов манифеста и уже принятого ограничения видимости, не новое продуктовое решение. Исходники, ORM, SQL/DDL, миграции и тесты не менялись; PostgreSQL, pytest и CI не запускались.
