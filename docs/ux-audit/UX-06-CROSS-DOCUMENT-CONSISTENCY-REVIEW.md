## 3. Уточнённый контракт BoxPlacement

Активный `BoxPlacement` допустим как для заполненной, так и для пустой коробки. При перегруппировке из размещённой коробки можно извлечь все карты: последний membership закрывает `BoxCycle`, но не `BoxPlacement` (DB-61). Пустая коробка может быть повторно заполнена через `box_add_card` без снятия с полки (DB-57) либо снята отдельной командой `box_unplace` (DB-58). При P-09 extraction последней карты placement закрывается автоматически (DB-11). Следовательно, общий trigger «активное размещение только для непустой коробки» недопустим; контекстные команды явно реализуют разные переходы, а прямой произвольный DML закрыт DB guard.

## 4. Уточнения, которые следует внести до реализации

1. **not_found comment policy — закрыто 2026-11-18.** Владелец продукта выбрал вариант Б: комментарий/обоснование необязателен; обязательны финальный результат, actor и timestamp. Контракты, техническая модель и DB-15 обновлены.
2. **Удаление позиции ЦО.** В технической схеме можно хранить audit tombstone, но текущая выборка/манифест заявки должны исключать такую позицию. История изменения состава — отдельный audit/event projection.
3. **Audit ownership.** Зафиксировать для каждого класса событий, что является authoritative записью: DomainEvent или отдельный admin/security audit. Не создавать дублирующие источники истины.
4. **Command ledger.** До проектирования SQL API выбрать уникальность command_id, input hash, хранение typed result, retention и поведение при повторе после успешного commit.
5. **Box/BoxCycle.** Связь подтверждена текущей ORM и integration test; до DDL проверить сохранение Box UUID, unique box_number и нумерации циклов. Новое бизнес-решение по связи не требуется.

## 7. Решение владельца продукта по `not_found` (2026-11-18)

Соответствующие command contract, technical data model и DB-15 обновлены; продуктовый вопрос закрыт.

## 10. Сверка неизменяемости состава P-09 (2026-11-20)

Ранее найденные формулировки в P-09, технической модели и DB command contracts допускали изменение состава после отправки заявки. Они противоречат принятому владельцем продукта правилу от 2026-11-20 и заменены. Автор ЦО редактирует только draft; отправка фиксирует неизменяемый набор карт. После отправки архив может менять только результат обработки каждой существующей позиции (например, `not_found`, `removed_by_archive`), но не состав/идентичность позиций. Отмена draft автором не требует причины; отмена submitted/processing архивом требует причины.

## 11. Рабочая очередь архива и отменённые P-09 (2026-11-20)

Согласовано владельцем продукта: отменённая после отправки P-09 исключается из текущей рабочей очереди архива, поскольку дальнейшие операционные действия по ней не требуются. Запись, причина отмены, actor/time и история сохраняются для аудита и последующего просмотра уполномоченными сотрудниками. Черновики ЦО не входят в очередь архива; завершённые заявки также не являются рабочими.


## 12. Завершённые P-09 не входят в рабочую очередь архива (2026-11-20)

Согласовано владельцем продукта: после перехода в `completed` P-09 исключается из рабочей очереди архива, поскольку операционные действия завершены. Запись заявки, состав, результаты обработки, сведения о fulfillment-отправлении и история событий сохраняются для исторического просмотра уполномоченными сотрудниками. Таким образом, рабочая очередь P-09 содержит только отправленные заявки, по которым архиву ещё требуется выполнить действия; отменённые и завершённые заявки в неё не входят.


## 13. Рабочая очередь P-09 и счётчик новых заявок архива (2026-11-20)

Владелец продукта согласовал, что рабочая очередь P-09 архива включает заявки в обоих родительских состояниях `submitted` и `processing`, пока заявка не завершена и не отменена. Переход `submitted → processing` убирает заявку только из общего счётчика новых заявок на навигации, но не из рабочей очереди. Заявка остаётся в рабочей очереди и после создания fulfillment-отправления, пока не перейдёт в `completed` или `cancelled`; отдельная очередь исходящих отправлений отслеживает физическую перевозку и не заменяет очередь P-09. `completed` и `cancelled` исключаются из рабочей очереди и доступны в истории.

Счётчик новых заявок остаётся общим для активных сотрудников архива с доступом к очереди и считает только `submitted`. Это отдельная метрика ожидания начала обработки, а не количество всех открытых P-09.

## 16. Разделение создания fulfillment-черновика и фактической передачи (2026-11-20)

При повторной сверке обнаружено, что §2.8 DB command contracts ошибочно объединял создание fulfillment-отправления и фактическую передачу в одну команду `request_handover`. Это противоречило уже согласованному двухэтапному процессу и §§5.4–5.5 технической модели. Исправлено:

- `request_create_fulfillment_draft` создаёт единственный shipment в `draft`, полный неизменяемый manifest и snapshot истории, а также устанавливает `ArchiveRequest.fulfillment_shipment_id` атомарно. Карты остаются в ответственности архива; `current_shipment_id` не устанавливается, item остаётся `extracted`.
- `shipment_confirm_handover` — отдельная команда, доступная только автору черновика, если он активен и имеет необходимые полномочия. Она атомарно переводит shipment в `in_transit`, карты — в shipment custody, позиции — в `in_shipment`, фиксирует actor/time без повторного snapshot.
- Отмена до фактической передачи остаётся атомарной с отменой parent P-09 и возвратом извлечённых карт; после фактической передачи отмена запрещена.
- Если передавать нечего, shipment не создаётся; P-09 завершается после окончательных результатов всех позиций.

Техническая модель уже содержала корректное разделение; синхронизированы DB command contracts, инварианты и эта cross-document review. Реализация не выполнялась.

This cap applies only to best-effort denial telemetry and cannot affect business operations or authorization outcomes. It coexists with the 15-minute window, five-denial threshold, operation/reason grouping and prohibition on per-user/network correlation. Concurrency-safe enforcement remains an implementation detail.


## 2026-11-21 — denial telemetry retention approved

Bounded aggregate authorization-denial telemetry is retained for 30 calendar days and then automatically deleted. This rule applies only to this best-effort telemetry stream; it does not change AdminSecurityAudit, DomainEvent or authoritative business-record retention. Cleanup is bounded and non-blocking. Together with prior approvals: 15-minute aggregation window, threshold of five matching denials, and application-wide cap of 100 aggregate events per hour.


## 2026-11-21 — denial telemetry unavailable-store behavior approved

Optional denial telemetry uses drop-on-failure semantics: no retry and no deferred queue when its store is unavailable or a write fails. The request and its authorization/business-operation result are unaffected; internal technical details are not exposed. This is strictly separate from mandatory DomainEvent/AdminSecurityAudit writes, which retain their approved atomic fail-closed behavior.


## 2026-11-21 — telemetry-loss monitoring approved

No separate user-interface notification is created for dropped/unavailable optional denial telemetry. Operational monitoring tracks telemetry-store availability and write failures using technical health signals only, without personal data. It is separate from AdminSecurityAudit and cannot become a request-path dependency or block/change authorization or business-operation outcomes. No retry or deferred queue is introduced. Implementation remains unauthorized.

## 2026-11-21 — operational telemetry monitoring access approved

Technical monitoring metrics and telemetry-store/write-failure diagnostics are restricted to infrastructure administrators and personnel explicitly responsible for system operations. Ordinary MedArchive users, including application-role `admin`, must not see internal infrastructure metrics or telemetry diagnostics through the application. This is a separate infrastructure/operations access boundary, not an application permission or AdminSecurityAudit feature. Exact identities/grants remain deployment-specific; implementation remains unauthorized.

## 2026-11-21 — technical monitoring access-view audit boundary approved

Viewing technical monitoring metrics is excluded from MedArchive `AdminSecurityAudit`. Access is controlled through infrastructure mechanisms; if required, monitoring-view access is recorded only in a separate infrastructure/operations log outside MedArchive business/security audit. This neither expands application audit events nor changes who may access monitoring. Implementation remains unauthorized.

## 2026-11-21 — no telemetry-outage notifications approved

No separate notifications or alerts are generated for denial-telemetry store unavailability, even when prolonged. Passive health metrics/diagnostics remain available to authorized infrastructure personnel under the existing access boundary, but no alerting workflow is introduced. Existing drop-on-failure and non-blocking semantics remain unchanged.

## 2026-11-21 — telemetry health UI exposure prohibited

Denial-telemetry storage availability, health, write failures, and diagnostics are not exposed in the MedArchive application UI, including to application administrators. Any passive technical health information remains outside the application UI and under the separate infrastructure/operations access boundary. The application `admin` role does not grant monitoring access.

## 2026-11-21 — separate audit-integrity verification feature excluded

A separate cryptographic integrity-verification feature for `AdminSecurityAudit` is not required. Hash chains, MACs, signatures, checkpoints, scheduled verification, integrity dashboards, and related UI/API are out of scope. This does not remove existing requirements for append-only behavior, restricted writes, atomic mandatory audit writes, retention governance, or backup/restore reconciliation. Key management remains deferred and is not an implementation prerequisite for an excluded feature.

## 2026-11-21 — failed login attempts excluded from persisted events

Do not persist individual failed-login attempts or login-throttle denials as `AdminSecurityAudit`, `DomainEvent`, or bounded security-telemetry events. Remove `authn.login_failed` and `authn.login_throttled` from the target event catalog. Preserve the login-throttle mechanism and its separately controlled internal counters/state only as needed to enforce rate limits; do not treat or expose those counters as audit events. Successful-login auditing and selected high-risk authorization-denial telemetry are unaffected.

## 2026-11-21 — normal session-expiration events excluded

Do not persist normal session expiration (timeout/ordinary expiry) as `AdminSecurityAudit`, `DomainEvent`, or bounded security telemetry. Do not add a session-expiration event or session registry solely to record it. Successful-login auditing and best-effort explicit logout telemetry remain unchanged.

## 2026-11-21 — administrative session termination

Record account deactivation/administrative disabling through its existing mandatory `AdminSecurityAudit` action. Do not emit a separate event for each session invalidated or terminated as a consequence. This is not a change to successful-login auditing, explicit logout telemetry, or the exclusion of ordinary session-expiration events.

## 2026-11-21 — завершение активных сессий при смене/сбросе пароля
