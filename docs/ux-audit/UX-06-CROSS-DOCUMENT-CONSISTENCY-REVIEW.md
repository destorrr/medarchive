## 3. Уточнённый контракт BoxPlacement

Активный `BoxPlacement` допустим как для заполненной, так и для пустой коробки. При перегруппировке из размещённой коробки можно извлечь все карты: последний membership закрывает `BoxCycle`, но не `BoxPlacement` (DB-61). Пустая коробка может быть повторно заполнена через `box_add_card` без снятия с полки (DB-57) либо снята отдельной командой `box_unplace` (DB-58). При P-09 extraction последней карты placement закрывается автоматически (DB-11). Следовательно, общий trigger «активное размещение только для непустой коробки» недопустим; контекстные команды явно реализуют разные переходы, а прямой произвольный DML закрыт DB guard.

## 4. Уточнения, которые следует внести до реализации

1. **not_found comment policy — закрыто 2026-11-18.** Владелец продукта выбрал вариант Б: комментарий/обоснование необязателен; обязательны финальный результат, actor и timestamp. Контракты, техническая модель и DB-15 обновлены.
2. **Удаление позиции ЦО.** В технической схеме можно хранить audit tombstone, но текущая выборка/манифест заявки должны исключать такую позицию. История изменения состава — отдельный audit/event projection.
3. **Audit ownership.** Зафиксировать для каждого класса событий, что является authoritative записью: DomainEvent или отдельный admin/security audit. Не создавать дублирующие источники истины.
4. **Command ledger.** Базовые решения по уникальности command_id, точному replay результата, 90-дневному TTL обычных записей и бессрочным tombstones необратимых операций зафиксированы. До SQL API остаются canonicalization/hash details, command_version, negative outcomes, retry horizons, cleanup/backup interaction и HTTP mapping.
5. **Box/BoxCycle.** Связь подтверждена текущей ORM и integration test; до DDL проверить сохранение Box UUID, unique box_number и нумерации циклов. Новое бизнес-решение по связи не требуется.

## 7. Решение владельца продукта по `not_found` (2026-11-18)

Владелец продукта выбрал вариант Б: комментарий/обоснование при фиксации `not_found` не обязателен. Обязательны только результат «не найдена», пользователь (`actor`) и время события (`timestamp`). Необязательный комментарий допускается сохранить, если он предоставлен. Это не затрагивает обязательный комментарий при первой фиксации `removed_by_archive` и обязательную причину отмены заявки; при повторной фиксации `removed_by_archive` после исправления новый комментарий необязателен. Соответствующие command contract, technical data model и DB-15 обновлены; продуктовый вопрос закрыт.

## 8. Статусная поправка после утверждения P-04/P-07 (2026-11-18)

Исторические формулировки в исходном snapshot, где P-04/D-13 и P-07 обозначены как открытые продуктовые решения, superseded. На актуальном HEAD оба вопроса закрыты на продуктовом уровне: P-04 включает закрытый каталог `lost`/`damaged`/`other`, а P-07 — утверждённые категории корректировок и запреты. Незакрытая детализация P-07 — точный список разрешённых clerical полей карточки; это не отменяет утверждённый запрет менять `card_number`, `full_name` и `date_of_birth` через P-07.


## 9. Решение по P-07 clerical card fields (2026-11-18)

Владелец продукта отклонил предложение разрешить исправление `Card.phone`. Обычный clerical field allowlist P-07 для карточки пуст: ни `card_number`, ни `full_name`, ни `date_of_birth`, ни `phone` не могут изменяться через P-07. Любое будущее изменение контактных/идентификационных данных требует отдельного процесса и отдельного согласования. Это не отменяет ранее утверждённые P-07 корректировки текущих custody/location, BoxCycle/membership, BoxPlacement и компенсацию ошибочного списания — они выполняются отдельными типизированными командами, а не generic card metadata patch.


## 10. Сверка неизменяемости состава P-09 (2026-11-20)

Ранее найденные формулировки в P-09, технической модели и DB command contracts допускали изменение состава после отправки заявки. Они противоречат принятому владельцем продукта правилу от 2026-11-20 и заменены. Автор ЦО редактирует только draft; отправка фиксирует неизменяемый набор карт. После отправки архив может менять только результат обработки каждой существующей позиции (например, `not_found`, `removed_by_archive`), но не состав/идентичность позиций. Отмена draft автором не требует причины; отмена submitted/processing архивом требует причины.

## 11. Рабочая очередь архива и отменённые P-09 (2026-11-20)

Согласовано владельцем продукта: отменённая после отправки P-09 исключается из текущей рабочей очереди архива, поскольку дальнейшие операционные действия по ней не требуются. Запись, причина отмены, actor/time и история сохраняются для аудита и последующего просмотра уполномоченными сотрудниками. ## 16. Разделение создания fulfillment-черновика и фактической передачи (2026-11-20)

При повторной сверке обнаружено, что §2.8 DB command contracts ошибочно объединял создание fulfillment-отправления и фактическую передачу в одну команду `request_handover`. Это противоречило уже согласованному двухэтапному процессу и §§5.4–5.5 технической модели. Исправлено:

Техническая модель уже содержала корректное разделение; синхронизированы DB command contracts, инварианты и эта cross-document review. Реализация не выполнялась.

## Решение от 2026-11-22 — порядок списания медицинской карты (P-04/D-13)

Владелец продукта подтвердил следующий процесс списания медицинской карты:

1. Центральный офис (ЦО) инициирует запрос на списание конкретной медицинской карты и указывает обязательную причину.
2. Архив проверяет карту и основание запроса.
3. Списание выполняет уполномоченный активный сотрудник архива после проверки.

Физическое удаление записи медицинской карты запрещено. Сохраняются сама запись, прежние данные, история перемещений и события; факт списания фиксируется отдельным событием с автором и временем. Филиал и администратор не инициируют и не исполняют списание; ЦО инициирует, архив исполняет. Это решение утверждает общий бизнес-порядок, но не определяет пока закрытый перечень оснований/документов, точные проверки допустимости, возможность и порядок отказа по запросу, а также детальную модель состояний и команд — эти технические детали будут проработаны без изменения утверждённого распределения ролей. Реализация не разрешена.

## 2026-11-22 — superseding decisions: коробочные отправления и выдача карт из архива

Последующие решения владельца продукта, зафиксированные после исходной cross-document review, имеют приоритет над более ранними конфликтующими формулировками. В частности, прежний вывод о полной приёмке fulfillment archive → CO без поштучных подтверждений больше не является актуальным.

Актуальная модель:
- Активные маршруты: филиал → архив (коробки), архив → ЦО (карты по заявке ЦО), ЦО → архив (коробки). Филиал → ЦО и ЦО → филиал исключены из целевой модели.
- Для обычных коробочных отправлений приёмка не предполагает пересчёта медицинских карт внутри коробок; количество карт не проверяется. Пломба и целостность упаковки не проверяются.
- Архив может массово размещать несколько принятых коробок на одной полке и массово перемещать несколько коробок на одну целевую полку. Обе операции атомарны; массовое извлечение карт из нескольких коробок запрещено.
- Одна заявка ЦО на получение карт может содержать несколько карт. Архив может выдавать их частями; невыданные остаются ожидающими, а найденные позднее карты можно выдать в рамках той же заявки.
- Для отдельной карты архив может зафиксировать «Не найдена» с обязательной причиной из закрытого справочника и необязательным комментарием. Карта не списывается и не удаляется; последующая выдача в той же заявке возможна.
- ЦО отменяет заявку до начала выдачи; после частичной выдачи отменяет только оставшуюся часть.
- ЦО подтверждает фактическое получение каждой карты; массовое подтверждение нескольких фактически полученных карт разрешено атомарно. До подтверждения ответственность остаётся у архива. Подтверждать получение до фактического поступления нельзя.

## 2026-11-22 — correction: ordinary box shipment receipt is per box

A later approved product decision dated 2026-11-21 requires individual receipt of each box in ordinary branch → archive and central_office → archive shipments. This supersedes prior wording in earlier sections and addenda that said the archive receives the entire box shipment as one indivisible operation.

Each box receipt independently records actor/time and transfers that box's custody to archive. The shipment remains open until all manifest boxes and discrepancies are resolved. A received box may be placed on a shelf immediately in a separate operation, without waiting for the rest of the shipment. Late boxes are received individually within the same shipment; unexpected boxes are recorded as discrepancies and are not auto-added. No card count, seal or packaging inspection is required.

This is distinct from P-09 archive → CO, which transports individual medical cards and requires item-level actual receipt by CO. Both workflows are granular at their own manifest item level, but they have different objects, custody semantics and commands.

## 2026-11-22 — сквозная сверка P-09: batches, item receipts и отмена остатка

Проверены актуальные редакции technical data model, DB command contracts, invariants DB-71…DB-73, route/state audit, readiness review и event/read-model inventory.

### Согласовано между целевыми документами

- Parent P-09 → 0..N fulfillment batches; каждая batch принадлежит одному parent и содержит только выбранные items этого parent.
- Item может иметь не более одной текущей активной/выданной batch; отмена draft batch атомарно освобождает текущую ссылку item, не удаляя исторический manifest.
- Batch имеет состояния `draft`, `in_transit`, `partially_received`, `received`, `cancelled`. `partially_received` возникает после первого item receipt, `received` — только после receipt всех items данной batch.
- Item receipt — отдельный факт на каждую карту. Bulk receipt набора реально поступивших карт — одна транзакция; любая недопустимая позиция откатывает весь набор.
- Handover партии не переводит custody в ЦО. Custody меняется только у конкретной карты при её item-level receipt.
- Исправление `not_found` / `removed_by_archive` оценивается по конкретному item. Наличие других batches того же parent не блокирует восстановление; item, уже назначенный в активную/выданную batch или получивший receipt, восстановлению не подлежит.
- Создание batch, handover, cancel remainder и receipt сериализуются на parent/items; инварианты DB-71…DB-73 отражают one-to-many и item-level lifecycle.

### Найдено противоречие / пробел в статусной проекции parent

После частичной выдачи команда отмены отменяет только невыданный остаток; уже выданные items остаются `issued_pending_receipt` и должны продолжить lifecycle до фактического receipt ЦО. При этом матрица действий route/state audit для parent `cancelled` описывает только read-only доступ, а технические документы не задают однозначно, в какой момент parent получает статус `cancelled`, если ещё остаются выданные, но не принятые карты.

Это не меняет согласованное право отменить остаток и не позволяет отменять выданные карты. Это незакрытая техническая проекция состояния: необходимо явно определить, остаётся ли parent в `processing` до receipt последней выданной карты с последующим переходом в `cancelled`, либо используется иная двухфазная модель. До фиксации этого правила UI/API не должны скрывать возможность ЦО подтвердить уже выданные карты только из-за отмены остатка. Parent нельзя считать полностью завершённым, пока существует `issued_pending_receipt`.

### Устаревшие формулировки

В исторической записи этого review (раздел 16, строки о единственном fulfillment shipment и `ArchiveRequest.fulfillment_shipment_id`) сохранён прежний вариант one-to-one. Он superseded решением one-to-many от 2026-11-22 и не является действующей спецификацией. Действующая матрица выше и раздел о транспортных партиях (раздел 4) имеют приоритет. Аналогично, ранние упоминания полного handover/full receipt следует читать как исторические.

## 2026-11-22 — закрытие P-09 parent terminal-state projection

Предыдущая запись о неопределённости статуса parent после отмены невыданного остатка снята после сверки с принятым P-09 §30–32, technical data model §§3.1/5.3, DB command contract §2.7, DB-22 и UX-05 queue semantics. Однозначная модель уже содержится в этих источниках:

- `cancelled` — полная отмена draft/submitted либо отмена processing до первой физической выдачи;
- после частичной выдачи отмена затрагивает только невыданные позиции и публикует `archive_request.remaining_items_cancelled`; parent остаётся `processing`, `cancelled_at/cancelled_by` не устанавливаются;
- ранее выданные позиции остаются `issued_pending_receipt`; ЦО продолжает item-level receipt;
- когда все позиции терминальны (получены ЦО, `not_found` или отменены как невыданный остаток), parent становится `completed` и публикуется `archive_request.completed`.

Таким образом, после частичной выдачи родительская заявка не переходит в `cancelled`. Дополнительное продуктовое решение не требуется. Матрица route/state, command event semantics, dashboard queue и event consumer inventory синхронизированы. Также исправлено устаревшее утверждение о единственной fulfillment transport record: актуальна one-to-many модель parent → batches.
