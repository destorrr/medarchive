# UX-06 — контракты защищённых DB-команд для заявок, отправлений и хранения

Дата: 2026-11-18  
Статус: проектная спецификация, не реализация  
Основа: принятые D-01…D-18, P-01…P-09 и DB-SEC-01…04; статическая инвентаризация текущего PostgreSQL кода.

## 1. Общие требования к каждой команде

Все команды выполняются одной транзакцией PostgreSQL. Runtime вызывает только разрешённые функции/процедуры; прямые INSERT/UPDATE/DELETE критичных таблиц после cutover запрещены.

### 1.1 Общий envelope

Каждая команда получает:
- `p_actor_user_id` — UUID пользователя, аутентифицированного application layer;
- `p_command_id` — UUID команды для идемпотентности;
- `p_correlation_id` — UUID бизнес-операции/сквозной трассировки;
- бизнес-параметры команды;
- при необходимости `p_reason` / `p_comment`.

Actor trust соответствует DB-SEC-01: БД проверяет, что пользователь существует, активен и имеет допустимую роль/branch scope; это не независимое криптографическое доказательство личности.

DB boundary обязан проверять:
1. actor существует и активен;
2. actor role и область полномочий соответствуют операции;
3. объект и связанные объекты доступны actor по серверному scope;
4. исходный статус и все предусловия;
5. уникальность `command_id` в пределах идемпотентного журнала;
6. бизнес-инварианты независимо от UI.

Возвращать типизированный результат: `success`, `already_applied`, `not_found`, `forbidden`, `invalid_state`, `conflict`, `validation_error`. Внутренние SQL детали не раскрывать пользователю.

**Обязательный формат результата (утверждён 2026-11-20):** каждая публичная DB-команда возвращает единый versioned JSONB envelope:

```json
{
  "result_code": "success",
  "result_version": 1,
  "result_payload": {},
  "command_id": "uuid",
  "correlation_id": "uuid",
  "completed_at": "database timestamp"
}
```

- `result_code` выбирается из закрытого allowlist конкретной команды/семейства команд.
- `result_version` версионирует схему `result_payload`.
- Для каждой команды документируется строгая схема и validator payload; произвольный JSON, ORM-объекты и SQL-диагностика запрещены.
- В payload возвращаются только минимально необходимые стабильные идентификаторы/состояния; PII — только при необходимости API use case и наличии актуального права чтения.
- Command ledger сохраняет точный committed envelope; replay возвращает первоначальный семантический результат, а не пересчитывает текущее состояние.
- HTTP status и публичное тело ответа формирует API adapter по отдельной спецификации. SQLSTATE, имена constraints и тексты исключений не входят в публичный envelope.
- Внутренние высокочастотные SQL-функции могут использовать фиксированные типизированные scalar returns, но внешний контракт DB-команд остаётся единым envelope.

### 1.2 Общая транзакционная последовательность

1. Проверить/зарегистрировать idempotency key.
2. Заблокировать principal actor и используемые role/location membership записи; при необходимости — principal текущего автора/целевого пользователя, в стабильном порядке UUID.
3. Заблокировать корневой агрегат (parent request либо shipment/box/cycle/card/admin entity).
4. Заблокировать карты в сортированном порядке UUID.
5. Заблокировать коробки, циклы, membership и placements в стабильном порядке.
6. Заблокировать/проверить shipment и manifest, если затрагиваются.
7. Повторно проверить активность, роль, scope, состояние и все предусловия после получения блокировок.
8. Выполнить все изменения состояния.
9. Записать DomainEvent и необходимые admin/security audit entries.
10. Сохранить результат команды для безопасного повтора и commit; любая ошибка до commit откатывает все изменения.

Общий lock order: сначала строки авторизационного контекста (пользователь и активные role/location membership, UUID по возрастанию), затем parent request → cards sorted → boxes/cycles/memberships/placements sorted → shipment/manifest. Для операций без заявки после авторизационного контекста использовать соответствующий корневой агрегат (shipment, box/cycle, card или admin entity) и не нарушать единый порядок связанных ресурсов. Если команда зависит от авторства черновика или другого пользователя, блокировать и повторно проверять также его principal/membership в том же порядке UUID.

### 1.3 Сериализация полномочий и деактивации

Проверка active/role/location только до получения блокировок недостаточна: деактивация пользователя или отзыв его membership могут конкурировать с уже начатой бизнес-командой.

Обязательный протокол:
- В той же транзакции заблокировать строку пользователя и все используемые для решения доступа активные role/location membership записи через FOR UPDATE, в стабильном порядке UUID.
- Повторно проверить после блокировки, что actor активен, его роль и membership действуют, а требуемая локация совпадает с объектом и операцией.
- Для команд, право которых зависит от текущего автора черновика, заблокировать и проверить также principal/membership текущего автора; для admin reassignment — principal/membership нового автора.
- Команды admin deactivation и изменения role/location membership используют те же строки и тот же порядок блокировок. Они не могут завершить отзыв полномочий посреди команды, которая уже получила блокировку; и наоборот, команда, пришедшая после commit деактивации/отзыва, обязана получить отказ.
- Если handover получил блокировку действующего автора первым, он может завершиться до деактивации. Если деактивация/отзыв завершились первыми, handover отклоняется; после этого admin может выполнить отдельное переназначение автора по §2.11. Никакого автоматического переназначения или подтверждения handover администратором нет.
- При повторе idempotency key применяются отдельные правила §11.4: перед возвратом сохранённого результата повторно проверяются активность actor и актуальное право читать чувствительные данные.

Деактивация не переписывает уже совершённые события, назначения курьера, manifest или custody. Этот протокол определяет только то, какая из конкурирующих операций получает право завершиться первой.

## 2. Команды родительской заявки ЦО

Целевая модель — `ArchiveRequest` как родительский aggregate и `ArchiveRequestItem` как отдельные позиции. Это проектная модель P-09; в текущем ORM она ещё не реализована.

### 2.1 `request_create_draft`

**Actor:** `central_office`.

**Вход:** набор уникальных `card_id`, `command_id`, `correlation_id`.

**Предусловия:**
- список непустой, без дубликатов;
- каждая карта существует, активна и доступна ЦО;
- карта не имеет действующего резервирования за другой незавершённой P-09;
- карта находится на балансе ЦО в допустимом состоянии;
- все карты доступны в scope actor.

**Изменения:**
- создать один parent request со статусом `draft`;
- создать по одной позиции `pending` на карту;
- сохранить автора и timestamps.

**Физическое состояние:** не менять Card location, BoxCycle, membership или BoxPlacement.

**События:** `archive_request.created` с parent aggregate и отдельные `archive_request.item_added` для состава; payload ссылается на item/card identifiers без копирования ФИО и других лишних PII.

### 2.2 `request_submit`

**Actor:** только автор черновика `central_office`.

**Вход:** `request_id`, idempotency metadata.

**Предусловия:** request `draft`, есть хотя бы одна активная позиция, позиции всё ещё соответствуют требованиям доступности.

**Изменения:** parent `draft → submitted`, зафиксировать submit actor/time.

**Физическое состояние:** никаких извлечений и перемещений карт.

**Событие:** `archive_request.submitted` с фактическим actor/time.

### 2.3 `request_edit_draft`

**Actor:** только автор черновика `central_office`.

**Вход:** `request_id`, списки add/remove card IDs, idempotency metadata.

**Предусловия:**
- parent находится строго в `draft`;
- actor совпадает с `requested_by`;
- удаляемые позиции принадлежат этому parent;
- добавляемые карты доступны ЦО, не дублируются и не конфликтуют с другими активными заявками.

**Изменения:**
- добавить позиции `pending`;
- удалённые из черновика позиции исключить из актуального состава; при необходимости сохранить audit tombstone `removed_by_central_office` и атомарно снять с них `reservation_active`;
- физически удалять строки и историю запрещено.

**Физическое состояние:** не менять коробки, membership и placements.

**Гонка:** сериализовать по parent request. После успешной отправки любая команда редактирования возвращает `invalid_state`; никакая роль не может менять состав submitted-заявки.

**События:** `archive_request.item_added`, `archive_request.item_removed_by_central_office` (только draft).

### 2.4 `request_start_processing`

**Actor:** `archive`.

**Вход:** `request_id`, idempotency metadata.

**Предусловия:**
- parent `submitted`;
- состав не пуст;
- все активные pending items проверены;
- каждая карта имеет ровно одно ожидаемое активное membership и допустимое архивное положение;
- карты не включены в активное отправление и не имеют несовместимого custody/status;
- archive actor имеет доступ к соответствующему архиву.

**Атомарные изменения:**
1. Заблокировать parent request.
2. Заблокировать все карты и их текущие циклы/членства/размещения в стабильном порядке.
3. Повторно проверить весь состав.
4. Закрыть активные `BoxCardMembership` для всех подлежащих обработке карт.
5. Перевести позиции в `extracted`, сохранить source box/cycle references для истории и возврата.
6. Для каждой коробки, у которой извлечение удалило последнюю активную карту, закрыть `BoxPlacement`; сама коробка остаётся в архивной локации без полочного размещения (D-11/P-06).
7. Parent `submitted → processing`.
8. Записать `archive_request.processing_started` и item-level `archive_request.item_extracted` для каждой автоматически извлечённой позиции; все события содержат фактического actor/time и записываются в той же транзакции.

**Результат по умолчанию:** в этой же атомарной операции каждая позиция получает `extracted`. Это не только физический факт извлечения: для P-09 `extracted` одновременно означает автоматический результат «карта найдена и готова к передаче». Отдельная команда/кнопка подтверждения «Найдена» не предусмотрена. После старта архив фиксирует только исключения, которые заменяют `extracted`: `not_found` или `removed_by_archive`.

**Запрет:** нельзя оставить parent в processing с частично извлечёнными картами. Ошибка любого шага откатывает всю команду.

**Идемпотентность:** повтор с тем же command_id возвращает сохранённый результат; другой command_id при уже processing возвращает `already_applied/invalid_state`, без повторного извлечения.

**Дальнейшая обработка:** после успешного старта любой активный сотрудник архива с доступом к очереди P-09 и данной заявке может фиксировать результаты незавершённых позиций; право не закрепляется за сотрудником, который начал обработку. Архив фиксирует результат каждой карты отдельной командой. Каждая команда результата — самостоятельная транзакция: результат и соответствующее событие сохраняются сразу, без промежуточного общего черновика и без отдельного действия «сохранить все результаты». Если сотрудник прерывает работу, уже зафиксированные результаты остаются сохранёнными; заявка остаётся в `processing`, а обработку можно продолжить позднее по ещё не завершённым позициям. Ошибка команды для одной позиции не откатывает результаты других ранее обработанных позиций и не отменяет атомарность первоначального извлечения всего состава.

### 2.5 `request_remove_item`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и данной заявке; не обязательно сотрудник, начавший обработку.

**Вход:** `request_id`, `item_id`, обязательный непустой комментарий, idempotency metadata.

**Предусловия:** parent `processing`, item `extracted` (автоматический результат «Найдена, готова к передаче»), карта ещё не передана в shipment.

**Изменения:**
- вернуть карту в допустимое архивное хранение через помещение в коробку;
- создать/активировать membership в текущем или новом BoxCycle по правилам D-10;
- item → `removed_by_archive`, actor/time; при первой фиксации сохранить обязательный комментарий, при повторной после исправления новый комментарий необязателен. `reservation_active` сохраняется, хотя карта физически возвращена в коробку; новая P-09 на эту карту до завершения/отмены текущей заявки запрещена;
- обновить состояние пустой коробки/placement по правилам операции возврата, не путать с regroup.

**Событие:** `archive_request.item_removed_by_archive` с item reference, actor/time и обязательным комментарием при первой фиксации.

**Атомарность:** возврат карты, изменение item и событие — одна транзакция. Успешная команда сразу фиксирует результат этой позиции; отдельное пакетное подтверждение результатов не требуется.

**Запрет:** нельзя исключать item после handover; нельзя удалить item без возврата карты. Уже завершённые позиции нельзя повторно обрабатывать как незавершённые; ошибка или прерывание обработки другой позиции не переписывает их результаты.

### 2.6 `request_mark_not_found`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и данной заявке; не обязательно сотрудник, начавший обработку.

**Вход:** `request_id`, `item_id`, idempotency metadata. Пользовательский комментарий/обоснование необязателен.

**Предусловия:** parent `processing`, item имеет текущий результат `extracted`, карта не находится в активном shipment и не была передана. Это условие действует и при повторном `extracted → not_found` после исправления.

**Изменения:** item `extracted → not_found`, сохранить actor/time; необязательный комментарий может быть сохранён, если предоставлен. Физическое размещение не создавать и не менять, поскольку карта не обнаружена. `reservation_active` сохраняется, пока parent остаётся `processing`.

**Событие:** `archive_request.item_marked_not_found` с item reference, actor/time и необязательным комментарием.

**Текущий результат:** `not_found` сохраняется сразу вместе с actor/time и событием. До создания fulfillment-черновика разрешён повторный цикл `not_found → extracted → not_found`: после обнаружения карта извлекается по §2.6a, а при последующем фактическом отсутствии `request_mark_not_found` фиксирует новое событие без membership. Каждое событие остаётся в истории. Новая потребность после завершения заявки оформляется новой заявкой (D-04).

### 2.6a `request_restore_item_to_extracted`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и конкретной заявке.

**Вход:** `request_id`, `item_id`, идентификатор текущего активного архивного membership/коробки, idempotency metadata. Комментарий исправления не запрашивается и не является обязательным; исходный комментарий `removed_by_archive` сохраняется в истории.

**Предусловия:** parent `processing`; `fulfillment_shipment_id IS NULL`; item имеет текущий статус `not_found` или `removed_by_archive`; карта фактически обнаружена в архивном хранении и может быть извлечена из конкретной коробки. Запрещено исправлять результат после создания fulfillment-черновика, после handover или после завершения/отмены parent.

**Изменения:**
- заблокировать parent, item, card, активное membership, BoxCycle и BoxPlacement;
- проверить, что карта находится в указанной коробке и принадлежит архиву;
- закрыть активное membership карты в коробке; не удалять его и не переписывать историю размещения;
- обновить размещение коробки по обычным правилам закрытия membership, не выполняя автоматическую перегруппировку;
- item → `extracted`; очистить только текущие поля результата исключения, если они моделируются как актуальное состояние; исходные сведения и комментарий остаются в append-only DomainEvent;
- сохранить актуальные `extracted_at`/`extracted_by` или эквивалентные метаданные повторного извлечения;
- добавить append-only событие исправления с `previous_status`, `new_status=extracted`, card/item, actor, timestamp и ссылкой на закрытое membership. Отдельное объяснение исправления не требуется.

**Атомарность:** закрытие membership, физическое размещение, изменение текущего результата позиции и событие исправления — одна транзакция. При любой ошибке всё откатывается.

**История:** исходное событие `not_found`/`removed_by_archive` остаётся неизменным; новое событие показывает исправление, прежний и новый результаты, сотрудника и время. Timeline отображает оба события в обратном хронологическом порядке.

**Идемпотентность и гонки:** повтор с тем же command_id возвращает исходный результат; новая команда при уже `extracted` получает `already_applied/invalid_state`. После `not_found → extracted` новая команда `request_mark_not_found` с другим command_id допустима, если карта фактически не обнаружена. Команды сериализуются с отменой parent и созданием fulfillment-черновика; если fulfillment-черновик создан первым, изменение отклоняется.

**Событие:** `archive_request.item_result_corrected` с item reference, `previous_status`, `new_status`, actor/time и ссылкой на закрытое membership; отдельное объяснение не требуется.

### 2.7 `request_cancel`

**Actor и причина зависят от состояния:**
- `draft`: только автор черновика ЦО; причина не требуется.
- `submitted`: только уполномоченный сотрудник архива; причина обязательна.
- `processing`: только уполномоченный сотрудник архива до фактической передачи fulfillment-отправления; причина обязательна.

**Вход:** `request_id`, причина только для состояний `submitted/processing`, idempotency metadata.

**Предусловия:** parent находится в одном из перечисленных состояний; фактическая передача fulfillment-отправления ещё не состоялась.

**Отмена draft:** parent → `cancelled`; все draft-позиции/аудиторские tombstones сохраняются; физическое состояние карт не меняется.

**Отмена submitted:** parent → `cancelled`; незавершённые позиции → `cancelled`; физическое состояние карт не меняется, поскольку обработка и извлечение не начинались.

**Отмена processing:** в одной транзакции:
- заблокировать parent, все extracted cards и связанные коробки/cycles;
- вернуть в коробки все извлечённые карты, остающиеся под ответственностью архива и ещё не переданные;
- перевести незавершённые позиции в `cancelled`;
- сохранить окончательные `not_found` и `removed_by_archive`;
- если fulfillment-черновик существует, отменить его в той же транзакции;
- parent → `cancelled`;
- записать actor/time и обязательную причину.

Если хотя бы одна карта не может быть возвращена, вся отмена откатывается.

**События:** `archive_request.cancelled` с actor/time и причиной для `submitted/processing` (для draft причина отсутствует); если существовал fulfillment draft, его отмена дополнительно фиксируется в истории shipment как `shipment.cancelled`. В timeline P-09 показывается одно родительское событие отмены, без дублирования связанного shipment cancellation.

**Гонка с handover:** request_cancel и shipment_confirm_handover сериализуются одной блокировкой parent. После успешного handover отмена невозможна.

### 2.8 `request_create_fulfillment_draft`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и конкретной заявке.

**Вход:** `request_id`, обязательный `courier_id` из общего справочника активных курьеров, snapshot отображаемого ФИО на момент назначения, idempotency metadata. Проверка активности и доступности курьера выполняется в транзакции создания.

**Предусловия:**
- parent находится в `processing`;
- `ArchiveRequest.fulfillment_shipment_id IS NULL`;
- все позиции имеют сохранённый результат: `extracted`, `removed_by_archive` или `not_found`; незавершённых `pending` нет;
- все карты `extracted` физически извлечены и доступны к передаче;
- ни одна такая карта не включена в другое активное отправление.

**Атомарные изменения:**
- создать ровно один Shipment archive → central_office со статусом `draft`;
- включить в его манифест все и только позиции со статусом `extracted`;
- создать единственный неизменяемый снимок полного манифеста в истории отправления: факт создания, actor, время и список карт;
- установить `ArchiveRequest.fulfillment_shipment_id` в той же транзакции;
- оставить карты под ответственностью архива: не устанавливать `current_shipment_id`, не переводить позиции в `in_shipment`;
- оставить parent в `processing`.

**Событие:** `shipment.draft_created` с aggregate shipment и `request_id` родителя; payload включает единственный неизменяемый snapshot полного манифеста, actor/time.

**Если карт для передачи нет:** fulfillment-отправление не создаётся. После фиксации последнего окончательного результата заявка автоматически переходит в `completed` по критерию §2.10.

**Запрет:** создание второго fulfillment shipment, частичного манифеста, повторное установление ссылки или изменение состава после создания черновика запрещены.

### 2.9 `shipment_confirm_handover` для fulfillment archive → CO

**Actor:** только автор черновика fulfillment-отправления; на момент команды он должен оставаться активным сотрудником архива с полномочиями на данную заявку.

**Вход:** `shipment_id`, idempotency metadata.

**Предусловия:**
- parent находится в `processing`;
- shipment находится в `draft` и связан с parent через единственную ссылку `ArchiveRequest.fulfillment_shipment_id`;
- фактическая передача ещё не подтверждалась;
- полный манифест неизменяем и содержит все и только карты со статусом `extracted` этой заявки;
- карты не возвращены в коробки и не переданы в другое отправление.

**Атомарные изменения:**
- shipment переходит `draft → in_transit`;
- всем картам манифеста устанавливается `current_shipment_id`;
- все соответствующие позиции переходят `extracted → in_shipment`;
- ответственность за карты переходит от архива к назначенному курьеру;
- записывается `shipment.handed_over` с actor/time и `request_id` родителя; второй снимок манифеста не создаётся;
- parent остаётся `processing` до полной приёмки ЦО.

**Запрет:** частичная передача, изменение манифеста, повторное подтверждение и отмена после фактической передачи запрещены.


### 2.8a `shipment_change_fulfillment_courier`

**Actor:** только сотрудник архива, создавший fulfillment-черновик; учётная запись должна оставаться активной и иметь доступ к заявке.

**Вход:** `shipment_id`, новый `courier_id` из общего справочника активных курьеров, новый snapshot отображаемого ФИО, idempotency metadata.

**Предусловия:**
- shipment archive → central_office находится в `draft` и связан с P-09;
- фактическая передача ещё не подтверждена;
- новый курьер активен на момент выполнения команды;
- вызывающий сотрудник является автором этого черновика.

**Атомарные изменения:**
- заменить ссылку на запись курьера;
- заменить snapshot ФИО курьера на значение из выбранной записи на момент переназначения.

**История:** отдельная история прежних назначений не ведётся; событие переназначения не добавляет снимок состава карт и не меняет единственный неизменяемый manifest snapshot. Текущее назначение и его snapshot доступны в карточке отправления.

**Запрет:** переназначение после фактической передачи, назначение нового неактивного курьера и переназначение сотрудником, отличным от автора черновика, запрещены. Если ранее назначенный курьер деактивирован после назначения, это не меняет существующее назначение и не препятствует подтверждению передачи.

### 2.10 Завершение parent request

Завершение — автоматическая часть последней команды, которая делает условие завершения истинным: последней фиксации результата позиции, если отправлять нечего, либо `shipment_receive_all`, если fulfillment-отправление создано.

При автоматическом переходе записывается `archive_request.completed` с фактическим actor/time команды, которая завершила условие (последний результат позиции либо receipt).

Parent → `completed`, когда:
- все позиции имеют окончательный результат;
- если создан shipment, он полностью принят ЦО;
- все отправленные items → `completed`;
- ни одна позиция не остаётся pending/extracted/in_shipment.

Если все позиции получили `removed_by_archive` или `not_found`, заявка завершается без shipment.

## 3. Команда `shipment_receive_all`

**Actor:** активный сотрудник целевой локации-получателя с полномочиями приёмки. Для fulfillment archive → central_office — сотрудник ЦО.

**Вход:** `shipment_id`, подтверждение получения всего отправления целиком, idempotency key. Поштучное подтверждение карт, подтверждение сверки и resolution metadata не запрашиваются.

**Предусловия:**
- shipment находится в состоянии, допускающем полную приёмку;
- actor принадлежит получающей локации;
- сохранённый манифест неизменяем; для fulfillment archive → central_office он является исходным перечнем отправленных карт;
- подтверждается получение всего отправления целиком; частичная приёмка запрещена;
- для fulfillment archive → central_office поштучная сверка полученных карт с манифестом не выполняется.

**Изменения:**
- атомарно принять весь manifest;
- обновить custody/location/status всех карт и коробок по маршруту;
- закрыть shipment;
- если shipment связан с archive request, все `in_shipment` items → `completed`, затем проверить условие завершения parent;
- записать `shipment.received` с фактическим actor/time и `request_id` (для P-09); если parent достиг `completed`, записать `archive_request.completed` с тем же фактическим actor/time. Для P-09 timeline включает эти два разных факта: приёмку отправления и завершение заявки.

Для fulfillment archive → central_office приёмка не включает проверку каждой карты, фиксацию поштучных расхождений или автоматическую корректировку. Состав манифеста не меняется; дополнительный snapshot на момент приёмки не создаётся.

## 4. Команды коробок и хранения

### 4.1 `box_create`

Создаёт только физическую тару в указанной допустимой локации; начальный BoxCycle при создании коробки не создаётся. Actor должен иметь право создавать коробки в этой локации. Человекочитаемый номер уникален. QR коробки не создаётся (D-17). Коробка без текущего цикла является допустимым полноценным объектом учёта.

### 4.2 `box_add_card` / `box_remove_card`

Проверяют роль, location scope, статус коробки, активные shipments, membership карты и отсутствие конфликтующей операции. Активный BoxPlacement сам по себе не блокирует добавление карты в пустую коробку, если коробка осталась на полке после перегруппировки и не участвует в активном shipment. При добавлении карты в коробку с открытым BoxCycle создаётся membership в этом цикле. Если открытого цикла нет, команда в одной транзакции создаёт новый BoxCycle и первое membership; при повторном заполнении пустой коробки на полке существующий BoxPlacement сохраняется. Цикл не может быть создан отдельно от фактического добавления первой карты. При закрытии последнего активного membership текущий BoxCycle автоматически завершается в той же транзакции независимо от причины удаления карты. Нельзя оставить открытый BoxCycle без активных карт или создать второе активное membership карты.

### 4.3 `box_repack`

**Actor:** уполномоченный активный сотрудник соответствующей операционной локации; для перегруппировки коробки с активным `BoxPlacement` — сотрудник архива в scope архивной локации.

Операция перегруппировки:
- блокирует исходные и целевые коробки, циклы и все карты в стабильном порядке;
- закрывает исходные memberships;
- создаёт новый BoxCycle для каждой физической тары, которая получает новое заполнение;
- создаёт новые memberships;
- сохраняет историю старых циклов;
- не меняет полочное размещение только из-за перегруппировки;
- архивный сотрудник может перегруппировать карты из коробки с активным `BoxPlacement`, в том числе извлечь последнюю карту;
- если коробка стала пустой в результате regroup, текущий BoxCycle завершается автоматически вместе с закрытием последнего membership, а активный `BoxPlacement` сохраняется; UI явно показывает, что пустая коробка остаётся на полке (D-11/P-03, DB-61).

Различие сценариев касается полочного размещения, а не жизненного цикла BoxCycle: при любом выходе последней карты цикл закрывается автоматически; при extraction последней карты по P-09 placement автоматически закрывается, а при перегруппировке пустая коробка остаётся размещённой.

### 4.4 `box_write_off`

**Actor и область доступа (P-05):** активный сотрудник с ролью `branch`, `central_office` или `archive` может списать коробку только в пределах собственной операционной области/локации. Активный `admin` имеет отдельное прямое полномочие списать коробку в любой локации; для него не требуется принадлежность к операционной области этой локации. Это узкое исключение P-05 и не предоставляет admin иных операционных полномочий. Сервер проверяет роль, активность учётной записи и применимое правило области доступа.

**Предусловия:** коробка пуста, не имеет активных memberships и открытого `BoxCycle`, не участвует в активном shipment и не имеет активного `BoxPlacement` (перед списанием должна быть снята с полки). Причина/комментарий не запрашивается. Команда фиксирует фактического actor и время; запись физической тары, завершённые циклы, прежние размещения и события сохраняются, физическая коробка не удаляется.

### 4.5 `box_unplace`

**Actor:** уполномоченный активный сотрудник архива в scope соответствующей архивной локации.

**Предусловия:** физическая коробка находится на учёте архива; у неё нет активных memberships и открытого `BoxCycle`; коробка не включена в активный shipment; существует ровно одно активное `BoxPlacement`.

**Изменения:** закрыть текущее `BoxPlacement` в той же транзакции, сохранив запись и её временные/аудиторские атрибуты в истории. Физическая коробка, её учётная локация, custody и завершённые `BoxCycle` не удаляются и не переписываются. После операции коробка остаётся в учётной локации архива без полочного размещения.

**Событие:** записать отдельное событие снятия коробки с полки с фактическим actor/time. Команда не требует обязательного комментария.

**Запреты:** нельзя снимать с полки непустую коробку, коробку с открытым циклом или коробку в активном shipment. Повторное размещение выполняется отдельной командой размещения; окончательное списание — отдельной `box_write_off`, которая по-прежнему требует отсутствия активного placement.

### 4.6 `box_place`

**Actor:** уполномоченный активный сотрудник архива в scope целевой архивной локации.

**Вход:** `box_id`, `shelf_id`, idempotency metadata.

**Предусловия:**
- коробка числится в той же архивной локации, к которой относится целевая полка;
- коробка не участвует в активном shipment;
- у коробки нет активного `BoxPlacement`;
- целевая полка существует, активна и относится к этой же архивной локации;
- коробка может быть как заполненной (есть активное membership и открытый BoxCycle), так и пустой (нет активных memberships и открытого BoxCycle).

**Изменения:** создать ровно одно активное `BoxPlacement`, связанное с указанной коробкой и полкой. Не создавать, не открывать и не менять `BoxCycle`/membership; не менять учётную локацию или custody. Предыдущие закрытые placements остаются в истории.

**Событие:** записать отдельное событие размещения коробки на полке с фактическим actor/time. Создание placement и событие выполняются одной транзакцией.

**Запреты:** нельзя размещать коробку из другой локации, на неактивную/чужую полку, коробку в активном shipment или коробку с уже активным placement. Повторное заполнение пустой размещённой коробки выполняется через `box_add_card` и сохраняет этот placement (DB-57).

## 5. Карта и внешнее хранение

### 5.1 `card_register_manual` / `card_register_qr`

Actor — branch. До создания карты выполнить проверку уникальности номера/QR и поиск возможных совпадений только по ФИО пациента; допускается неполный ввод ФИО, включая поиск только по фамилии и поиск по началу фамилии. Ручной поиск по номеру медицинской карты, телефону или дате рождения не предоставляется; сканирование штрихкода остаётся отдельным способом идентификации карты. В строке результата показываются ФИО и номер медицинской карты; дата рождения и телефон (если указаны) показываются всем активным сотрудникам, имеющим доступ к соответствующей карте в пределах действующих scope/custody/process rules; отдельные права на чтение этих двух полей не требуются. В выдаче отображаются все доступные сотруднику совпадения по ФИО единым списком: без ограничения количества результатов, скрытого top-N и разбиения на отдельные группы. Поиск должен находить совпадения при неполном вводе: достаточно фамилии или начальной части фамилии; запрос только по фамилии возвращает все доступные совпадения с этой фамилией независимо от имени и отчества. Если введено несколько частей ФИО, каждая введённая часть сопоставляется с начала соответствующего слова ФИО без требования заполнить ФИО целиком; порядок частей сохраняется. Например, «Иванов Ив» находит «Иванов Иван Петрович», а «Иванов Иван П» — «Иванов Иван Петрович». Правило применяется и к отчеству, если оно введено. Сопоставление выполняется без учёта регистра и с нормализацией `е`/`ё`: варианты написания с `е` и `ё` считаются эквивалентными (например, «Семенов» и «Семёнов»). Перед сопоставлением поисковый ввод нормализуется по пробелам: пробелы в начале и конце удаляются, последовательности из нескольких пробельных символов между частями ФИО сводятся к одному пробелу. Это влияет только на поиск и не изменяет сохранённое ФИО. Порядок частей ФИО в поисковом запросе сохраняется: перестановка фамилии, имени и отчества не допускается и не должна давать совпадение только за счёт перестановки (например, запрос «Иван Петрович Иванов» не находит «Иванов Иван Петрович»). Поиск по фамилии выполняется только по её началу: запрос «Ива» может находить «Иванов», запрос «ванов» не находит «Иванов». Поиск по произвольному фрагменту внутри фамилии запрещён. Если технически требуется постраничная загрузка, она должна быть непрерывной частью того же списка и обеспечивать доступ ко всем совпадениям; результат не должен выглядеть как полный, пока не загружены все записи.
 
Найденные записи показываются сотруднику до создания новой карты и только в пределах его read permissions. Совпадение ФИО рассматривается как подсказка для проверки, а не как запрет на создание карты: один пациент может иметь несколько самостоятельных медицинских карт, в том числе из разных филиалов. Сотрудник может выбрать существующую запись, если это именно та медицинская карта, которая ему нужна; если требуется оформить другую карту тому же пациенту, создание новой записи разрешается. Совпадение номера медицинской карты или QR/штрихкода означает конфликт уникального идентификатора и не может быть обойдёно подтверждением «другая карта». Автоматическое объединение, слияние или изменение существующих записей запрещено.
 
Проверка выполняется сервером повторно при регистрации; уникальность номера/QR и защита от конкурентного создания записей с одинаковыми идентификаторами обязательны. QR payload сохраняется в существующем формате (D-17). Создание карты и DomainEvent — атомарны. При создании карты непосредственно из сценария добавления в коробку те же правила поиска и различения существующей/новой карты применяются без изменений; создание новой карты и её добавление в коробку остаются единым атомарным бизнес-сценарием.

### 5.2 `card_mark_external` / `card_return_external`

Actor — central_office. Проверить, что карта на балансе ЦО, не в shipment, не в коробке/активном membership и не списана. Внешнее хранение не является shipment route (D-05/D-18). Сохранить type, organization, comment и timestamps; событие записать в той же транзакции.

## 6. Административные DB-команды

Разрешённый набор следует ограничить конкретными use cases:
- `admin_create/update/deactivate_branch`;
- `admin_create/update/deactivate_user`;
- `admin_create/update/deactivate_courier`;
- `admin_create/update/deactivate_shelf`;
- `shipment_reassign_draft_author` — отдельная административная команда переназначения автора деактивированного черновика по контракту §2.11;
- `admin_correct` — только отдельный allowlist корректирующих операций с обязательным reason.

Для всех команд:
- actor role = admin;
- запрет самодеактивации и деактивации последнего active admin;
- deactivate вместо физического удаления;
- сохранение ссылок и истории;
- блокировка конкурирующих изменений;
- before/after, actor, time и correlation записываются в отдельный admin/security audit; reason обязателен для корректирующих операций и отмен, но не вводится для `shipment_reassign_draft_author`, где фиксируются прежний и новый авторы;
- не позволять произвольные table/column names или произвольный SQL через generic correction API.

Текущая запись `admin.*` в DomainEvent не является достаточной целевой реализацией отдельного security/admin audit.

## 7. Общий DomainEvent contract

Обязательные envelope fields:
- `event_id`;
- `event_type`;
- `event_version`;
- `aggregate_type`, `aggregate_id`;
- `actor_user_id` (nullable только для явно определённых system/migration events);
- `command_id`, `correlation_id`;
- `occurred_at` (DB timestamp);
- `payload` с версионированной схемой;
- `request_id` / parent reference при применимости.

Требования:
- event_type входит в каталог/allowlist;
- payload валидируется по версии схемы;
- PII минимизируется; ФИО и номера карт не копируются в event payload без необходимости;
- события и изменения агрегатов записываются в одной транзакции;
- append-only запрет UPDATE/DELETE сохраняется;
- `request_id` у события связанного fulfillment shipment обязателен и используется только для разрешённой контекстной проекции P-09; он не предоставляет доступ к независимой истории карты или ко всем событиям других агрегатов;
- типы событий жизненного цикла заявки/отправления и их allowlist определены в §7.1; связанные события сохраняют собственный aggregate, не копируются как вторые записи в родителя;
- consumers должны быть идемпотентными и поддерживать переходные версии событий;
- admin/security audit не смешивается с операционной историей DomainEvent.

### 7.2. Контракт чтения и авторизации связанных объектов

Read-side endpoints и запросы карточек не являются DB-командами изменения состояния, но обязаны применять тот же принцип deny-by-default и актуальную серверную авторизацию до возврата чувствительных полей. Разрешения проверяются отдельно для каждого целевого агрегата; доступ к исходному объекту или наличие FK/ссылки не передаёт разрешение связанному объекту.

Разделяются три независимых права:

1. **Shipment manifest:** чтение полного манифеста конкретного отправления, включая номера карт и ФИО, доступно только его отправителю и получателю на всех этапах активного отправления и после полной приёмки согласно D-09/P-08. Неучастник не получает доступ по знанию shipment ID.
2. **Shipment card/timeline:** отправитель и получатель сохраняют постоянный read-only доступ к карточке конкретного shipment, его route-specific manifest и истории после `received`. Это право относится только к самому shipment и его неизменяемым снимкам/событиям.
3. **Standalone card/box/timeline:** самостоятельная карточка и история карты или коробки доступны только при наличии отдельного разрешения в текущей области объекта и с учётом текущего custody/state. Участие в shipment, чтение P-09 или наличие объекта в manifest само по себе не предоставляет такое разрешение. Для исходного филиала действует D-08: история карты прекращается после её передачи в архив.

Для P-09 до `submitted` draft и его история доступны только автору. После `submitted` состав и request-scoped timeline доступны сотрудникам той же локации ЦО в режиме чтения; это не открывает самостоятельную карточку/историю карт. Архивные сотрудники получают доступ к P-09 и картам в пределах действующего archive processing/custody scope. После handover archive → CO участники продолжают видеть shipment, manifest и shipment timeline, но самостоятельная карточка карты не открывается через P-09/shipment-ссылку, если у них нет отдельного актуального разрешения.

Для обычных branch/CO → archive манифест содержит только коробки. После handover и receipt отправитель сохраняет shipment/manifest/timeline access, но не получает через shipment-ссылку доступ к самостоятельной карточке коробки, её циклу или картам внутри. Архив открывает коробку и её содержимое в своей области после полной приёмки.

Обязательные свойства read path:
- авторизация выполняется сервером для каждого прямого ID/URL/API-запроса; UI hide/show — только presentation;
- проверка выполняется до сериализации/возврата PII, event payload, связанных объектов и счётчиков;
- ссылки, поиск, autocomplete, pagination, экспорт и вложенные API не расширяют scope;
- доступ к P-09 timeline строится только по разрешённому allowlist событий; `request_id` не является grant на события карты или других агрегатов;
- неизвестный и недоступный объект не должны различаться ответом, раскрывающим существование/чувствительные поля;
- replay сохранённого результата команды не обходит актуальную read authorization: после деактивации/отзыва scope чувствительный сохранённый payload не выдаётся без действующего права чтения.

Это read-side contract; он не добавляет бизнес-команд, не меняет custody и не создаёт новые роли.

## 8. Идемпотентность и ошибки

- У каждой изменяющей команды есть `command_id`.
- Повтор того же command_id с теми же параметрами возвращает первоначальный результат.
- Повтор с тем же command_id и другими параметрами — конфликт.
- Команда, уже применённая другим command_id, не должна повторно менять состояние; возвращается корректный `already_applied` или `invalid_state`.
- Ошибки валидации не оставляют частичных изменений.
- Техническая ошибка/serialization failure допускает повтор всей транзакции только при наличии безопасного idempotency key.

## 11. Утверждённый idempotency contract (2026-11-18)

Этот раздел конкретизирует пункты разделов 8–9. Все четыре положения подтверждены владельцем продукта 2026-11-18 как обязательный технический стандарт МедАрхива. Это утверждение проектного контракта, не разрешение на реализацию.

### 11.1 Генерация command_id и повтор

- Для пользовательской команды клиент создаёт UUID v4 один раз при подтверждении действия и сохраняет его до получения терминального ответа. Сетевой retry, повтор отправки после timeout и восстановление запроса используют тот же command_id.
- Любое новое намерение пользователя, изменённый состав/параметры или новая попытка после полученного бизнес-отказа получает новый command_id.
- Для внутренних system jobs command_id создаёт доверенный server-side caller до первого вызова и сохраняет его при retry.
- command_id глобально уникален в пределах одной базы/среды; не включать actor_id в пространство уникальности вместо проверки совпадения владельца команды.

### 11.2 Canonical input и hash

Hash вычисляется только сервером/защищённой DB-командой после разбора входа по конкретной command schema. Клиентский hash не принимается.

Рекомендуемый алгоритм:
1. Валидировать command_type и command_version по allowlist.
2. Построить semantic input object только из полей, влияющих на результат команды. Transport headers, request timestamp, retry count, trace/span IDs и correlation_id не включать.
3. Применить schema-specific normalization: UUID привести к lowercase canonical form; даты/время — к UTC и единому формату; числовые значения — к однозначному представлению; применить defaults до hashing; определить для каждого поля, различаются ли absent и null.
4. Для object keys использовать стабильную сортировку; строки сериализовать в UTF-8 с фиксированными правилами escaping. Unicode normalization и trim не применять глобально: только если это прямо определено семантикой конкретного поля.
5. Массивы сохранять в исходном порядке, если порядок семантически значим; сортировать и дедуплицировать только для schema-полей, определённых как mathematical set (например, набор card IDs в команде, где порядок не влияет на manifest).
6. Вычислить SHA-256 от domain-separated bytes, включающих canonicalization version, command_type, command_version, actor_user_id и canonical semantic input. Пример логической структуры: medarchive-command\ncanon-v1\n<command_type>\n<command_version>\n<actor_uuid>\n<canonical-json>.

Отдельно хранить canonicalization_version. При изменении алгоритма не переинтерпретировать старые hashes; повтор существующего command_id сравнивается по сохранённой версии canonicalization.

### 11.3 Корреляция

- command_id — ключ идемпотентности одной команды.
- correlation_id — идентификатор более широкой бизнес-операции/цепочки команд; он может охватывать несколько command_id.
- correlation_id не влияет на input_hash. При replay возвращаются исходные command_id/correlation_id и сохранённый результат; новое trace ID не меняет семантику команды.
- request_id остаётся transport/request reference и не заменяет command_id или correlation_id.

### 11.4 Транзакционный протокол и конкурентный retry

- Ledger row, aggregate mutations, DomainEvent, admin/security audit и typed result commit-ятся одной транзакцией.
- Уникальный PK по command_id; конкурентная регистрация выполняется через INSERT ... ON CONFLICT DO NOTHING либо эквивалентный механизм, не оставляющий транзакцию в aborted state после ожидаемого конфликта.
- Конкурентный запрос с тем же command_id ждёт завершения первой транзакции. После её commit он читает ledger: совпавший actor/type/version/hash возвращает сохранённый результат; несовпадение — idempotency_key_reused без выполнения команды.
- Незавершённый ledger row не должен быть видим как committed in_progress. Временное состояние допустимо только внутри незавершённой транзакции; при crash/rollback исчезают и ledger row, и все бизнес-эффекты.
- После нахождения существующей записи повторно не выполнять мутацию. Перед выдачей сохранённого результата повторно проверить, что actor существует и активен; если результат содержит чувствительные данные — дополнительно проверить актуальное право прочитать эти данные. Повтор не должен раскрывать результат деактивированному/лишённому полномочий пользователю.

### 11.5 Какие отрицательные результаты сохранять

Рекомендуемое разделение:

| Ситуация | Записывать завершённую ledger запись? | Поведение retry |
|---|---|---|
| Невалидный envelope, неизвестный command type/version, отсутствующий/неактивный actor | Нет | Повторная проверка; security/diagnostic log отдельно по политике |
| Отказ аутентификации/авторизации или scope (forbidden) | Нет | Повторная проверка актуальных полномочий; не кэшировать отказ как бизнес-результат |
| Детерминированный бизнес-результат после успешной авторизации: not_found, invalid_state, conflict, validation_error | Да | Тот же ключ возвращает тот же отказ; новое намерение/повтор после изменения состояния — новый command_id |
| Успешная команда / подтверждённый already_applied в рамках конкретного idempotency contract | Да | Возвращается исходный сохранённый result envelope |
| Deadlock/serialization failure, timeout, connection loss до подтверждённого commit, internal error | Нет, транзакция откатывается | Повторить всю команду с тем же command_id; если commit мог завершиться, сначала проверить ledger |

Не следует сохранять transient infrastructure errors как терминальный результат. Для отказа авторизации отдельно сохранять минимальный security audit факт, но не копировать его в бизнес DomainEvent.

### 11.6 Result envelope и API mapping

Сохранять стабильные поля: result_code, result_version, result_payload, completed_at. Payload ограничен схемой конкретной команды и не содержит лишних PII/секретов. В envelope также возвращать command_id, correlation_id и ссылки на созданные aggregate/event IDs, если они нужны клиенту.

HTTP mapping остаётся responsibility API adapter, не DB command: успешный original/replay result сохраняет один semantic outcome; DB не возвращает SQLSTATE, имена constraints или внутренний текст исключения. Для idempotency_key_reused использовать явный conflict outcome.

### 11.7 Retention и защита от повторного исполнения после очистки

- Для необратимых логистических и административных команд command identity/tombstone хранить не меньше срока authoritative history; предпочтительный baseline — не удалять ключи необратимых действий, а минимизировать payload результата.
- Для обычных (обратимых) команд срок хранения записи идемпотентности составляет **90 календарных дней после завершения команды**. По истечении срока запись может быть очищена автоматической процедурой; очистка не затрагивает authoritative business records, DomainEvent и audit records.
- Для необратимых логистических и административных команд command identity/tombstone сохраняется бессрочно; при необходимости очистки result payload сохраняются `command_id`, actor, command_type/version, input_hash, canonicalization_version, завершённый result_code и ссылки на authoritative records. Удаление tombstone запрещено.
- Очистка обычных записей не должна затрагивать незавершённые транзакции или записи моложе 90 дней. Процедура должна быть ограниченной по объёму и безопасной при параллельной работе; точный operational schedule и backup interaction специфицируются до реализации.

### 11.8 Утверждённый технический стандарт (2026-11-18)

Владелец продукта подтвердил все четыре положения как обязательный технический стандарт:

1. **Lifecycle ключа:** клиент создаёт UUID v4 один раз при подтверждении пользовательского действия и сохраняет его до терминального ответа. Все сетевые повторы, timeout retries и восстановление запроса используют тот же `command_id`. Новое пользовательское намерение или изменённые параметры получают новый ключ.
2. **Canonicalization и hash:** canonical input строится только на сервере по конкретной command schema; используется schema-specific normalization и SHA-256. В записи сохраняется `canonicalization_version`; старые hashes не переинтерпретируются при изменении алгоритма.
3. **Replay policy:** успешные результаты и детерминированные бизнес-отказы после успешной аутентификации/авторизации сохраняются и возвращаются при повторе того же ключа. Authentication/authorization failures и transient infrastructure errors не сохраняются как завершённые результаты команды.
4. **Retention/tombstone:** ключи необратимых логистических и административных операций не удаляются. При очистке result payload сохраняется tombstone с идентификатором команды, actor, типом/версией команды, input hash, версией canonicalization, result code и ссылками на authoritative records. Для обычных команд срок хранения записи идемпотентности — 90 календарных дней после завершения команды; затем запись может быть очищена. Это не распространяется на authoritative business records, DomainEvent и audit records.

Дополнительные обязательные ограничения:
- `command_id` глобально уникален в пределах базы/среды; совпадение ключа с другим actor/type/version/hash приводит к `idempotency_key_reused`, без повторного исполнения.
- `correlation_id` не входит в input hash и связывает несколько команд одной бизнес-операции.
- Ledger, изменения агрегатов, DomainEvent, необходимые admin/security audit записи и результат команды фиксируются одной транзакцией.
- Replay не повторяет мутацию; перед возвратом результата повторно проверяются активность actor и актуальное право читать содержащиеся в результате чувствительные данные.
- Детерминированные бизнес-отказы сохраняются только после успешной авторизации. Ошибки envelope/identity/access и временные инфраструктурные ошибки не превращаются в терминальные бизнес-результаты.

Владелец продукта утвердил 90 календарных дней после завершения команды для обычных команд. До реализации всё равно требуется проверить, что retry horizons фактических клиентов/jobs не превышают этот срок, а также определить безопасный bounded cleanup и его взаимодействие с backup/restore. Если inventory обнаружит retry horizon более 90 дней, это будет техническим конфликтом, который необходимо вынести на отдельное согласование, а не молча менять срок.


### 11.9 Authoritative event and audit ownership (technical contract)

The two append-only stores have distinct authority; they are not duplicate copies of one event stream:

- **DomainEvent** is authoritative for the business fact and aggregate state transition, including a correction to card, custody, BoxCycle, BoxPlacement, shipment or archive-request domain state.
- **AdminSecurityAudit** is authoritative for the privileged/security action: authenticated admin actor, action/command, mandatory reason, authorization/outcome, target aggregate, and references to the resulting DomainEvent and command/correlation IDs.
- A P-07 command that changes a business aggregate writes one typed DomainEvent and one linked AdminSecurityAudit record in the same transaction. The audit record does not duplicate the full business before/after payload; it contains only allowlisted security context and references. DomainEvent does not become the global admin/security feed.
- Pure admin CRUD and authentication/authorization/security events write AdminSecurityAudit only; they do not create a business DomainEvent unless a future explicitly approved domain event is required for a separate aggregate.
- If either required write fails, the entire privileged mutation rolls back. No success response may be returned for a partially audited correction.


### 2.11 `shipment_reassign_draft_author`

**Назначение:** восстановить возможность завершить черновик, если его первоначальный автор деактивирован до фактической передачи. Команда применяется к обычным черновикам branch → archive и central_office → archive, а также к fulfillment-черновику archive → central_office по P-09.

**Actor:** только активный `admin`.

**Вход:** `shipment_id`, `new_author_user_id`, idempotency metadata.

**Предусловия:**
- shipment находится в `draft`; фактическая передача не подтверждена;
- текущий автор деактивирован;
- новый автор активен;
- новый автор принадлежит той же отправляющей локации, что и shipment (для fulfillment — той же archive location); роль нового автора соответствует отправляющей локации;
- shipment и его текущий автор доступны для административной операции.

**Атомарные изменения:**
- заменить только текущий `author_user_id`/поле авторства черновика на нового автора;
- сохранить исходного создателя неизменяемым в событии создания и не переписывать исторические actor;
- записать отдельное append-only событие `shipment.draft_author_reassigned` с admin actor, прежним автором, новым автором и временем.

**Не изменяются:** маршрут, состав и manifest snapshot, parent P-09 link, назначение курьера, courier FK/snapshot, состояние карт и ответственность за них.

**Права нового автора:** все права автора черновика для соответствующего маршрута, в том числе редактирование состава, если оно допускается текущей фазой обычного отправления, замена курьера и подтверждение фактической передачи. Право не распространяется на изменение уже зафиксированного P-09 состава.

**Запрет:** переназначение, если исходный автор активен; назначение неактивного сотрудника или сотрудника другой локации/роли; переназначение после handover; повторная передача авторства без нового основания; выполнение handover администратором вместо назначенного автора. Операция не отменяет и не создаёт отправление.


## 2.12. Обычные отправления коробок: branch → archive и central_office → archive

Обе команды используют одинаковый lifecycle `draft → in_transit → received`; различается только отправляющая локация. Манифест содержит только коробки, не карты. Курьер обязателен при создании черновика.

### `shipment_create_draft`
**Actor:** активный сотрудник отправляющей локации (branch либо central_office) с правом создавать отправления в своём scope.
**Вход:** маршрут, непустой набор уникальных `box_id`, активный `courier_id`, idempotency metadata.
**Предусловия:** у actor нет другого незавершённого черновика обычного отправления; каждая коробка принадлежит отправляющей локации, имеет допустимый активный BoxCycle и непустой состав; коробка не включена в другое активное отправление; курьер активен; все объекты доступны actor.
**Атомарные изменения:** создать shipment `draft`, сохранить текущего автора, маршрут, коробочный manifest и назначение курьера (FK + snapshot ФИО). Записать `shipment.draft_created` с actor/time. Само создание не меняет custody, location или состояние карт.

### `shipment_edit_draft_manifest`
**Actor:** только текущий автор активного черновика.
Добавление/удаление/замена коробок допускается только в `draft`; все коробки повторно проверяются по доступности, принадлежности, непустому циклу и отсутствию в другом активном shipment. Хранится только актуальный состав черновика; история редактирования состава не ведётся. Изменение manifest и проверки выполняются атомарно.

### `shipment_change_draft_courier`
**Actor:** только текущий автор активного черновика.
До handover можно заменить назначение на любого другого активного курьера общего справочника. FK и snapshot ФИО обновляются атомарно; история предыдущих назначений не ведётся. Уже назначенный курьер, деактивированный после назначения, не блокирует handover; повторная замена на неактивного курьера запрещена.

### `shipment_confirm_handover` для обычного отправления
**Actor:** только текущий автор черновика, активный и имеющий полномочия в отправляющей локации. После административного переназначения авторства это новый текущий автор; admin не подтверждает передачу вместо него.
**Предусловия:** shipment `draft`; назначенный courier FK/snapshot существует; полный manifest коробок целостен; каждая коробка и цикл всё ещё относятся к отправляющей локации и не конфликтуют с другим shipment; handover ранее не выполнялся.
**Атомарные изменения:** shipment `draft → in_transit`; записать `shipment.handed_over` с handover actor/time и неизменяемым snapshot полного списка коробок; установить shipment custody для коробок и содержащихся карт без изменения состава коробок. Ответственность переходит назначенному курьеру. После commit manifest и courier assignment неизменяемы.

### `shipment_receive_all` для входящего обычного отправления
**Actor:** любой активный сотрудник archive с полномочиями приёмки в целевой archive location; не обязательно сотрудник, создавший/обрабатывавший отправление.
**Предусловия:** shipment `in_transit`, маршрут заканчивается в archive, приёмка ранее не выполнялась. Приёмка подтверждает получение коробок как целых логистических единиц; сотрудник не сверяет количество карт внутри и не перечитывает их манифест.
**Атомарные изменения:** shipment `in_transit → received`; записать `shipment.received` с receipt actor/time и snapshot списка коробок; custody/location коробок и карт переходит архиву. Одна полная операция для всего shipment.

### Отмена и повторные команды
Только текущий автор может отменить `draft` без причины. Отмена не допускается после `in_transit`. Изменение manifest/courier после handover запрещено. Handover и receipt сериализуются блокировкой shipment; после успешной первой команды повтор с новым command_id отклоняется как `invalid_state`/`already_applied` без повторного бизнес-события. Retry с тем же command_id возвращает сохранённый результат по общему idempotency contract. Любая ошибка до commit откатывает все связанные изменения и события.


### 2.13. Сквозные переходы коробочного отправления и карты в составе коробки

Для обычных маршрутов branch → archive и central_office → archive manifest shipment состоит из коробок (`ShipmentBox`), а не из отдельных карт. На handover shipment `draft → in_transit`; custody коробок и всех карт, входящих в их текущие BoxCycle, переходит назначенному курьеру. Состав BoxCycle и активные memberships не закрываются и не пересоздаются: передача коробки не является распаковкой/перегруппировкой. Для этих карт не создаются `ShipmentCard`, P-09 item или индивидуальный `current_shipment_id`.

На полной приёмке shipment `in_transit → received` custody и учётная локация коробок и всех карт внутри них атомарно переходят архиву. Активные memberships и BoxCycle сохраняются. Receipt не назначает полочное место: `BoxPlacement` создаётся отдельной операцией размещения. Нельзя считать отдельную карту принятой независимо от коробки.

Это отличается от P-09 archive → central_office: там manifest состоит из отдельных `ShipmentCard`, а позиции P-09 и `current_shipment_id` переходят `extracted → in_shipment` только при handover.

### 2.11. Резервирование карты за незавершённой P-09

Резервирование карты не определяется только статусом позиции. Любая позиция актуального состава удерживает `reservation_active = true` на всём протяжении жизни родителя в `draft`, `submitted` или `processing`, включая результаты `removed_by_archive` и `not_found`. Это предотвращает включение одной карты в параллельную заявку, пока архив ещё обрабатывает её исходную заявку.

Снять резервирование разрешено только:
- при удалении позиции из draft автором ЦО (перевод в audit tombstone `removed_by_central_office`);
- при атомарном переводе родителя в `completed` или `cancelled` — для всех его позиций.

Создание новой P-09 проверяет резервирование и пытается установить его под защитой уникального ограничения по `card_id`. Предварительная проверка без уникального ограничения не считается достаточной. При гонке двух заявок только одна транзакция может получить резервирование; другая откатывается без частично созданной заявки/позиции. Команды отмены/завершения родителя блокируют parent и позиции и снимают резервирование в той же транзакции, что и terminal transition.


### 11.10 Обязательные события и отказ при недоступности audit/event storage (2026-11-21)

Для любой команды, меняющей состояние и требующей по своему контракту обязательный `DomainEvent` и/или `AdminSecurityAudit`, бизнес-изменение, все обязательные записи событий и сохранённый результат команды входят в одну транзакцию. Ошибка записи любой обязательной записи означает rollback всей транзакции: нельзя фиксировать изменение без требуемой истории или audit evidence. Если privileged correction требует оба класса событий, оба сохраняются атомарно с изменением агрегата; AdminSecurityAudit ссылается на бизнес-событие и не дублирует его полный payload.

Правило распространяется на значимые бизнес-команды по картам, коробкам, отправлениям и архивным заявкам, а также на privileged administrative mutations. Успешная аутентификация не приводит к выдаче сессии до успешного commit обязательной записи `authn.login_succeeded`; при ошибке записи новая сессия не выдаётся. Обычные read-only запросы автоматически не блокируются из-за недоступности audit storage. Каждый отказ 401/403 не обязан создавать синхронную durable запись. Routine authorization denials не записываются в основной бизнес-журнал и не порождают обязательную отдельную audit-запись на каждую попытку. Для явно выбранных high-risk случаев или threshold crossings допускается отдельная restricted security telemetry; повторные отказы группируются/агрегируются, а частота и объём ограничиваются. Запись telemetry — best-effort: её недоступность или ошибка не блокирует запрос и не меняет результат авторизации. Сам отказ остаётся отказом. Это утверждённое поведение; технические параметры telemetry должны быть специфицированы до реализации, реализация/DDL не разрешены.


## AdminSecurityAudit read authorization — approved product rule (2026-11-21)

The global `AdminSecurityAudit` feed and event-detail read surfaces are restricted to active actors with role `admin`. Actors with roles `branch`, `central_office` or `archive` must not receive the feed or event payload through UI, direct URL, API, search, filters or any alternate read path. Enforce authorization server-side before event payload serialization; UI visibility is not an authorization control. Even authorized admins receive only explicitly allowlisted fields: credentials, passwords, tokens and unnecessary personal data are prohibited. Feed/detail reads are not themselves logged. Export of the `AdminSecurityAudit` feed remains prohibited. This is a product-level access decision; implementation and tests are not authorized yet.


### 2.14. Корректировка ошибочного перемещения коробки между архивными полками

Ошибочное перемещение не отменяется удалением или редактированием первоначального события/размещения. Для исправления предусмотрена отдельная корректирующая команда, которая сохраняет первоначальный факт и создаёт самостоятельное событие корректировки с исполнителем и датой/временем. Команда проверяет актуальное действующее размещение, фактическое положение коробки, активность целевой полки и её принадлежность той же архивной области, полномочия и scope исполнителя, а также отсутствие конфликтующих операций. Возврат на прежнюю полку допустим только если подтверждено, что коробка физически находится там и это не переписывает последующее реальное перемещение. Если коробка физически находится в другом месте, нельзя автоматически восстановить прежнее размещение: требуется отдельное явно подтверждённое действие, соответствующее фактическому положению. Изменение действующего размещения и обязательное событие корректировки атомарны. Состав коробки, BoxCycle, memberships, custody и учётная локация не меняются. Первоначальная запись размещения и событие перемещения остаются неизменными. Причина корректировки обязательна и передаётся как код из закрытого перечня; свободный комментарий не требуется. Конкретные коды причин и полномочие исполнителя должны быть определены в техническом контракте до реализации. Команда применяется только к одной коробке; массовая корректировка нескольких коробок одной командой не поддерживается.
### 2.15. Запрет перемещения коробки между полками при незавершённой заявке ЦО → Архив

Команда перемещения коробки между архивными полками отклоняет операцию, если коробка включена в незавершённую заявку ЦО → Архив. Сервер проверяет актуальное участие коробки в заявке и её состояние непосредственно при выполнении команды; клиентский статус или предварительная проверка не являются достаточными. Проверка заявки/состава и изменение BoxPlacement с записью обязательного события должны быть согласованы транзакционно и защищены от гонок с изменением состава или завершением заявки. После завершения заявки запрет по этому основанию снимается; остальные проверки полномочий, scope, фактического размещения и целевой полки продолжают действовать. Это ограничение относится к перемещению между архивными полками и само по себе не меняет правила иных операций с коробкой.
### 2.16. Корректировка фактического размещения коробки при незавершённой заявке ЦО → Архив

При активном запрете обычного перемещения коробки, участвующей в незавершённой заявке ЦО → Архив, отдельная защищённая корректирующая команда может изменить её фактическое размещение только для исправления подтверждённого физического положения. Команда не является обходом запрета для планового перемещения. Обязательны код причины из закрытого перечня и отдельное событие; свободный комментарий не требуется. Сервер проверяет специальное полномочие и scope исполнителя, актуальное участие коробки в заявке, фактическое положение коробки, активность и принадлежность целевой полки той же архивной области и отсутствие конфликтующих процессов. Команда не меняет shipment manifest, состав/состояние/историю заявки, handover/receipt, custody, состав коробки, BoxCycle, memberships или учётную локацию. Проверки и изменение действующего BoxPlacement вместе с обязательным событием выполняются атомарно; конкурентные изменения заявки, состава и размещения не должны позволять обойти проверки. Команду вправе выполнять только активный сотрудник архива с отдельным специальным полномочием на корректировку в пределах своего scope. Обычного `box_place` недостаточно; роль администратора сама по себе такого права не предоставляет. Сервер проверяет активность учётной записи, роль `archive`, отдельное специальное полномочие и scope при выполнении команды. Закрытый перечень кодов причин определяется до реализации.




Поиск начинается с фамилии. Запрос только по имени или отчеству (например, «Иван» или «Петрович») не выполняет поиск и не должен возвращать карты. Допустимы фамилия или фамилия с последующими частями ФИО; каждая введённая часть сопоставляется с начала соответствующего слова.


**Поведение интерфейса поиска:** результаты обновляются автоматически после изменения поискового ввода с небольшой задержкой (debounce), без обязательного нажатия кнопки «Найти». Запрос должен начинаться с фамилии; при каждом новом вводе предыдущий ожидающий запрос отменяется или его устаревший ответ игнорируется, чтобы результаты соответствовали последнему значению поля. Серверная авторизация и правила поиска применяются при каждом запросе.


## 2026-11-21 — сохранение поиска при возврате из карточки медицинской карты

Утверждено владельцем продукта: если сотрудник открывает карточку медицинской карты из результатов поиска и возвращается назад, система сохраняет поисковый запрос и состояние списка результатов, чтобы не требовалось выполнять поиск заново. При восстановлении списка сохраняются введённый запрос, позиция/состояние списка и ранее полученные результаты; при этом данные и доступность результатов не считаются бессрочно разрешёнными: серверные права, scope и актуальность доступа должны быть повторно проверены перед повторным показом или использованием сохранённых результатов. Если доступ изменился, недоступные записи и поля не показываются. Возврат не должен запускать неожиданный поиск по устаревшему вводу или позволять позднему ответу перезаписать актуальное состояние. Реализация не разрешена.


## 2026-11-21 — сортировка результатов поиска медицинских карт

Утверждено владельцем продукта: результаты поиска медицинских карт отображаются в алфавитном порядке по полному ФИО — фамилия, имя, отчество. Для однозначного и стабильного порядка записей с одинаковым ФИО применяется дополнительная сортировка по номеру медицинской карты. Сортировка не расширяет набор доступных результатов и применяется только после серверной проверки действующих прав, scope и доступности полей. Реализация не разрешена.


## 2026-11-21 — визуальное выделение совпадений в ФИО

Утверждено владельцем продукта: в результатах поиска визуально выделяются совпавшие части ФИО, соответствующие введённым компонентам поискового запроса. ## Дополнение — ручное создание медицинской карты

Решение утверждено 2026-11-21. При ручном создании карты обязательны `card_number`, `full_name` и `date_of_birth`; `phone` необязателен. `card_number` — уникальный внешний идентификатор: повторное создание записи с уже существующим номером запрещено и должно обрабатываться как конфликт/предложение открыть существующую карту, без создания дубля. До создания система выполняет проверку возможных совпадений по ФИО. Совпадение ФИО не является уникальным ограничением и не блокирует создание: сотрудник проверяет найденные самостоятельные карты и явно подтверждает создание отдельной карты, если это другая медицинская карта. Автоматическое объединение записей запрещено. Эти правила применяются также к сценарию создания карты непосредственно при добавлении в коробку. Создание и добавление остаются одной пользовательской последовательностью, но отдельными защищёнными командами/изменениями с атомарностью добавления.

## Решение от 2026-11-22 — полномочия на исправление данных медицинской карты

Полномочие не предоставляется сотрудникам автоматически по роли или подразделению. Активный администратор может назначить или отозвать `card_correct` у другого сотрудника; назначать это полномочие самому себе администратор не может. Назначение/отзыв выполняется только для активной учётной записи, с проверкой целевой роли и состояния, и обязательно фиксируется в `AdminSecurityAudit`. Роль администратора сама по себе не даёт `card_correct`: администратор получает его только если другой активный администратор назначил это полномочие. Все требования к причине исправления, сохранению старых/новых значений, автора и времени, неизменности номера карты и append-only истории сохраняются. Реализация не разрешена.

Новый номер должен сохранять глобальную уникальность; если он уже принадлежит другой карте, операция отклоняется и объединение/перенос номера автоматически не выполняются. Исходный номер и история его использования не удаляются и не переписываются. Конкретное отдельное полномочие и круг сотрудников, которым оно может назначаться, подлежат отдельному проектному решению. ## Проектный контракт — списание медицинской карты (P-04/D-13)

Процесс состоит из двух отдельных действий: `ЦО → запрос на списание` и `архив → проверка и исполнение`. При создании запроса указываются карта и обязательная причина. Исполнить списание может только активный уполномоченный архивный сотрудник после проверки основания. Успешное исполнение меняет статус карты на «Списана» и фиксирует отдельное append-only событие с actor/time. Запись карты, исходные данные и история не удаляются и не переписываются. Branch и admin не имеют права инициировать или исполнять списание. Имена конкретных DB-команд, модель запроса, закрытый список оснований/документов, точные preconditions и обработка отказа будут определены в последующей технической детализации; этот контракт не разрешает физическое удаление.


## Решение от 2026-11-22 — порядок списания медицинской карты (P-04/D-13)

Владелец продукта подтвердил следующий процесс списания медицинской карты:

1. Центральный офис (ЦО) инициирует запрос на списание конкретной медицинской карты и указывает обязательную причину.
2. Архив проверяет карту и основание запроса.
3. Списание выполняет уполномоченный активный сотрудник архива после проверки.
4. После успешного списания карта получает статус «Списана» и больше не участвует в обычных операциях.

Физическое удаление записи медицинской карты запрещено. Сохраняются сама запись, прежние данные, история перемещений и события; факт списания фиксируется отдельным событием с автором и временем. Филиал и администратор не инициируют и не исполняют списание; ЦО инициирует, архив исполняет. Это решение утверждает общий бизнес-порядок, но не определяет пока закрытый перечень оснований/документов, точные проверки допустимости, возможность и порядок отказа по запросу, а также детальную модель состояний и команд — эти технические детали будут проработаны без изменения утверждённого распределения ролей. Реализация не разрешена.
