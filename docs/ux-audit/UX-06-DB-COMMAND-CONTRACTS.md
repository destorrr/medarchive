# UX-06 — контракты защищённых DB-команд для заявок, отправлений и хранения

Дата: 2026-11-18  
Статус: проектная спецификация, не реализация  
Основа: принятые D-01…D-18, P-01…P-09 и DB-SEC-01…04; статическая инвентаризация текущего PostgreSQL кода.

## 1. Общие требования к каждой команде

Все команды выполняются одной транзакцией PostgreSQL. Runtime вызывает только разрешённые функции/процедуры; прямые INSERT/UPDATE/DELETE критичных таблиц после cutover запрещены.

### 1.1 Общий envelope

Каждая команда получает:
- `p_actor_user_id` — UUID пользователя, аутентифицированного application layer;
- `p_command_id` — UUID команды для идемпотентности;
- `p_correlation_id` — UUID бизнес-операции/сквозной трассировки;
- бизнес-параметры команды;
- при необходимости `p_reason` / `p_comment`.

Actor trust соответствует DB-SEC-01: БД проверяет, что пользователь существует, активен и имеет допустимую роль/branch scope; это не независимое криптографическое доказательство личности.

DB boundary обязан проверять:
1. actor существует и активен;
2. actor role и область полномочий соответствуют операции;
3. объект и связанные объекты доступны actor по серверному scope;
4. исходный статус и все предусловия;
5. уникальность `command_id` в пределах идемпотентного журнала;
6. бизнес-инварианты независимо от UI.

Возвращать типизированный результат: `success`, `already_applied`, `not_found`, `forbidden`, `invalid_state`, `conflict`, `validation_error`. Внутренние SQL детали не раскрывать пользователю.

**Обязательный формат результата (утверждён 2026-11-20):** каждая публичная DB-команда возвращает единый versioned JSONB envelope:

```json
{
  "result_code": "success",
  "result_version": 1,
  "result_payload": {},
  "command_id": "uuid",
  "correlation_id": "uuid",
  "completed_at": "database timestamp"
}
```

- `result_code` выбирается из закрытого allowlist конкретной команды/семейства команд.
- `result_version` версионирует схему `result_payload`.
- Для каждой команды документируется строгая схема и validator payload; произвольный JSON, ORM-объекты и SQL-диагностика запрещены.
- В payload возвращаются только минимально необходимые стабильные идентификаторы/состояния; PII — только при необходимости API use case и наличии актуального права чтения.
- Command ledger сохраняет точный committed envelope; replay возвращает первоначальный семантический результат, а не пересчитывает текущее состояние.
- HTTP status и публичное тело ответа формирует API adapter по отдельной спецификации. SQLSTATE, имена constraints и тексты исключений не входят в публичный envelope.
- Внутренние высокочастотные SQL-функции могут использовать фиксированные типизированные scalar returns, но внешний контракт DB-команд остаётся единым envelope.

### 1.2 Общая транзакционная последовательность

1. Проверить синтаксис и допустимость command envelope, нормализовать вход и вычислить серверный input hash. Найти/попытаться зарегистрировать `command_id` под уникальным ограничением. При существующем committed ключе перейти в **отдельную replay-ветку §1.4**, не продолжая бизнес-шаги 2–10. При конкурентном незавершённом insert дождаться исхода транзакции; при rollback повторить регистрацию, при commit — проверить ключ и replay по §1.4. Не сохранять committed `in_progress` без отдельного recovery-протокола.
2. Только для новой команды заблокировать principal actor и используемые role/location membership записи; при необходимости — principal текущего автора/целевого пользователя, в стабильном порядке UUID.
3. Заблокировать корневой агрегат (parent request либо shipment/box/cycle/card/admin entity).
4. Заблокировать карты в сортированном порядке UUID.
5. Заблокировать коробки, циклы, membership и placements в стабильном порядке.
6. Заблокировать/проверить shipment и manifest, если затрагиваются.
7. Повторно проверить активность, роль, scope, состояние и все предусловия после получения блокировок.
8. Выполнить все изменения состояния.
9. Записать DomainEvent и необходимые admin/security audit entries.
10. Сохранить результат команды для безопасного повтора и commit; любая ошибка до commit откатывает все изменения.

Общий lock order: сначала строки авторизационного контекста (пользователь и активные role/location membership, UUID по возрастанию), затем корневой агрегат и связанные ресурсы в зафиксированном для семейства команд порядке. Для обычных коробочных/карточных операций после parent request блокируются cards sorted → boxes/cycles/memberships/placements sorted → shipment/manifest. **Специальный порядок P-09** для `request_cancel`, `request_create_fulfillment_draft` и `request_handover` определён в §§2.7–2.9 и DB-73: parent → shipment (если существует) → request items в стабильном порядке → cards/memberships/boxes. Этот P-09 порядок является явным исключением из общего порядка выше и обязателен для всех конкурирующих команд, затрагивающих P-09. Для операций без заявки после авторизационного контекста использовать соответствующий корневой агрегат (shipment, box/cycle, card или admin entity) и не нарушать единый порядок связанных ресурсов. Если команда зависит от авторства черновика или другого пользователя, блокировать и повторно проверять также его principal/membership в том же порядке UUID.

### 1.3 Сериализация полномочий и деактивации

Проверка active/role/location только до получения блокировок недостаточна: деактивация пользователя или отзыв его membership могут конкурировать с уже начатой бизнес-командой.

Обязательный протокол:
- В той же транзакции заблокировать строку пользователя и все используемые для решения доступа активные role/location membership записи через FOR UPDATE, в стабильном порядке UUID.
- Повторно проверить после блокировки, что actor активен, его роль и membership действуют, а требуемая локация совпадает с объектом и операцией.
- Для команд, право которых зависит от текущего автора черновика, заблокировать и проверить также principal/membership текущего автора; для admin reassignment — principal/membership нового автора.
- Команды admin deactivation и изменения role/location membership используют те же строки и тот же порядок блокировок. Они не могут завершить отзыв полномочий посреди команды, которая уже получила блокировку; и наоборот, команда, пришедшая после commit деактивации/отзыва, обязана получить отказ.
- Если handover получил блокировку действующего автора первым, он может завершиться до деактивации. Если деактивация/отзыв завершились первыми, handover отклоняется; после этого admin может выполнить отдельное переназначение автора по §2.11. Никакого автоматического переназначения или подтверждения handover администратором нет.
- При повторе idempotency key применяются правила §1.4: сначала проверяются совпадение исходного actor/command/input, затем активность actor и актуальное право читать возвращаемые данные.

Деактивация не переписывает уже совершённые события, назначения курьера, manifest или custody. Этот протокол определяет только то, какая из конкурирующих операций получает право завершиться первой.

### 1.4 Повтор команды и безопасный replay сохранённого результата

Replay — это возврат результата ранее committed команды, а не новое исполнение и не повторная проверка её бизнес-предусловий.

Порядок обработки повторного `command_id`:

1. Найти ledger record по `command_id` и проверить совпадение `command_type`, `command_version` (если введён), исходного `actor_user_id` и серверного `input_hash`. Любое несовпадение возвращает `idempotency_key_reused`/conflict; сохранённый результат не раскрывается.
2. Для точного совпадения повторно проверить, что исходная учётная запись actor существует и активна. Повтор от другой учётной записи не становится допустимым даже при совпадающем payload.
3. Проверить актуальное право этого actor читать каждый объект и каждое чувствительное поле, которое будет включено в replay response. Проверка выполняется по текущим role/location memberships и scope, а не по полномочиям на момент исходной команды.
4. Если actor деактивирован либо актуального права чтения недостаточно, вернуть безопасный `forbidden` или недифференцирующий `not_found` согласно политике нераскрытия объекта. Это отказ только в выдаче replay: исходная ledger record и первоначальный committed result не изменяются и не удаляются.
5. Если проверки пройдены, вернуть сохранённый committed result envelope без повторного изменения агрегатов, повторной записи событий/audit или пересчёта текущего состояния.

**Граница гонки с отзывом прав:** проверка активности actor и текущих read memberships при replay должна быть согласована с тем же протоколом блокировок principal/membership из §1.3, чтобы отзыв прав и выдача сохранённого результата имели определённый порядок. Это не блокировка бизнес-агрегата и не повторное исполнение команды. До выбора транзакционного режима replay и проверки non-disclosure при конкурентном отзыве прав реализация остаётся техническим gate.

Replay не должен требовать, чтобы исходная команда всё ещё была допустима к новому исполнению: например, уже выполненный handover не становится ошибкой при повторе только потому, что shipment теперь находится в `in_transit`. Проверяются identity/контракт команды и актуальная авторизация на чтение ответа, но не текущие бизнес-предусловия исходного перехода. Технический сбой проверки авторизации/чтения не превращается в завершённый ledger outcome и не перезаписывает исходный результат.

## 2. Команды родительской заявки ЦО

Целевая модель — `ArchiveRequest` как родительский aggregate и `ArchiveRequestItem` как отдельные позиции. Это проектная модель P-09; в текущем ORM она ещё не реализована.

### 2.1 `request_create_draft`

**Actor:** `central_office`.

**Вход:** набор уникальных `card_id`, `command_id`, `correlation_id`.

**Предусловия:**
- список непустой, без дубликатов;
- каждая карта существует, активна и доступна ЦО;
- карта не имеет действующего резервирования за другой незавершённой P-09;
- карта находится на балансе ЦО в допустимом состоянии;
- все карты доступны в scope actor.

**Изменения:**
- создать один parent request со статусом `draft`;
- создать по одной позиции `pending` на карту;
- сохранить автора и timestamps.

**Физическое состояние:** не менять Card location, BoxCycle, membership или BoxPlacement.

**События:** `archive_request.created` с parent aggregate и отдельные `archive_request.item_added` для состава; payload ссылается на item/card identifiers без копирования ФИО и других лишних PII.

### 2.2 `request_submit`

**Actor:** только автор черновика `central_office`.

**Вход:** `request_id`, idempotency metadata.

**Предусловия:** request `draft`, есть хотя бы одна активная позиция, позиции всё ещё соответствуют требованиям доступности.

**Изменения:** parent `draft → submitted`, зафиксировать submit actor/time.

**Физическое состояние:** никаких извлечений и перемещений карт.

**Событие:** `archive_request.submitted` с фактическим actor/time.

### 2.3 `request_edit_draft`

**Actor:** только автор черновика `central_office`.

**Вход:** `request_id`, списки add/remove card IDs, idempotency metadata.

**Предусловия:**
- parent находится строго в `draft`;
- actor совпадает с `requested_by`;
- удаляемые позиции принадлежат этому parent;
- добавляемые карты доступны ЦО, не дублируются и не конфликтуют с другими активными заявками.

**Изменения:**
- добавить позиции `pending`;
- удалённые из черновика позиции исключить из актуального состава; при необходимости сохранить audit tombstone `removed_by_central_office` и атомарно снять с них `reservation_active`;
- физически удалять строки и историю запрещено.

**Физическое состояние:** не менять коробки, membership и placements.

**Гонка:** сериализовать по parent request. После успешной отправки любая команда редактирования возвращает `invalid_state`; никакая роль не может менять состав submitted-заявки.

**События:** `archive_request.item_added`, `archive_request.item_removed_by_central_office` (только draft).

### 2.4 `request_start_processing`

**Actor:** `archive`.

**Вход:** `request_id`, idempotency metadata.

**Предусловия:**
- parent `submitted`;
- состав не пуст;
- все активные pending items проверены;
- каждая карта имеет ровно одно ожидаемое активное membership и допустимое архивное положение;
- карты не включены в активное отправление и не имеют несовместимого custody/status;
- archive actor имеет доступ к соответствующему архиву.

**Атомарные изменения:**
1. Заблокировать parent request.
2. Заблокировать все карты и их текущие циклы/членства/размещения в стабильном порядке.
3. Повторно проверить весь состав.
4. Закрыть активные `BoxCardMembership` для всех подлежащих обработке карт.
5. Перевести позиции в `extracted`, сохранить source box/cycle references для истории и возврата.
6. Для каждой коробки, у которой извлечение удалило последнюю активную карту, закрыть `BoxPlacement`; сама коробка остаётся в архивной локации без полочного размещения (D-11/P-06).
7. Parent `submitted → processing`.
8. Записать `archive_request.processing_started` и item-level `archive_request.item_extracted` для каждой автоматически извлечённой позиции; все события содержат фактического actor/time и записываются в той же транзакции.

**Результат по умолчанию:** в этой же атомарной операции каждая позиция получает `extracted`. Это не только физический факт извлечения: для P-09 `extracted` одновременно означает автоматический результат «карта найдена и готова к передаче». Отдельная команда/кнопка подтверждения «Найдена» не предусмотрена. После старта архив фиксирует только исключения, которые заменяют `extracted`: `not_found` или `removed_by_archive`.

**Запрет:** нельзя оставить parent в processing с частично извлечёнными картами. Ошибка любого шага откатывает всю команду.

**Идемпотентность:** повтор с тем же command_id возвращает сохранённый результат; другой command_id при уже processing возвращает `already_applied/invalid_state`, без повторного извлечения.

**Завершение обработки до отправки:** после старта любой активный сотрудник архива с доступом к очереди P-09 и заявке может фиксировать исключения по отдельным позициям; право не закрепляется за сотрудником, который начал обработку. Каждая команда результата — самостоятельная транзакция: результат и событие сохраняются сразу. Если сотрудник прерывает работу, уже зафиксированные результаты остаются сохранёнными, а заявка остаётся в `processing`. **Единственное fulfillment-отправление запрещено создавать, пока не обработаны все позиции заявки.** Каждая позиция должна иметь окончательный результат: `extracted`, `not_found` или `removed_by_archive`. Наличие позиции, результат которой ещё требуется установить или исправить, блокирует создание shipment. После создания shipment draft обработка заявки закрыта: менять результаты, восстанавливать исключения или возвращать карты в рамках этой заявки нельзя.

### 2.5 `request_remove_item`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и данной заявке; не обязательно сотрудник, начавший обработку.

**Вход:** `request_id`, `item_id`, обязательный непустой комментарий, idempotency metadata.

**Предусловия:** parent `processing`, единственный fulfillment shipment по заявке ещё не создан, item `extracted`

**Изменения:**
- вернуть карту в допустимое архивное хранение через помещение в коробку;
- создать/активировать membership в текущем или новом BoxCycle по правилам D-10;
- item → `removed_by_archive`, actor/time; при первой фиксации сохранить обязательный комментарий, при повторной после исправления новый комментарий необязателен. `reservation_active` сохраняется, хотя карта физически возвращена в коробку; новая P-09 на эту карту до завершения/отмены текущей заявки запрещена;
- обновить состояние пустой коробки/placement по правилам операции возврата, не путать с regroup.

**Событие:** `archive_request.item_removed_by_archive` с item reference, actor/time и обязательным комментарием при первой фиксации.

**Атомарность:** возврат карты, изменение item и событие — одна транзакция. Успешная команда сразу фиксирует результат этой позиции; отдельное пакетное подтверждение результатов не требуется.

**Запрет:** нельзя исключать item после handover; нельзя удалить item без возврата карты. Уже завершённые позиции нельзя повторно обрабатывать как незавершённые; ошибка или прерывание обработки другой позиции не переписывает их результаты.

### 2.6 `request_mark_not_found`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и данной заявке; не обязательно сотрудник, начавший обработку.

**Вход:** `request_id`, `item_id`, обязательный `not_found_reason_code` из закрытого справочника, необязательный свободный комментарий, idempotency metadata.

**Предусловия:** parent `processing`, единственный fulfillment shipment по заявке ещё не создан, item имеет текущий результат `extracted`

**Изменения:** item `extracted → not_found`, сохранить actor/time; необязательный комментарий может быть сохранён, если предоставлен. Физическое размещение не создавать и не менять, поскольку карта не обнаружена. `reservation_active` сохраняется, пока parent остаётся `processing`.

**Событие:** `archive_request.item_marked_not_found` с item reference, обязательным reason code, actor/time и необязательным комментарием.

**Текущий результат:** `not_found` сохраняется сразу вместе с actor/time и событием. Цикл `not_found → extracted → not_found` допускается только до создания единственного fulfillment shipment. После обнаружения карта извлекается по §2.6a; повторное фактическое отсутствие фиксируется новым событием без membership. Каждое событие остаётся в истории. Новая потребность после завершения заявки оформляется новой заявкой (D-04).

### 2.6a `request_restore_item_to_extracted`

**Actor:** любой активный сотрудник `archive`, имеющий доступ к очереди P-09 и конкретной заявке.

**Вход:** `request_id`, `item_id`, идентификатор текущего активного архивного membership/коробки, idempotency metadata. Комментарий исправления не запрашивается и не является обязательным; исходный комментарий `removed_by_archive` сохраняется в истории.

**Предусловия:** parent `processing`, единственный fulfillment shipment по заявке ещё не создан; item имеет текущий статус `not_found` или `removed_by_archive`; карта фактически обнаружена в архивном хранении и может быть извлечена из конкретной коробки. Исправление результата разрешено только до создания shipment draft. После draft результаты всех позиций фиксированы.

**Изменения:**
- заблокировать parent, item, card, активное membership, BoxCycle и BoxPlacement;
- проверить, что карта находится в указанной коробке и принадлежит архиву;
- закрыть активное membership карты в коробке; не удалять его и не переписывать историю размещения;
- обновить размещение коробки по обычным правилам закрытия membership, не выполняя автоматическую перегруппировку;
- item → `extracted`; очистить только текущие поля результата исключения, если они моделируются как актуальное состояние; исходные сведения и комментарий остаются в append-only DomainEvent;
- сохранить актуальные `extracted_at`/`extracted_by` или эквивалентные метаданные повторного извлечения;
- добавить append-only событие исправления с `previous_status`, `new_status=extracted`, card/item, actor, timestamp и ссылкой на закрытое membership. Отдельное объяснение исправления не требуется.

**Атомарность:** закрытие membership, физическое размещение, изменение текущего результата позиции и событие исправления — одна транзакция. При любой ошибке всё откатывается.

**История:** исходное событие `not_found`/`removed_by_archive` остаётся неизменным; новое событие показывает исправление, прежний и новый результаты, сотрудника и время. Timeline отображает оба события в обратном хронологическом порядке.

**Идемпотентность и гонки:** повтор с тем же command_id возвращает исходный результат; новая команда при уже `extracted` получает `already_applied/invalid_state`. После `not_found → extracted` новая команда `request_mark_not_found` с другим command_id допустима, если карта фактически не обнаружена. Команды сериализуются с отменой parent и созданием fulfillment-черновика; если fulfillment-черновик создан первым, изменение отклоняется.

**Событие:** `archive_request.item_result_corrected` с item reference, `previous_status`, `new_status`, actor/time и ссылкой на закрытое membership; отдельное объяснение не требуется.

### 2.6b Завершение обработки P-09 без отправления

После фиксации результата последней позиции система пересчитывает терминальность parent в той же транзакции:
- если все позиции имеют окончательные результаты `not_found` и/или `removed_by_archive`, а позиций `extracted` нет, parent автоматически переходит `processing → completed`; fulfillment shipment не создаётся;
- если хотя бы одна позиция остаётся `extracted`, parent остаётся `processing` и требует создания единственного полного fulfillment draft со всеми позициями `extracted`;
- после handover parent остаётся `processing` до item-level receipt всех карт manifest; после receipt последней карты parent переходит `completed`;
- `completed` публикуется событием `archive_request.completed`; завершённые parent/items неизменяемы.
### 2.7 `request_cancel`

**Actor и причина зависят от состояния:**
- `draft`: только автор черновика ЦО; причина не требуется.
- `submitted`: только уполномоченный сотрудник архива; причина обязательна.
- `processing` до фактического handover: только уполномоченный сотрудник архива может отменить всю заявку; причина обязательна.
- После фактического handover отмена заявки запрещена. Частичной отмены уже переданных карт или «невыданного остатка» в P-09 нет.

**Вход:** `request_id`, причина для `submitted/processing`, idempotency metadata.

**Предусловия:** parent находится в `draft`, `submitted` или `processing`; фактический handover по P-09 ещё не выполнялся.

**Отмена draft:** parent → `cancelled`; все draft-позиции/audit tombstones сохраняются; физическое состояние карт не меняется.

**Отмена submitted:** parent → `cancelled`; все активные позиции терминализируются; физическое состояние карт не меняется, поскольку обработка и извлечение не начинались.

**Отмена processing до handover:** в одной транзакции:
- блокировать объекты в общем для P-09 порядке `parent → shipment` (если существует) `→ request items` в стабильном порядке `→ cards/memberships/boxes`; после блокировок повторно проверить actor role/scope, состояния parent/shipment/items и отсутствие handover;
- вернуть в коробки все карты со статусом `extracted`, которые ещё не были возвращены;
- перевести эти позиции в `cancelled`;
- сохранить `not_found` и `removed_by_archive` без изменения: это уже зафиксированные результаты обработки; `removed_by_archive` не переводится в `cancelled`, поскольку карта уже возвращена в коробку;
- отменить связанный draft shipment, если он существует;
- перевести parent в `cancelled`, записать actor/time и обязательную причину.

Если хотя бы одну извлечённую карту нельзя вернуть в коробку или draft shipment нельзя отменить согласованно, вся операция откатывается. После handover команда отклоняется: все карты `extracted` уже переданы в составе единственного отправления.

**События:** полная отмена фиксируется как `archive_request.cancelled`; отмена связанного draft shipment — как `shipment.cancelled` в той же транзакции. События сохраняют actor/time/reason и не переписывают исходные события `not_found`/`removed_by_archive`.

**Гонка с handover:** cancel и handover сериализуются блокировкой parent, items, cards и shipment. Если первой зафиксирована отмена, handover запрещён; если первым зафиксирован handover, отмена запрещена. Оба исхода одновременно невозможны.

### 2.8 Создание единственного fulfillment-отправления P-09

**Actor:** любой активный сотрудник архива с доступом к очереди P-09 и конкретной заявке.

**Вход:** `request_id`, обязательный `courier_id` из общего справочника активных курьеров, idempotency metadata.

**Предусловия:**
- parent находится в `processing`;
- обработка завершена для **всех** позиций заявки: каждая имеет окончательный результат `extracted`, `not_found` или `removed_by_archive`;
- существует хотя бы одна позиция `extracted`;
- по parent ещё не создано fulfillment-отправление;
- все позиции `extracted` принадлежат parent, физически извлечены и остаются на ответственности архива;
- courier активен на момент создания отправления.

**Атомарные изменения:**
- создать единственное Shipment archive → central_office, связанное с parent;
- включить в полный manifest **все и только** позиции со статусом `extracted`;
- не включать позиции `not_found` и `removed_by_archive`;
- связать каждую отправляемую позицию с соответствующей строкой `ShipmentCard`;
- сохранить courier FK и snapshot ФИО;
- оставить custody карт у архива и parent в `processing`.

**Кардинальность и порядок:** одна P-09 имеет не более одного fulfillment-отправления. Сначала архив завершает обработку всех позиций, затем создаёт один draft с полным набором всех карт `extracted`. Отправка подмножества карт, создание нескольких отправлений по одной заявке и обработка оставшихся позиций после отправки запрещены. После создания draft результаты всех позиций фиксированы; исправление `not_found`/`removed_by_archive` и повторная обработка запрещены.

**Манифест:** полный состав фиксируется при создании draft и неизменяем. Ошибочный draft отменяется только вместе с отменой всей заявки до handover; отдельная замена draft новым отправлением по той же заявке не предусмотрена. Курьер обязателен.

**Событие:** `shipment.draft_created` с request_id, полным набором item/card IDs, actor/time и courier snapshot. Не копировать лишнюю PII.

### 2.9 Фактическая передача единственного fulfillment-отправления P-09

**Actor:** только текущий автор draft отправления; активный сотрудник архива с полномочиями.

**Вход:** `shipment_id`, idempotency metadata.

**Предусловия:**
- parent `processing`, обработка всех позиций завершена;
- shipment — единственный draft, связанный с parent;
- manifest содержит все и только позиции parent со статусом `extracted`;
- все карты manifest физически извлечены и остаются на ответственности архива;
- физическая выдача ранее не подтверждалась;
- courier assignment сохранён, manifest неизменяем.

**Атомарные изменения:**
- shipment draft → `in_transit`;
- все позиции полного manifest одновременно получают состояние `issued_pending_receipt`;
- записать actor/time и `shipment.handed_over`;
- **не переводить custody карт к курьеру или ЦО**: ответственность остаётся у архива до item-level receipt ЦО;
- parent остаётся `processing`.

**Запрет:** нельзя передать только часть manifest, выполнить повторный handover, включить чужие/неизвлечённые карты, изменить manifest/courier после handover или создать второе fulfillment-отправление для parent.

**Идемпотентность и гонки:** lock parent → shipment → items/cards в стабильном порядке; сериализовать с отменой parent и receipt. Повтор с тем же command_id возвращает исходный результат; повтор с новым command_id отклоняется без второго handover/event.

### 2.8a `shipment_change_fulfillment_courier`

**Actor:** только сотрудник архива, создавший fulfillment-черновик; учётная запись должна оставаться активной и иметь доступ к заявке.

**Вход:** `shipment_id`, новый `courier_id` из общего справочника активных курьеров, новый snapshot отображаемого ФИО, idempotency metadata.

**Предусловия:**
- shipment archive → central_office находится в `draft` и связан с P-09;
- фактическая передача ещё не подтверждена;
- новый курьер активен на момент выполнения команды;
- вызывающий сотрудник является автором этого черновика.

**Атомарные изменения:**
- заменить ссылку на запись курьера;
- заменить snapshot ФИО курьера на значение из выбранной записи на момент переназначения.

**История:** отдельная история прежних назначений не ведётся; событие переназначения не добавляет снимок состава карт и не меняет единственный неизменяемый manifest snapshot. Текущее назначение и его snapshot доступны в карточке отправления.

**Запрет:** переназначение после фактической передачи, назначение нового неактивного курьера и переназначение сотрудником, отличным от автора черновика, запрещены. Если ранее назначенный курьер деактивирован после назначения, это не меняет существующее назначение и не препятствует подтверждению передачи.



## 2026-11-22 — command/event version axes and envelope separation

This clarification supersedes any interpretation that actor/time/command metadata must be duplicated inside JSONB payload.

The common event envelope fields defined in UX-06-ADMIN-SECURITY-EVENT-CATALOG.md are top-level record fields: occurred_at, actor_user_id, actor_role_code, actor_scope_ref, outcome, reason_code, target_type/target_id, command_id, correlation_id, source_channel and event_type/event_version. Event-specific payload contains only additional allowlisted facts needed by that event. Where the existing P-09 event table lists actor_user_id or occurred_at in its “required minimal payload”, those values are envelope metadata, not duplicated payload keys. This keeps payloads minimal and prevents conflicting actor/time copies.

Version axes are independent:
- command_version: input semantics/canonicalization for a command;
- result_version: public committed result_payload schema (the common result envelope baseline 1 is approved);
- event_version: event-specific payload schema.

The public command input list currently names command_id and correlation_id but does not explicitly name command_version. Proposed contract: add a required integer command_version to the command envelope before DB API freeze; the first published input contract for each command starts at 1. This is a design proposal, not an owner-approved field/number. Do not reuse result_version or event_version for command input.

A command-level event emitted by a business operation and every per-item event in an atomic bulk command share command_id/correlation_id. A single command may emit multiple DomainEvent records; each keeps its own event ID, event_type/version, aggregate identity and occurred_at. AdminSecurityAudit remains a separate authoritative record where required.

No implementation or DDL is authorized by this clarification.
