# UX-06 — итоговая сверка design exit и передача в UX-07 (2026-11-22)

> Статус: документальный handoff, **не** свидетельство готовности реализации, миграций, БД или production. Исторические разделы с one-to-many P-09, частичной отправкой и cancel remainder не являются действующими acceptance criteria.

## 1. Зафиксированный baseline для UX-07

- Три маршрута: филиал → архив (коробки), ЦО → архив (коробки), архив → ЦО (карты только по заявке ЦО P-09). Филиал не создаёт заявки. Маршруты филиал → ЦО и ЦО → филиал не проектируются.
- Обычные отправления коробок: черновик, курьер, handover, поштучная приёмка коробок архивом, отдельное размещение на полке. Приёмка коробки не требует пересчёта карт.
- P-09: одна родительская заявка ЦО с фиксированными позициями; все позиции обработаны до формирования **не более одного** fulfillment shipment; manifest содержит все и только `extracted`; один атомарный handover. `not_found` и `removed_by_archive` — результаты обработки, а не отдельные отправления.
- После handover ЦО подтверждает получение каждой реально поступившей карты отдельно или выбранным набором атомарно. Shipment может быть `partially_received`, parent остаётся `processing` до получения всех отправленных карт; если extracted нет, завершение без shipment. Учётная ответственность за каждую карту остаётся у архива до её receipt ЦО. Отмена после handover запрещена.
- Рабочая очередь архива P-09: `submitted` + `processing`; навигационный счётчик **новых** заявок: только `submitted`; `completed`/`cancelled` — исторический просмотр. Физические отправления — отдельная очередь.
- Переход по ссылке из заявки, отправления, манифеста или истории **не** даёт прав на самостоятельную карточку связанного объекта. Серверная авторизация по роли, локации, custody и объекту обязательна. Очереди не раскрывают пациентские данные без отдельного основания.
- Для филиала два равноправных сценария: создание карты заранее (QR/ручной ввод) и создание карты непосредственно при наполнении коробки; далее оформление коробочного отправления в архив.

## 3. Конечный перечень оставшихся design-exit проверок (не новые вопросы владельцу продукта)

1. **UX06-A1 — единый источник действующих acceptance criteria.** Проставить прямые ссылки из рабочих чек-листов и основных UX-экранов на актуальный baseline; исключить попадание superseded one-to-many, cancel remainder и запрета item-level receipt в тестовые/UX-критерии. Ответственный: документация/UX. Результат: проверенный перечень действующих критериев.
2. **UX06-A2 — финальная матрица переходов и прав.** Проверить сценарии филиала, ЦО, архива и admin по направлениям «реестр → карточка → действие → история», включая D-08/P-08, независимый доступ к карте, минимизацию PII, закрытые состояния и ошибки доступа. Ответственный: UX. Результат: одна компактная матрица и список конкретных расхождений либо отметка «не обнаружены».
3. **UX06-A3 — закрытие design exit.** Зафиксировать итог A1/A2 в PROGRESS и решение о переходе к UX-07. Ответственный: владелец этапа/UX. Нельзя автоматически приравнивать этот handoff к формальному закрытию UX-06.

**На дату записи новых продуктовых решений, требующих повторных вопросов владельцу, в проверенных UX-04/05/06 фрагментах не выявлено.** Возможные расхождения по A1/A2 закрывать прежде всего по уже принятым решениям.

## 4. Отложено до implementation/API/DDL freeze — не препятствие для проектирования UX-07

- Реализация parent/item/shipment, per-item receipt/custody и read-model/queue SQL; миграция legacy per-card ArchiveRequest.
- Версионирование и валидация DB command/event контрактов, idempotency/replay, typed error mapping.
- Реальные DB principals/grants/RLS, AdminSecurityAudit, password lifecycle, минимизация payload.
- Миграционная карта legacy→target, rollback/quarantine и контракт обратной совместимости.

## 5. Отложено до cutover/production

- Read-only inventory фактических DB прав, ролей, внешних consumers и данных.
- Репетиции миграции, backup/restore, тесты конкурентности, безопасности и проверка исполнения UI/API.
- Организационное решение по срокам хранения/правовым ограничениям AdminSecurityAudit.

## 6. Стартовая постановка UX-07

После документального закрытия UX06-A1/A2/A3 начать UX-07 с **интерактивных пользовательских сценариев/экранных переходов по утверждённой архитектуре**: филиал (создание карты → коробка → отправление), архив (приёмка коробок и хранение; исполнение P-09), ЦО (заявка → отслеживание → item-level receipt), admin (справочники/права/аудит). Не проектировать запрещённые маршруты и частичную отправку P-09. Для каждого сценария фиксировать права, состояния, пустые/ошибочные состояния и проверяемые переходы. Точная формулировка scope UX-07 должна быть сверена с общим планом UX-аудита перед формальным стартом.
