# UX-06 — матрица ролевых переходов и проверка design exit (A1/A2)

Дата: 2026-11-22. Ветка: `docs/ux-audit-project`. Статус: **документальная проверка целевых UX-контрактов; не runtime verification**.

## A1. Действующие acceptance criteria (единственный приоритет при конфликте с историческими записями)

1. UX-04: `UX-04-information-architecture-and-navigation.md` — роли, разделы, переходы, серверные ограничения.
2. UX-05: `UX-05-dashboard-design.md` — счётчики и фильтры очередей, равенство предикатов реестра и счётчика.
3. UX-06: `UX-06-SHIPMENT-ROUTE-AND-STATE-AUDIT.md` — только три разрешённых маршрута и один полный P-09 shipment.
4. UX-06: `UX-06-OBJECT-DETAIL-AND-TIMELINE-CONTRACT.md` — карточки, права, receipt/custody, история.
5. `UX-06-DESIGN-EXIT-AND-UX07-HANDOFF.md` — действующий baseline и отделение design от implementation.

При конфликте исторической записи с более поздним решением владельца продукта от 2026-11-22 **не переносить** в критерии: one-to-many P-09, выдачу подмножества карт, обработку оставшихся позиций после handover, отмену невыданного остатка после handover, единовременное получение всех карт ЦО, автоматическую передачу custody курьеру для P-09. Старые audit-заметки сохраняются как история решений, а не как обязательные сценарии.

## A2. Матрица «реестр → карточка → действие → история»

| Роль / объект | Доступный реестр → карточка | Действие | История / граница доступа |
|---|---|---|---|
| Филиал / карты | Карты текущего филиала → доступная карточка | Создать QR/вручную; добавить в коробку | После handover в архив не открывать последующую независимую историю карты |
| Филиал / коробки и отправления | Свои коробки → упаковка; исходящие branch→archive → shipment | Наполнить коробку, создать черновик, назначить курьера, единый handover | Свой shipment/манифест коробок/его timeline доступны и после receipt; это не право на карточки коробок и карт после передачи |
| ЦО / заявки P-09 | Черновик — только автор; submitted/processing/completed/cancelled — сотрудники той же локации в пределах разрешённой видимости | Автор создаёт и отправляет заявку; ЦО не отменяет отправленную заявку | Request timeline и позиции; ссылка на карту не открывает независимую card history |
| ЦО / входящее archive→CO | Свой incoming shipment → полный manifest карт | Подтвердить только фактически полученные карты по одной или выбранным набором атомарно | Item receipt меняет custody только этой карты; shipment может быть partially_received; карточка карты — по самостоятельному разрешению |
| ЦО / исходящее CO→archive | Собственные коробки → черновик shipment | Назначить курьера, передать коробки одним handover | Собственный shipment и timeline доступны после получения архивом; самостоятельная карточка коробки проверяется отдельно |
| Архив / входящие коробки | Входящие branch/CO→archive → manifest коробок | Принимать коробки по одной; затем отдельно размещать коробки на полках | В основной карточке архива не показывать ФИО создателя/курьера, содержимое коробок и ФИО пациентов; событие содержит допустимого actor |
| Архив / P-09 | Очередь submitted+processing → parent и позиции | Обработать все позиции, создать одно полное отправление, единый handover; полная отмена только до handover уполномоченным сотрудником | Parent остаётся processing до receipt всех отправленных карт; архив сохраняет custody каждой до item receipt; no partial dispatch |
| Архив / исходящее archive→CO | Отправление по P-09 → карточный manifest | Автор черновика подтверждает handover | После передачи архив сохраняет shipment/timeline; независимая карточка карты — только по актуальным правам |
| Admin / справочники и аудит | Административные реестры → пользователь/курьер/полка/аудит | Управлять разрешёнными справочниками, назначениями и правами | Нет общей операционной ленты; глобальный просмотр объектов не означает право на операционные действия; AdminSecurityAudit отдельный target |
| Все роли / прямой URL, поиск, экспорт | Только server-scoped доступные объекты | Не раскрывать чужие объекты через поиск, URL, счётчик или ссылку | Права проверяются на каждой карточке, запросе истории, фильтрации и экспорте; UI-сокрытие недостаточно |

## Проверенные конкретные расхождения и их исправления

- UX-04 ошибочно описывал приёмку коробочного отправления архивом как полную единовременную: исправлено, коммит `71aec3d`.
- UX-04 связывал P-09 custody с фактом физической передачи, а не item-level receipt: исправлено, коммит `71aec3d`.
- UX-04 содержал запрет частичной приёмки карт, неверный actor custody и устаревшую навигацию ЦО: исправлено, коммиты `4263077`, `2e9661e`, `413d9e0`.
- UX-05 содержал устаревшие частичную выдачу/несколько fulfillment и полную приёмку коробок: исправлено, коммиты `b285979`, `efacead`, `c91d695`.
- UX-06 object detail содержал статус отмены остатка и частичную выдачу в активной очереди: исправлено, коммиты `c9014b9`, `7477a15`.

## Вывод A1/A2

**Действующая целевая UX-модель для проверенных основных сценариев согласована** по маршрутам, ролевой видимости, карточкам, handover, item/box receipt, очередям и custody. Новых вопросов владельцу продукта по этим сценариям не выявлено.

**Ограничение:** проверка выполнялась по целевым UX-04/05/06 и выборочно по аудитам, а не как автоматическая построчная проверка каждого исторического раздела огромного корпуса. Сохраняющиеся исторические тексты должны быть помечены superseded; их нельзя превращать в acceptance criteria.

**Не проверено:** фактические API/SQL/UI/DB permissions, миграции, end-to-end сценарии и тесты. Их готовность не следует из UX design exit.

**A3:** после внесения ссылки на эту матрицу в общий прогресс можно формально отметить документальное закрытие UX-06 и начать UX-07. До этого UX-06 не объявлять закрытым.
