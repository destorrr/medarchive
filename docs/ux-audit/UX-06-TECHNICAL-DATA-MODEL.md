# UX-06 — техническое проектирование целевой модели данных

**Статус:** проект технической модели подготовлен на основе статической инвентаризации; требует отдельного согласования перед реализацией.  
**Рабочая ветка:** `docs/ux-audit-project`  
**Бизнес-основание:** D-01…D-18, P-01…P-09 и `UX-06-storage-model-design.md`.  
**Граница:** только проектирование. Этот документ не является разрешением на изменение ORM, SQL, Alembic, сервисов, роутеров или тестов.

## 1. Вывод

Существующая PostgreSQL-модель уже содержит большую часть базовых строительных блоков хранения: `Card`, `Box`, `BoxCycle`, `BoxCardMembership`, `BoxPlacement`, `Shipment`, `ShipmentCard` и `DomainEvent`. Их следует развивать, а не заменять параллельной моделью.

Ключевые архитектурные разрывы:

1. `ArchiveRequest` — сейчас одна строка на одну карту; целевая модель требует родителя и дочерние позиции.
2. В целевой модели нужна явная фиксация состояния извлечённой карты и её связи с позицией заявки до подтверждение фактической передачи.
3. `CardPlacement` противоречит правилу «полка → коробка → карты» и должен перестать быть действующим механизмом, но его исторические данные нельзя удалять или молча преобразовывать.
4. Ограничения, запрещающие менять членство коробки при активном `BoxPlacement`, конфликтуют с двумя разными согласованными сценариями: извлечением последней карты (автоматически снять коробку) и перегруппировкой на полке (не снимать автоматически, пустую коробку оставить с предупреждением).
5. Существующие статусы/ограничения `ArchiveRequest` и `Shipment` отражают старый однокарточный процесс и не выражают групповой жизненный цикл целиком.

Рекомендация: сохранить физические сущности и историю, добавить родительскую модель заявки с позициями и контекстной историей, затем отдельными миграционными шагами переключить workflow и только после проверки данных отключить legacy-поведение.

## 2. Сопоставление предметных понятий и текущей схемы

| Целевое понятие | Текущая таблица / ORM | Решение |
|---|---|---|
| Карта | `cards` / `Card` | Сохранить как главный объект. Не переносить идентичность карты в коробку или заявку. |
| Физическая тара | `boxes` / `Box` | Сохранить. `box_number` — человекочитаемый номер; PK остаётся внутренним UUID. |
| Логистический цикл | `box_cycles` / `BoxCycle` | Сохранить; новый цикл при каждом новом заполнении/перегруппировке, старые записи не переписывать. |
| Членство карты | `box_card_memberships` / `BoxCardMembership` | Сохранить как историю помещения/извлечения карты из цикла. |
| Полочное размещение | `box_placements` / `BoxPlacement` | Сохранить как единственный действующий тип размещения на полке. |
| Индивидуальное размещение карты | `card_placements` / `CardPlacement` | Вывести из целевой операционной модели; запретить новые записи, сохранить существующие исторические записи в read-only без физического удаления. Историческая запись не определяет текущее местоположение карты. |
| Родительская заявка ЦО | Сейчас отсутствует; текущая `archive_requests` однокарточная | Ввести `archive_requests` как родителя групповой заявки после миграции старых строк. |
| Позиция заявки | Сейчас отсутствует | Ввести `archive_request_items`, одна позиция на одну карту. |
| История изменений заявки | `domain_events` | Использовать единый append-only `DomainEvent` как источник истины; события заявки и связанного fulfillment shipment связываются с parent через `request_id` и агрегируются в контекстный timeline P-09. Отдельная таблица `RequestEvent` как второй источник истины не вводится. |
| Транспортная партия P-09 | `shipments`, `shipment_cards` | Сохранить `Shipment` как транспортную партию. Одна P-09 parent связана с 0..N партиями через `Shipment.request_id`; обычные box shipments не имеют `request_id`. |
| История событий | `domain_events` | Сохранить append-only; не превращать в доступный всем ролям глобальный операционный журнал. |

**Кардинальность пациента и медицинской карты.** Один пациент может иметь несколько самостоятельных медицинских карт, в том числе оформленных в разных филиалах. Совпадение ФИО или телефона не означает, что карты являются одной и той же записью; модель и ограничения не должны навязывать уникальность медицинской карты на пациента по этим атрибутам. При этом номер медицинской карты и QR/штрихкод сохраняют собственные правила уникальности. Общая карточка/профиль пациента и отдельная сущность «Пациент» в целевой модели не вводятся. Не создаётся единая запись, которая объединяет несколько медицинских карт или их историю. Процедуры объединения карточек также нет: каждая медицинская карта остаётся самостоятельным учётным объектом со своей историей, локацией, custody и членством в коробке. При поиске по ФИО все доступные сотруднику совпадения выводятся единым списком без искусственного ограничения количества; состав результата ограничен только действующими правами и scope. Поиск поддерживает неполный ввод: достаточно фамилии или начальной части фамилии, полное ФИО не обязательно. Запрос только по фамилии возвращает все доступные карты с этой фамилией независимо от имени и отчества. Сопоставление выполняется без учёта регистра и с нормализацией `е`/`ё`, которые считаются эквивалентными. Поисковый ввод нормализуется по пробелам: крайние пробелы удаляются, последовательности повторяющихся пробельных символов между частями ФИО сводятся к одному; нормализация не изменяет сохранённое ФИО. Порядок частей ФИО в поисковом запросе сохраняется; перестановка фамилии, имени и отчества не выполняется. Каждая введённая часть ФИО сопоставляется только с начала соответствующего слова, поэтому неполный ввод нескольких частей поддерживается по префиксу каждой части (например, «Иванов Ив» находит «Иванов Иван Петрович», а «Иванов Иван П» находит «Иванов Иван Петрович»; правило применяется и к началу отчества); совпадение по произвольному внутреннему фрагменту не выполняется. Поиск по-прежнему не использует номер карты, дату рождения или телефон как критерии.

### 2.1. Предлагаемая целевая структура связей

```text
ArchiveRequest (1)
  ├── ArchiveRequestItem (N) ── Card (1)
  ├── DomainEvent (N) [aggregate_type/id + request_id]
  └── Shipment fulfillment (0..1, только archive → central_office)

Shipment fulfillment batch (N)
  ├── request_id → ArchiveRequest (1)
  └── ShipmentCard (1..N) → ArchiveRequestItem (1)

Card (1)
  ├── BoxCardMembership (0..N исторических; максимум 1 активное)
  │     └── BoxCycle ── Box
  ├── ArchiveRequestItem (0..N исторических; максимум 1 активная позиция)
  └── ShipmentCard (0..N исторических; максимум 1 активная/выданная связь)

Box (1)
  ├── BoxCycle (0..N; максимум 1 открытый)
  └── BoxPlacement (0..N исторических; максимум 1 активное)
```

Кардинальности «максимум одна активная» должны обеспечиваться БД, а не только проверками формы.

## 3. Целевая модель групповой заявки

### 3.1. Родитель `ArchiveRequest`

Рекомендуемые поля:

| Поле | Назначение / правило |
|---|---|
| `id` | UUID PK |
| `requested_by` | Автор-инициатор из роли `central_office`; неизменяем |
| `status` | `draft`, `submitted`, `processing`, `completed`, `cancelled` |
| `created_at`, `updated_at` | Системные даты |
| `submitted_at` | Факт отправки заявки в архив |
| `processing_started_at`, `processing_started_by` | Факт явного начала обработки архивом |
| `cancelled_at`, `cancelled_by`, `cancellation_reason` | Actor и время обязательны; причина обязательна для отмены после отправки, но отсутствует при самостоятельной отмене автором черновика |
| `fulfillment_shipment_id` | Nullable UNIQUE FK на единственное fulfillment-отправление P-09; полный manifest содержит все позиции `extracted` |
| `completed_at` | Заполняется только при выполнении критерия завершения |

Не добавлять в родителя дублирующие поля карты, коробки или полки. Состав хранится в дочерних позициях.

Переходы:

- `draft → submitted`: только автор черновика из ЦО; отправка фиксирует точный набор позиций, который после этого неизменяем.
- `draft → cancelled`: только автор черновика; причина не требуется.
- `submitted → processing`: любой активный сотрудник архива с доступом к очереди P-09 и заявке; переход атомарно извлекает все карты из зафиксированного набора. Инициатор начала обработки не получает эксклюзивных прав на дальнейшую обработку.
- `submitted → cancelled`: только уполномоченный сотрудник архива; причина обязательна.
- `processing → completed`: после receipt всех карт единственного fulfillment-отправления; остальные позиции должны иметь окончательный результат `not_found` или `removed_by_archive`;
- `processing`: архив полностью обрабатывает все позиции до создания единственного fulfillment-отправления.
- Завершённые и отменённые позиции/заявки неизменяемы, кроме отдельного административного корректирующего механизма P-07.

### 3.2. Позиция `ArchiveRequestItem`

Рекомендуемые поля:

| Поле | Назначение / правило |
|---|---|
| `id` | UUID PK |
| `request_id` | FK на родителя, ON DELETE RESTRICT |
| `card_id` | FK на карту, ON DELETE RESTRICT |
| `status` | `pending`, `extracted`, `removed_by_central_office` (только draft tombstone), `removed_by_archive`, `not_found`, `issued_pending_receipt`, `completed`, `cancelled` |
| `added_at`, `added_by` | Кто и когда добавил карту в состав |
| `extracted_at`, `extracted_by` | Факт атомарного извлечения и автоматической фиксации результата `extracted` («карта найдена и готова к передаче») при старте обработки |
| `resolved_at`, `resolved_by` | Актуальные метаданные последнего результата-исключения `not_found` или `removed_by_archive`; исходные значения каждого решения и исправления сохраняются в append-only DomainEvent. Для текущего `extracted` используются актуальные `extracted_at`, `extracted_by` |
| `not_found_reason_code` | Обязательный FK на закрытый справочник причин для результата `not_found` |
| `resolution_comment` | Обязателен при первой фиксации `removed_by_archive`; при повторной фиксации после исправления новый комментарий необязателен. Для `not_found` свободный комментарий необязателен |
| `shipment_card_id` | Nullable UNIQUE связь с единственной строкой `ShipmentCard`, если позиция вошла в fulfillment manifest |
| `source_membership_id` | Ссылка на закрываемое членство, если применимо; FK RESTRICT для трассировки исходной коробки/цикла |
| `returned_membership_id` | Ссылка на новое членство при возврате карты после исключения/отмены |
| `created_at`, `updated_at` | Системные даты |

До отправки автор черновика может менять состав. Удалённую из черновика позицию допустимо сохранять как audit tombstone со статусом `removed_by_central_office`; она не входит в набор позиций, зафиксированный при отправке, и не показывается в актуальном составе. После перехода родителя в `submitted` запрещены любые изменения набора позиций и их связей с картами. Разрешены только переходы статуса/результата уже зафиксированной позиции по контракту обработки; такие результаты не меняют состав и не удаляют строку.

При первой фиксации `removed_by_archive` позиция остаётся видимой в теле заявки с обязательным комментарием; при повторной фиксации после исправления новый комментарий необязателен. Карта возвращается архивом в коробку в той же транзакции, что и фиксация результата.

При атомарном старте обработки все позиции одновременно получают `extracted`. Для P-09 это также автоматический результат «карта найдена и готова к передаче»; отдельное подтверждение найденной карты не требуется. Архив фиксирует только исключения: `not_found` или `removed_by_archive`. Каждое исключение заменяет `extracted` отдельной атомарной командой и становится сохранённым сразу после её успешного выполнения. Сотрудники могут прерывать и продолжать обработку: сохранённые результаты остаются, заявка — в `processing`. **Ни одна fulfillment-партия не может быть создана, пока не завершена обработка каждой позиции заявки** (окончательный результат каждой позиции — `extracted`, `not_found` или `removed_by_archive`). Поэтому после создания первой партии нет позиций, обработка которых должна продолжаться позднее. Любой активный сотрудник архива с доступом к заявке может фиксировать результаты; `resolved_by` сохраняет фактического исполнителя. Ошибочные `not_found` и `removed_by_archive` можно исправлять на `extracted` только до создания первой fulfillment-партии; после первого fulfillment-черновика результаты всех позиций неизменяемы. Переход `not_found → extracted` требует обнаружить карту в коробке и закрыть membership; повторный `extracted → not_found` фиксирует фактическое отсутствие без membership; `removed_by_archive → extracted` требует повторного извлечения из коробки. Физическое состояние, текущий результат и append-only событие изменяются атомарно; исходные события и комментарии не переписываются.

### 3.3. Индексы и ограничения

Целевые ограничения (названия условные, SQL не фиксируется этим документом):

- CHECK для допустимых статусов родителя и позиции.
- CHECK согласованности метаданных: `cancelled` требует actor/time; nonblank reason обязателен, если родитель был `submitted` или `processing`, и отсутствует для отмены черновика автором; первичная фиксация `removed_by_archive` требует actor/time/comment; повторная фиксация после исправления требует actor/time, новый комментарий необязателен; `not_found` требует actor/time.
- UNIQUE partial на `card_id` для позиций с активным признаком `reservation_active = true` — карта не может одновременно быть зарезервирована более чем за одной незавершённой P-09. Признак сохраняется для всех включённых в состав позиций независимо от текущего результата (`pending`, `extracted`, `removed_by_archive`, `not_found`, `issued_pending_receipt`); draft tombstone его не имеет. Резервирование снимается только при переходе родителя в `completed` или `cancelled`.
- Родитель хранит nullable UNIQUE FK `fulfillment_shipment_id` на единственное fulfillment-отправление;
- В `ShipmentCard` хранится `request_item_id`; составной FK/guard проверяет принадлежность строки manifest позиции этого parent.
- Создание партии, её manifest и связи с выбранными items выполняются одной транзакцией.
- Не использовать единственный `ArchiveRequest.fulfillment_shipment_id`; отмена одной draft партии не отменяет parent и не освобождает/меняет другие партии.
- Deferred consistency guard проверяет, что каждая карта партии принадлежит parent, item status и batch status согласованы, а состав партии неизменяем после handover.
- FK всех actor полей на users с RESTRICT; при деактивации пользователя история остаётся.
- Исторические строки и события запрещено удалять; переходы статусов — только по whitelist, без повторного открытия терминальных состояний.

**Важно:** обычный partial index не может проверять статус родителя через JOIN. Поэтому уникальность активной заявки на карту должна выражаться состоянием позиции, либо отдельным денормализованным признаком с DB trigger. Нельзя проектировать индекс по условию, которое требует чтения родительской таблицы. Поэтому `reservation_active` — денормализованный признак на позиции, поддерживаемый только защищёнными DB-командами/trigger: включается при создании активной позиции; выключается для draft tombstone и для всех позиций при терминализации родителя (`completed`/`cancelled`). Deferred consistency trigger проверяет соответствие признака статусу родителя и tombstone. `removed_by_archive` и `not_found` при родителе `submitted`/`processing` сохраняют резервирование, даже если карта физически находится в коробке или не локализована.

### 3.4. Связь заявки с единственным транспортным отправлением

**Техническое решение:** P-09 parent связан максимум с одним fulfillment shipment (one-to-one, 0..1 на стороне заявки до создания). В целевой модели используется `ArchiveRequest.fulfillment_shipment_id` как nullable UNIQUE FK; обратный `Shipment.request_id` может быть UNIQUE FK либо вычисляемой/нехранимой связью — выбрать один authoritative вариант при финализации DDL. Отправление создаётся только после полного завершения обработки всех позиций и содержит все позиции `extracted`. Позиции `not_found` и `removed_by_archive` в manifest не включаются. Отправка подмножества карт, несколько отправлений по одной заявке и продолжение обработки после отправки запрещены.

### 3.5. Единственное fulfillment-отправление P-09 (`Shipment`)

Для P-09 используется существующий агрегат `Shipment` в роли единственного отправления по заявке. Целевая связь: `ArchiveRequest 1 → 0..1 Shipment`; маршрут — `archive → central_office`. Обычные box shipments не имеют связи с P-09 и продолжают использовать собственный жизненный цикл.

Рекомендуемые поля/ограничения:

| Поле | Назначение / правило |
|---|---|
| `id` | UUID PK, идентификатор отправления |
| `request_id` | UNIQUE FK на P-09 parent; NULL для обычных отправлений |
| `status` | `draft`, `in_transit`, `partially_received`, `received`, `cancelled` |
| `created_by`, `created_at` | Автор и время создания draft |
| `handed_over_by`, `handed_over_at` | Автор и время единственного фактического handover |
| `received_at` | Заполняется, когда все карты manifest фактически подтверждены ЦО |
| `courier_id` | Обязательный FK на активного курьера при создании draft |
| `courier_name_snapshot` | Историческое отображаемое ФИО курьера на момент назначения |
| `cancelled_by`, `cancelled_at`, `cancellation_reason` | Actor/time/reason отмены draft только вместе с отменой parent до handover |
| `created_at`, `updated_at` | Системные даты |

**Проекция состояния отправления:**
- `draft`: полный manifest всех карт `extracted` создан, handover ещё не выполнен.
- `in_transit`: единственный handover выполнен, ни одна карта ещё не подтверждена ЦО.
- `partially_received`: ЦО подтвердил хотя бы одну, но не все карты manifest.
- `received`: фактическое получение ЦО подтверждено для каждой карты manifest.
- `cancelled`: draft отменён только в составе отмены parent до handover; отправление остаётся в истории.

Состояние `received` отправления означает, что все карты полного manifest получили item-level receipt. Поскольку все остальные позиции уже имеют окончательные результаты `not_found` или `removed_by_archive`, получение полного manifest позволяет завершить P-09 parent.

**Manifest и связи:**
- Для каждой позиции `extracted` создаётся ровно одна `ShipmentCard` с `request_item_id`; составной FK/guard проверяет, что позиция и карта принадлежат parent, связанному с этим единственным shipment.
- UNIQUE по `request_item_id` и `card_id` в `ShipmentCard` запрещает повторное включение позиции/карты в другое отправление.
- Manifest содержит все и только позиции `extracted` данного parent; частичный manifest запрещён. Состав фиксируется при создании draft и далее неизменяем.
- Ошибочный draft отменяется только вместе с отменой всей заявки; новое отправление по той же заявке не создаётся.
- После handover запрещено менять manifest и курьера. Item-level receipt меняет состояние конкретной позиции и проекцию shipment, но не manifest.
- Parent остаётся `processing`, пока все карты manifest не получили receipt. Handover не меняет custody; receipt каждой карты меняет её учётную локацию/custody на ЦО.

### 3.6. Целевые persisted-связи, индексы и ограничения P-09

Этот раздел фиксирует рекомендуемую целевую реляционную форму. Имена колонок должны быть сверены с фактическими SQLAlchemy-моделями и текущими Alembic revisions на read-only preflight; до этой сверки DDL не создаётся.

**1. Parent ↔ единственное shipment**
- `archive_requests.fulfillment_shipment_id UUID NULL UNIQUE REFERENCES shipments(id) ON DELETE RESTRICT` (имя рабочее; проверить фактическую DDL). NULL до создания draft; заполнено после создания единственного fulfillment shipment.
- `shipments.request_id UUID NULL UNIQUE REFERENCES archive_requests(id) ON DELETE RESTRICT`; NULL означает обычное отправление, NOT NULL — fulfillment P-09. Две ссылки должны быть согласованы deferred guard; при выбранном варианте можно оставить одну FK как authoritative, вторую не хранить.
- Уникальность по request_id запрещает два fulfillment shipments на один parent.

**2. Item ↔ immutable manifest**
- Не добавлять `archive_request_items.fulfillment_batch_id`. Связь item/shipment задаётся через `shipment_cards.request_item_id`.
- `shipment_cards.request_item_id UUID NULL REFERENCES archive_request_items(id) ON DELETE RESTRICT`; для P-09 NOT NULL, для обычных отправлений NULL. UNIQUE по `request_item_id` запрещает включить позицию в другое отправление.
- Составной FK/constraint trigger проверяет, что `shipment_cards.shipment_id` — единственный shipment данного parent, `request_item_id` принадлежит этому parent и `shipment_cards.card_id = archive_request_items.card_id`.
- Manifest guard требует равенства множества manifest items множеству всех items parent со статусом `extracted` на момент создания draft; subset/superset запрещены.
- Индексы: `(shipment_id, request_item_id)` для манифеста и UNIQUE `request_item_id` для защиты от повторного включения.

**3. Immutable manifest**
- `shipment_cards` сохраняет связь `shipment_id → shipments.id`; для P-09 `request_item_id` обязателен, для обычных отправлений допускается NULL.
- Изменение/удаление строк manifest после создания draft запрещено; отмена draft возможна только в одной транзакции с отменой parent до handover.
- Если `shipment_cards.card_id` сохраняется для совместимости, DB guard проверяет равенство `request_item.card_id`.

**4. Согласованность статусов и custody**
- Допустимые P-09 shipment states: `draft`, `in_transit`, `partially_received`, `received`, `cancelled`. `partially_received` отражает item-level receipt части manifest; `cancelled` допустим только до handover и вместе с отменой parent.
- Item `issued_pending_receipt` требует shipment `in_transit` или `partially_received`, manifest membership и неизменяемый факт единого handover. Custody карты при этом остаётся у архива.
- Item `completed` после receipt требует shipment handover, фактического item receipt, `cards.current_location_id = central_office` и custody ЦО.
- Shipment state — проекция item receipts, но persisted status обновляется в той же транзакции, что и receipt; периодическая задача не является источником истины.
- Parent `completed` только когда все позиции получили терминальный исход: отправленные карты — `completed` после item receipt, остальные — `not_found` или `removed_by_archive`; при отмене до handover извлечённые позиции становятся `cancelled`. Позиции `pending`, `extracted` и `issued_pending_receipt` блокируют завершение.

**5. Разделение физического перемещения и учётной ответственности**

Фактическая ORM-модель `Card` сейчас требует ровно одно из `current_location_id` и `current_shipment_id`; это описывает физическое состояние/транспорт, но не позволяет независимо выразить custodian во время P-09. Не переиспользовать существующий `custody_status`: сейчас он описывает доступность и внешнее хранение (court/insurance/external organization), а не подразделение, ответственное за карту.

Целевая модель должна добавить отдельный FK `cards.custody_location_id → locations.id` (NOT NULL после backfill и reconciliation):
- в обычном стационарном состоянии `custody_location_id = current_location_id`;
- при handover единственного P-09 shipment карта получает `current_shipment_id = shipment.id`, `current_location_id = NULL`, но `custody_location_id` остаётся archive;
- после item receipt ЦО `current_shipment_id = NULL`, `current_location_id = central_office`, `custody_location_id = central_office`;
- перевод custody в ЦО разрешён только item-level receipt конкретной карты, не общий handover и не receipt другой карты;
- существующие внешние custody-сценарии не меняют семантику; правила совместимости `custody_location_id` с `custody_status` задаются отдельным CHECK/trigger и миграционным mapping.

Это отдельное измерение ответственности, не замена `current_location_id/current_shipment_id`. Для коробочных маршрутов сохраняются уже согласованные правила custody; новое поле не должно менять их без отдельной проверки каждого маршрута.

**6. Изменения существующих Shipment/ShipmentCard для P-09**

Сверка фактического ORM на ветке показала, что текущий `Shipment.status` допускает `draft/in_transit/received/exception/cancelled`, а `ShipmentCard` содержит только `shipment_id/card_id/box_id`. Целевая миграция должна:
- расширить допустимые shipment states значением `partially_received` только для P-09 fulfillment; обычные box shipments сохраняют собственные допустимые переходы;
- добавить в `shipment_cards` nullable `request_item_id` и item-level `received_by`, `received_at`; для P-09 эти поля обязательны по факту receipt, для других маршрутов остаются NULL;
- добавить в `shipments` `request_id` (nullable UNIQUE), `courier_name_snapshot` и необходимые actor/time поля handover/receipt, если их нет после проверки фактического DDL;
- статус `shipments.received` и shipment-level `received_by/received_at` фиксировать только при receipt всех карт единственного P-09 manifest; до этого после первого item receipt статус `partially_received`, до первого receipt — `in_transit`;
- не использовать shipment-level receipt как замену item receipt. Источником item факта являются `shipment_cards.received_by/received_at` и отдельный DomainEvent для каждой карты.

Текущие CHECK constraints `shipments_status_check`, `ck_shipment_handover_time`, `ck_shipment_received_fields` и deferred shipment guards требуют согласованного расширения; нельзя просто добавить enum value, оставив старые constraints, которые запрещают `partially_received` или требуют shipment-wide receipt metadata.

**7. Защита и конкурентность**
- Создание единственного shipment: lock parent, затем все items/cards в стабильном UUID-порядке; повторно проверить parent `processing`, окончательный outcome всех items и точное соответствие manifest множеству items `extracted`.
- Handover и cancel parent: один и тот же lock order parent → items/cards → shipment/manifest; это сериализует конкурирующие команды и исключает одновременно зафиксированные handover и отмену.
- Receipt: lock parent → shipment → items/cards в стабильном порядке; bulk receipt all-or-nothing.
- CHECK отвечает только за локальные значения/metadata; межтабличные условия реализуются составными FK и deferred constraint triggers. Не полагаться на обычный CHECK с подзапросами или на partial index, которому требуется JOIN.

### 3.7. План аддитивной миграции и backfill P-09

Миграция выполняется только после отдельного разрешения на реализацию и read-only preflight. Это проект последовательности, а не утверждение, что фактическая legacy-схема уже проверена.

1. **Baseline и инвентаризация.** Подтверждённая статическая ORM-сверка на текущей ветке: `ArchiveRequest` — per-card (`card_id`, `requested_by`, `status=new/in_progress/completed/not_found/cancelled`, `fulfilled_by`, `fulfillment_shipment_id`); CHECK `ck_archive_request_fulfillment` связывает in_progress/completed с единственным shipment, а partial UNIQUE `uq_card_one_active_archive_request` резервирует карту. `Shipment` имеет статусы `draft/in_transit/received/exception/cancelled`, courier FK, `issued_by`, `handed_over_at`, shipment-level `received_by/received_at`; `ShipmentCard` имеет PK `(shipment_id, card_id)` и nullable `box_id`, без request_item/individual receipt. `Card` имеет взаимоисключающие `current_location_id/current_shipment_id`, а `custody_status` описывает внешнее хранение, не custodian location. Перед DDL дополнительно подтвердить фактический Alembic head, SQL DDL, grants и production-like данные. Снять backup и подтвердить restore на изолированной среде. Проверить все активные и исторические per-card ArchiveRequest, связи с shipment, manifest, handover/receipt, timestamps, actor IDs и card custody.
2. **Аддитивная схема.**
3. **Детерминированное преобразование заявок.** Каждая legacy per-card request становится parent + одной item; сохранить исходный UUID в `legacy_archive_request_id`/legacy reference и не переиспользовать его как parent ID, пока не проверены все существующие FK/API. Создать устойчивую mapping table `legacy_archive_request_map(legacy_request_id UNIQUE, parent_request_id, item_id, migration_batch_id)`. Backfill идемпотентен по исходному UUID; повторный запуск не создаёт повторных parent/items/events.
4. **Преобразование fulfillment.** Создавать batch только если связь старого shipment ↔ legacy request/card manifest доказуема однозначно. Сопоставлять ShipmentCard с item через сохранённый legacy request/card pair. Не объединять разные старые shipment rows в одну batch только по совпадению даты, курьера или набора карт. Если один старый shipment содержит карты нескольких per-card requests, группировать их под общим parent только при наличии доказуемого общего исходного запроса; иначе сохранить исходные shipment records как legacy и поместить связь в reconciliation report, не угадывать.
5. **Статусы и custody.** Не выводить receipt из одного только статуса shipment, если нет подтверждённого item/card receipt evidence. Если legacy receipt был shipment-wide и не содержит item-level факта, сохранить legacy событие и классифицировать строки в quarantine/reconciliation; не генерировать фиктивные item receipt. Аналогично, handover и custody переносить только по доказуемым событиям/полям. Ambiguous rows блокируют cutover.
6. **Проверка.** Сверить counts и контрольные суммы parent/items/batches/manifests/events, проверить FK orphan, дубли активных reservations, несогласованные custody/location, дублирующие manifest membership и несовместимые статусы. Сформировать отчёты до/после и выборочные trace по UUID.
7. **Cutover.** Версионированно переключить guards/constraints и command/API/read models на parent/item/batch только после 100% reconciliation либо утверждённого карантина с ответственным и планом. Заменить shipment-wide consistency logic на batch/item-level checks, сохранив независимую ветку обычных box shipments. Старые колонки/связи и legacy `archive_requests` оставить read-only на период совместимости; destructive drop/rename — отдельный будущий gate после подтверждения отсутствия legacy readers/writers и проверенного rollback.

**Обязательные миграционные отчёты:** source row counts; migrated/skipped/quarantined counts с причинами; mapping uniqueness; parent/item/batch/manifest counts; orphan and duplicate FK reports; custody/location reconciliation; event continuity; checksum comparison; idempotent rerun report. Любая unexplained delta блокирует cutover.

## 4. Целевые состояния карты и коробки

### 4.1. Карта

Не добавлять отдельный дублирующий enum `card.storage_status`, если текущее состояние однозначно выводится из отношений. Предлагаемая интерпретация:

| Состояние | Учётная локация / связь |
|---|---|
| В филиале или ЦО | `cards.current_location_id` указывает на соответствующую локацию; членства архива нет |
| Обычное архивное хранение | `current_location_id = archive`, `current_shipment_id IS NULL`, одно активное членство в открытом BoxCycle |
| Извлечена по заявке | Та же архивная локация, нет активного членства, ровно одна позиция `extracted` у родителя `processing` |
| Не найдена по заявке | Физически не локализована; membership и shipment отсутствуют; сохраняется терминальная позиция `not_found` в истории P-09, в том числе после `completed`/`cancelled` |
| Выдана, receipt ожидается | `current_shipment_id` указывает на конкретную fulfillment batch, членства в обычном хранении нет, позиция `issued_pending_receipt`; custody остаётся у архива |
| В ЦО после приёмки | `current_location_id = central_office`, отправление принято, позиция `completed` |
| Внешнее хранение ЦО | Текущая модель `custody_status` и атрибуты внешней организации; это не маршрут отправления |

Должен существовать deferred DB-инвариант: карта в обычном физическом хранении архива без shipment и без отдельного утверждённого состояния внешнего хранения имеет ровно одно из двух взаимоисключающих состояний: активное членство в коробке ИЛИ одна активная позиция заявки `extracted` у родителя `processing`. Отдельное терминальное исключение — сохранённый результат `not_found`: membership и shipment отсутствуют, физическая локализация не заявляется, а позиция остаётся исторически связанной с завершённой/отменённой P-09. `not_found` не является активной позицией для ограничения уникальности активных заявок. Нельзя допускать свободную карту без одного из этих объяснённых состояний или одновременное членство и извлечение.

### 4.2. Коробка

- Открытый `BoxCycle` — текущее заполнение физической тары.
- Создание физической коробки не создаёт `BoxCycle`: коробка может существовать без текущего цикла.
- Первый `BoxCycle` создаётся атомарно с добавлением первой карты в коробку. Если открытый цикл уже есть, новая карта включается в него; если открытого цикла нет, команда добавления первой карты создаёт новый цикл и первое membership в одной транзакции.
- Пустую коробку, оставшуюся на полке после перегруппировки с активным `BoxPlacement`, разрешено повторно заполнять без предварительного снятия с полки. `box_add_card` создаёт новый `BoxCycle` и первое membership атомарно, сохраняя существующий `BoxPlacement`; сам факт активного placement не является запретом на добавление в такую пустую коробку. Остальные ограничения (scope, статус, активные shipments и конфликты) продолжают действовать.
- Нельзя создавать пустой начальный цикл отдельной командой или считать сам факт создания физической тары началом логистического цикла. После завершения предыдущего цикла следующий начинается только при фактическом добавлении первой карты.
- Активное `BoxPlacement` может относиться как к заполненной, так и к пустой коробке в архиве. Пустая коробка может остаться на полке после перегруппировки (D-11/P-03) либо быть размещена на полке отдельной командой `box_place`; это допустимое состояние. Пустая коробка, опустевшая вследствие extraction последней карты по заявке, напротив, автоматически снимается с полки в той же транзакции.
- При любом закрытии последнего активного membership текущий `BoxCycle` автоматически завершается в той же транзакции, независимо от причины (P-09 extraction, перегруппировка или иная разрешённая операция извлечения). Открытый цикл без активных карт недопустим.
- Правило завершения `BoxCycle` не определяет судьбу `BoxPlacement`: при extraction последней карты по P-09 `BoxPlacement` закрывается в той же транзакции; при перегруппировке пустая коробка может остаться размещённой на полке с предупреждением.
- `box_write_off` выводит пустую коробку из действующего учёта только при отсутствии активных memberships/открытого BoxCycle, активного shipment и активного BoxPlacement; доступ определяется P-05 и scope соответствующей роли. Причина/комментарий не требуется. Команда фиксирует фактического actor/time и append-only событие; физическая запись коробки, завершённые BoxCycle, placements и прежние события сохраняются, удаление истории запрещено.
- Команда `box_place` разрешает размещать на активной полке той же архивной локации и заполненную, и пустую коробку. Коробка должна числиться в этой архивной локации, не участвовать в активном shipment и не иметь другого активного `BoxPlacement`; целевая полка должна быть активной. Команда создаёт только `BoxPlacement` и событие в одной транзакции, не создаёт BoxCycle и не меняет membership, учётную локацию или custody. Предыдущие placements сохраняются в истории.
- При перегруппировке на полке автоматического снятия нет. Если коробка опустела, она остаётся на полке; UI показывает предупреждение. Решение о дальнейшей судьбе принимает пользователь. Пользователь может отдельной командой `box_unplace` снять пустую коробку с полки: команда закрывает активный `BoxPlacement`, сохраняя его в истории, но не удаляет физическую коробку, завершённые `BoxCycle`, учётную локацию или custody. Для `box_unplace` коробка должна быть пустой, без открытого цикла и активного shipment; операция доступна уполномоченному сотруднику архива в соответствующем scope. После снятия коробка остаётся в учётной локации архива без placement и может быть повторно размещена либо отдельно списана через `box_write_off`. Списание не заменяет снятие с полки и по-прежнему невозможно при активном placement.
- Следовательно, нельзя вводить общий trigger «запрещено менять membership, пока коробка размещена». Проверка должна различать контекст операции и разрешённые атомарные сценарии; прямой произвольный SQL по-прежнему должен быть закрыт DB guard.

## 5. Транзакционные сценарии и порядок блокировок

Все перечисленные операции должны исполняться в одной транзакции PostgreSQL. Любая ошибка — полный rollback. Рекомендуемый единый порядок блокировок для предотвращения deadlock:

1. Родительская заявка (если операция относится к заявке).
2. Карты по UUID в стабильном сортированном порядке.
3. Коробки по UUID в стабильном сортированном порядке.
4. BoxCycle по UUID в стабильном сортированном порядке.
5. Активные memberships и placements в стабильном порядке.
6. Отправление/строки манифеста.
7. Добавление append-only событий в той же транзакции.

Для перегруппировки, не связанной с заявкой, порядок начинается с локации, затем карты, коробки, циклы, членства и размещения. Все workflow должны соблюдать один согласованный порядок.

### 5.1. Начало обработки заявки

1. Заблокировать родителя; проверить `submitted`, роль archive и отсутствие подтверждение фактической передачи.
2. Заблокировать все карты состава в стабильном порядке.
3. Проверить, что каждая карта активна, находится в archive, не в отправлении, имеет ровно одно активное членство в открытом цикле и не конфликтует с другой активной заявкой.
4. Заблокировать коробки/циклы/членства/размещения.
5. Закрыть членства всех карт, создавая позициям ссылки на исходные membership.
6. Для каждой затронутой коробки проверить остаток карт после пакетного извлечения. Если остаток нулевой — закрыть активное BoxPlacement; коробка остаётся в archive без полки. Если остаток положительный — placement не менять.
7. Перевести позиции в `extracted`, родителя в `processing`, заполнить actor/time.
8. Записать события; commit.

Нельзя извлекать карты по одной отдельными HTTP-запросами или фиксировать `processing` до успешного извлечения всего состава. При этом атомарность старта не означает пакетного сохранения последующих результатов: после старта каждая позиция обрабатывается отдельно.

### 5.2. Исключение позиции архивом

1. Заблокировать родителя, позицию, карту и целевую коробку/цикл.
2. Проверить `processing`, отсутствие подтверждения фактической передачи и статус позиции `extracted` (автоматический результат «Найдена, готова к передаче»).
3. Закрыть состояние извлечения; включить карту в допустимую коробку в новом/актуальном цикле, создав новое membership.
4. Зафиксировать `removed_by_archive`, actor/time и ссылку на возвратное membership; комментарий обязателен при первой фиксации и необязателен при повторной после исправления.
5. Если коробка размещена на полке, разрешить атомарное добавление только в рамках этой операции без снятия коробки, при соблюдении согласованных правил упаковки.
6. Записать контекстное событие; commit. Результат этой позиции становится окончательно сохранённым сразу после commit; результаты других позиций не входят в эту транзакцию и не откатываются при ошибке или паузе.

### 5.3. Отмена заявки до handover

- В состоянии `draft`: только автор ЦО может отменить собственный черновик без причины; физические членства/размещения не меняются.
- В состоянии `submitted` до начала обработки: уполномоченный сотрудник архива может отменить заявку с обязательной причиной; физические членства/размещения не меняются.
- В состоянии `processing` до handover: уполномоченный сотрудник архива может отменить заявку с обязательной причиной; все карты `extracted` возвращаются в коробки, эти позиции получают `cancelled`, parent отменяется атомарно.
- Позиции `not_found` и `removed_by_archive` сохраняют окончательные результаты. `removed_by_archive` не переводится в `cancelled`, поскольку карта уже возвращена в коробку.
- Если fulfillment draft уже создан, он отменяется в той же транзакции, что и parent. После handover отмена заявки запрещена.
- Cancel и handover сериализуются блокировкой parent, items/cards и shipment: оба исхода одновременно невозможны.

### 5.4. Создание единственного транспортного отправления P-09

Целевая модель P-09: **одна заявка → не более одного fulfillment-отправления**. Архив завершает обработку всех позиций до создания отправления. Все карты `extracted` включаются в один полный manifest; позиции `not_found` и `removed_by_archive` не включаются.

1. Заблокировать parent; убедиться, что он находится в `processing` и fulfillment shipment ещё не создан.
2. Проверить, что каждая позиция заявки имеет окончательный результат `extracted`, `not_found` или `removed_by_archive`.
3. Убедиться, что существует хотя бы одна позиция `extracted`; если все позиции имеют `not_found`/`removed_by_archive`, parent может завершиться без отправления.
4. Создать единственное отправление archive → central_office и включить в manifest все и только позиции `extracted`.
5. Назначить активного курьера из общего справочника; сохранить FK и snapshot ФИО. Проверить активность курьера в той же транзакции.
6. Создать Shipment, полный manifest, связи `ShipmentCard.request_item_id`, courier FK/snapshot и DomainEvent одной транзакцией.
7. Зафиксировать parent в `processing`; после создания draft результаты всех позиций неизменяемы.

**Кардинальность и ограничения:**
- ArchiveRequest имеет nullable UNIQUE связь с единственным fulfillment shipment.
- Отправка подмножества карт, несколько отправлений по одной заявке и продолжение обработки после отправки запрещены.
- Manifest содержит все и только позиции `extracted` данного parent; позиции `not_found` и `removed_by_archive` исключены.
- Манифест фиксируется при создании draft и после создания не меняется. Ошибочный draft отменяется только вместе с отменой всей заявки до handover.
- Курьер обязателен для единственного отправления.

### 5.5. Фактическая передача единственного отправления

1. Заблокировать parent, shipment, все позиции manifest и соответствующие карты.
2. Подтвердить, что действие выполняет текущий автор draft — активный сотрудник архива с полномочиями.
3. Проверить, что shipment находится в draft, manifest содержит все и только позиции `extracted`, а карты остаются на ответственности архива.
4. Перевести shipment draft → `in_transit`; все позиции полного manifest одновременно получают состояние `issued_pending_receipt`. Записать actor/time и `shipment.handed_over`.
5. **Не переводить custody карт к курьеру или ЦО:** ответственность остаётся у архива до item-level receipt ЦО.
6. После handover manifest и назначение курьера неизменяемы; отмена parent запрещена.
7. Handover, item state updates и события выполняются одной транзакцией. Повтор с тем же command_id идемпотентен; новый повторный handover отклоняется.

### 5.6. Фактическое получение карт ЦО и завершение P-09

- ЦО подтверждает получение каждой реально поступившей карты отдельно. Несколько фактически поступивших карт можно подтвердить одной атомарной bulk-командой.
- Bulk receipt блокирует выбранные request items/cards в стабильном порядке, повторно проверяет actor scope и допустимость receipt; если одна позиция не допускает подтверждения, весь набор откатывается.
- В одной транзакции для каждой выбранной карты фиксируются item receipt, custody archive → CO, учётная локация ЦО, actor/time и отдельный DomainEvent.
- Частичная приёмка единственного отправления допустима на уровне карт: shipment имеет `in_transit` до первого receipt, `partially_received` после первого, но до последнего receipt, и `received` после receipt всех карт manifest.
- Receipt одной карты не меняет остальные карты. Нельзя подтвердить карту, которая фактически не поступила.
- Parent становится `completed`, когда все карты manifest получили receipt, а остальные позиции уже имеют окончательные результаты `not_found` или `removed_by_archive`.
- После handover частичная отмена не допускается.
- Повтор с тем же command_id возвращает исходный результат; новый command_id не создаёт повторный receipt и не меняет custody.
### 5.7. Перегруппировка

- Операция перемещает набор карт между коробками атомарно, закрывает старые memberships и циклы, создаёт новые циклы и memberships.
- Разрешена для коробок на полке без предварительного снятия.
- Не смешивать с извлечением по заявке: если коробка стала пустой именно из-за перегруппировки, placement остаётся активным, UI предупреждает пользователя.
- Коробка, участвующая в активном shipment, либо карта в активной заявке/отправлении, не может участвовать в перегруппировке.
- Нельзя использовать общий триггер, который автоматически снимает пустую коробку во всех сценариях.

## 6. Миграционный план: additive-first, история сохраняется

Миграции должны быть отдельными, последовательными и проверяемыми. Не переписывать старые revisions и не пытаться удалить необратимую `0003_card_placements`.

### Этап M0 — preflight и отчёт данных

До DDL собрать read-only отчёт:
- число карт с активным CardPlacement;
- число карт с активным BoxCardMembership;
- пересечение двух множеств;
- карты в archive без membership и без активной заявки;
- карты в archive с несколькими/несогласованными активными связями;
- коробки с активным placement без карт и с картами;
- активные ArchiveRequest по статусам, связанные shipment и фактический подтверждение фактической передачи;
- дубликаты активных заявок на одну карту;
- расхождения current_location/current_shipment/manifest.

Не исправлять автоматически. Каждый конфликт должен иметь классификацию и план разрешения.

### Этап M1 — расширение схемы

- Добавить таблицу `archive_request_items` и новые поля родителя/истории без удаления старых колонок.
- Сохранить прежнюю `archive_requests` как источник legacy-записей; выбрать стратегию преобразования старых строк в родитель + одну позицию с сохранением исходного UUID (например, UUID прежней строки становится ID родителя, позиция получает новый UUID).
- Добавить nullable actor/time/reason и новые поля состояния, индексы и FK; constraints включать после backfill/валидации.
- Сохранить старые статусы/поля на период перехода, не менять их смысл на лету.
- Добавить append-only историю изменения состава заявки, чтобы удалённые ЦО позиции оставались аудируемыми, но скрытыми из активного состава.

### Этап M2 — backfill и сверка

- Перенести каждую старую однокарточную заявку в родителя с одной дочерней позицией; сохранить created_at, requested_by, результат, fulfillment shipment, fulfilled_by и completed_at.
- Сопоставить старые статусы `new`, `in_progress`, `completed`, `not_found`, `cancelled` с новыми состояниями по фактическому наличию shipment/подтверждение фактической передачи и текущему местонахождению карты; не делать механическое соответствие без проверки.
- Сформировать контрольные суммы/счётчики до и после миграции: число заявок, карт в заявках, завершённых/отменённых результатов, shipment links.
- Backfill должен быть идемпотентным и возобновляемым; отдельный отчёт — для строк, которые нельзя однозначно преобразовать.

### Этап M3 — legacy CardPlacement

- Не удалять таблицу, записи, trigger-функции или revision 0003 из истории миграций.
- Сначала перевести UI/API и сервисы на запрет новых CardPlacement и чтение legacy-записей только для админской диагностики/исторического контекста.
- Не конвертировать CardPlacement в BoxPlacement автоматически: у индивидуального размещения карты нет гарантированного соответствия конкретной коробке.
- Карты с активным CardPlacement без членства должны попасть в отчёт ручной сверки и быть размещены в коробки уполномоченным архивным пользователем с записью нового события.
- После нулевого количества активных CardPlacement и подтверждения отсутствия обращений к legacy-пути можно отдельной миграцией удалить только действующие write triggers/guards, мешающие целевой модели. Историческую таблицу сохранить read-only.
- Согласованное правило: существующие записи CardPlacement сохраняются как исторические данные без физического удаления; они не участвуют в определении текущего местоположения карты и не должны возвращаться в операционные выборки как active placement.
- Автоматическое удаление/очистка CardPlacement по TTL не предусматривается. Если появится обязательное правовое требование об удалении или ограничении хранения, оно требует отдельной правовой оценки и отдельного согласованного решения; ad hoc purge запрещён.

### Этап M4 — переключение ограничений и workflow

- Перевести `ArchiveRequest` на родителя и внедрить `ArchiveRequestItem`.
- Внедрить атомарные workflow начала обработки, полной отмены до handover, фиксации исключений, единого handover полного manifest, item-level receipt и bulk receipt.
- Заменить общий guard изменения membership при активном placement на контролируемые транзакционные процедуры с различной семантикой «извлечение» и «перегруппировка».
- Добавить deferred constraints/triggers для инварианта «архивная карта либо в коробке, либо извлечена активной заявкой».
- Добавить DB-защиту one-to-one fulfillment shipment, полного manifest, item-to-shipment uniqueness и item-level custody/receipt.
- Обновить dashboard/list predicates так, чтобы счётчики и списки использовали единые определения.

### Этап M5 — очистка legacy и проверка

- Удалить/вывести из эксплуатации старые endpoint-ы и шаблоны только после миграции пользователей и переключения всех ссылок.
- Оставить историю и события доступными в карточках карты, коробки, заявки и отправления по scope ролей.
- Проверить полную миграцию на копии production-like данных, rollback/restore, конкурентные операции и негативные сценарии.
- Не включать SQLite removal в эту миграцию: это отдельный согласованный технический этап.

## 7. Обязательные DB-инварианты целевой модели

1. Одна активная membership на карту максимум.
2. Одна открытая BoxCycle на физическую коробку максимум.
3. Одно активное BoxPlacement на коробку максимум.
4. Активное BoxPlacement может относиться к заполненной или пустой коробке в архиве. Пустая коробка может остаться на полке после regroup либо быть размещена отдельной командой `box_place` (DB-59). Архивный сотрудник вправе перегруппировать карты из размещённой коробки, включая последнюю: BoxCycle закрывается, но BoxPlacement сохраняется (DB-61). Если последняя карта извлекается в рамках P-09, placement закрывается атомарно в той же транзакции (DB-11).
5. Карта в обычном физическом хранении архива без shipment — ровно в одном из состояний: активная membership либо активная позиция `extracted` у родителя `processing`. Терминальный `not_found` — отдельное историческое исключение: без membership/shipment, не считается активной позицией и не означает физическую локализацию.
6. Карта не может одновременно иметь membership и активную extracted-позицию.
7. Карта не может одновременно иметь две активные позиции разных заявок.
8. Позиция `issued_pending_receipt` обязана входить ровно в одну fulfillment batch; каждая batch содержит только позиции своего parent.
9. Один parent может иметь не более одного fulfillment shipment; маршрут строго archive → central_office.
10. Родитель не может стать `completed`, пока все позиции не терминальны; выданная, но не полученная карта не терминальна.
11. После handover отмена заявки запрещена;
12. При `cancelled` родителе все незавершённые позиции `cancelled`; `not_found`, `removed_by_archive` и `removed_by_central_office` сохраняются.
13. Терминальные статусы и исходные actor/time/reason/comment неизменяемы.
14. Исторические memberships, placements, cycles, requests, items, shipments и events не удаляются и не переписываются.
15. Прямое изменение локации карты/коробки в обход shipment workflow запрещено.

### 7.1. Сериализация полномочий с деактивацией

Все защищённые команды блокируют в одной транзакции principal actor и активные role/location membership записи, используемые для авторизации, через FOR UPDATE в стабильном порядке UUID. После получения блокировок полномочия проверяются повторно. Если команда зависит от текущего автора черновика или нового автора при admin reassignment, соответствующие principal/membership также блокируются и проверяются.

Admin deactivation и отзыв/изменение role/location membership используют те же строки и тот же порядок блокировок. Поэтому результат гонки детерминирован commit-порядком: уже начавшаяся команда может завершиться, если первой получила блокировки; после commit деактивации/отзыва последующие команды обязаны отказать. Переназначение автора разрешается отдельной командой только после того, как деактивация прежнего автора подтверждена под блокировкой. Деактивация не изменяет историю, назначение курьера, manifest или custody.

## 8. Пробелы и риски, требующие учёта до DDL

- **Циклические FK:** текущие Card/Shipment/ShipmentCard уже используют deferred composite FK. Новая связь parent ↔ shipment должна иметь один источник истины и явный порядок вставки.
- **DB-инвариант архива:** простой CHECK не может проверить membership/request item в других таблицах; понадобится deferred constraint trigger или контролируемая процедура с защитой прямого DML.
- **Уникальность активной заявки:** partial index по item status проще и надёжнее, чем условие по родителю через JOIN.
- **Различие сценариев пустой коробки:** один общий trigger не должен автоматически закрывать placement; команда должна явно определять сценарий. При перегруппировке placement сохраняется даже после извлечения последней карты (DB-61); при P-09 extraction последней карты placement закрывается (DB-11).
- **Старые данные CardPlacement:** автоматическое преобразование в коробочное размещение опасно и недостоверно.
- **Текущие тесты:** часть проверок закрепляет legacy CardPlacement и запрет изменения membership при placement; тесты потребуется переработать вместе с новым контрактом, а не механически обновить ожидания.
- **Текущий статус ArchiveRequest:** legacy CHECK требует fulfillment shipment для in_progress/completed; он несовместим с родительской заявкой, у которой позиции могут завершиться без отправления. Ограничения нужно заменить только после backfill.
- **История удаления ЦО:** физическое удаление строки позиции недопустимо, даже если UI скрывает её; требуется сохранение события/терминальной записи.

### 5.5a. Назначение и переназначение курьера fulfillment-отправления

- Курьер обязателен при создании fulfillment-черновика archive → central_office; выбирается из общего справочника активных курьеров без ограничения локацией.
- В отправлении хранятся ссылка на запись курьера и snapshot отображаемого ФИО. Snapshot отражает ФИО на момент текущего назначения.
- До фактической передачи изменить назначение может только автор черновика. Новый курьер должен быть активен на момент команды; ссылка и snapshot обновляются атомарно.
- История предыдущих назначений не ведётся. Изменение справочника после назначения не переписывает snapshot. Деактивация уже назначенного курьера не снимает назначение и не блокирует передачу.
- После фактической передачи назначение неизменяемо. Подтверждение передачи использует уже сохранённое назначение; повторный выбор курьера не требуется.


### 5.5b. Переназначение автора fulfillment-черновика

Если первоначальный автор fulfillment-черновика деактивирован до фактической передачи, только admin может отдельной атомарной командой переназначить авторство активному сотруднику той же archive location. Новый автор получает права автора черновика, включая замену курьера и подтверждение фактической передачи. Событие создания сохраняет первоначального автора; отдельное append-only событие переназначения хранит admin actor, прежнего и нового авторов и время. Manifest, parent link, courier FK/snapshot, состав карт и custody не меняются. После handover переназначение запрещено; admin не подтверждает передачу вместо нового автора.


## 2026-11-20 — Обычные отправления: единый lifecycle

Для обычных маршрутов branch → archive и central_office → archive техническая модель фиксирует draft, handover и индивидуальный box-level receipt. Черновик содержит только коробки и обязательное назначение курьера. До handover текущий автор может менять manifest и курьера; handover выполняет только текущий активный автор, после чего manifest и курьер неизменяемы, а ответственность переходит назначенному курьеру. Архив принимает каждую коробку отдельно; custody конкретной коробки и карт внутри неё переходит архиву при её receipt. Shipment закрывается после обработки всех коробок исходного manifest и расхождений. Пересчёт карт, проверка пломб и упаковки не выполняются. Принятую коробку можно разместить отдельно до завершения shipment. Все переходы атомарны и защищены блокировкой shipment; retry с тем же command_id идемпотентен.


## 4.3. Сквозная модель коробочного отправления и содержимого карты

Для обычных маршрутов branch → archive и central_office → archive манифест `Shipment` состоит из `ShipmentBox` (коробок). Карты внутри коробок не становятся отдельными строками `ShipmentCard`: их состав и связь с коробкой продолжают определяться активными `BoxCardMembership` и соответствующим открытым `BoxCycle`.

| Фаза | Shipment / Box | Карта внутри коробки | Ответственность |
|---|---|---|---|
| До handover | Shipment `draft`; коробки остаются у отправителя | Membership и BoxCycle не меняются | Отправляющая локация |
| После handover, до receipt | Shipment `in_transit`; коробки связаны с shipment через `ShipmentBox` | Membership и BoxCycle сохраняются; отдельный P-09 item и `current_shipment_id` для карты не создаются | Назначенный курьер |
| После полной receipt | Shipment `received`; коробки переходят в целевую локацию | Membership и BoxCycle сохраняются; учётная локация карты обновляется вместе с коробкой | Архив |

Факт нахождения в пути определяется shipment и связью с коробкой, а не попыткой отслеживать физическое местоположение курьера. Не создавать для обычных коробочных отправлений дублирующие `ShipmentCard` для каждой вложенной карты. Handover не меняет состав коробок, циклы и memberships. Receipt обновляет локацию коробки и содержащихся карт атомарно; он сам по себе не назначает коробке полочное место и не создаёт `BoxPlacement` — размещение на полке остаётся отдельной складской операцией.

Для P-09 archive → central_office действует иная модель: каждая fulfillment batch содержит отдельные карты через `ShipmentCard`; карты до выдачи имеют `extracted` без membership, после handover конкретной batch получают `current_shipment_id` и `issued_pending_receipt`, при этом custody остаётся у архива; после item-level receipt — локация ЦО и `completed`. Смешивать две модели манифеста запрещено.

### 4.4. Учётная позиция карты с результатом `not_found`

`not_found` — терминальный результат конкретной позиции P-09, а не физическое размещение карты и не активное членство. После завершения или отмены родительской заявки позиция `not_found` и её история сохраняются; карта остаётся в учёте архива как физически не локализованная, без membership и без shipment. Это отдельное допустимое исключение к обычному правилу «архивная карта находится в коробке либо временно извлечена по обрабатываемой заявке». Такой результат не превращает карту в свободно размещённую или доступную для обычной упаковки. Если позднее возникнет новая потребность, создаётся новая P-09; старый результат не переписывается.

### 4.5. Резервирование карты за незавершённой P-09

Каждая карта, включённая в актуальный состав P-09, зарезервирована за этой заявкой до перехода родителя в `completed` или `cancelled`. Резервирование не зависит от текущего результата позиции и физического состояния карты. В частности, `removed_by_archive` означает, что карта возвращена в коробку, но не освобождает её для другой P-09, пока исходная заявка остаётся `processing`. Аналогично `not_found` не освобождает карту, пока родитель не завершён/отменён: это результат обработки внутри существующей заявки, а не разрешение создать параллельную заявку.

Для позиции, удалённой автором из черновика, резервирование снимается вместе с переводом в draft tombstone `removed_by_central_office`. Для всех позиций резервирование снимается атомарно при переходе родителя в `completed` или `cancelled`; исторические позиции и события сохраняются. После этого новая потребность может быть оформлена новой P-09 согласно D-04.

Технически частичный UNIQUE по `card_id` опирается на `reservation_active`, а не на JOIN к родителю или список item statuses. Защищённые команды и deferred trigger обеспечивают согласованность признака с состоянием родителя. Гонка двух заявок за одну карту разрешается уникальным ограничением: только одна команда может успешно удержать резервирование.

### 5.8. Контекстная история и снимки манифестов

Единственный authoritative источник бизнес-событий — append-only DomainEvent. Отдельная таблица RequestEvent не создаётся: история P-09 строится как контекстная проекция DomainEvent по request_id. События родителя имеют aggregate_type='archive_request'; события связанного fulfillment shipment сохраняют собственный aggregate_type='shipment' и тот же request_id. События карты/коробки не включаются в историю P-09 только из-за совпадения card_id: это независимые истории объектов.

В timeline P-09 включаются бизнес-события жизненного цикла заявки: создание и изменение состава черновика, отправка, начало обработки, автоматическое извлечение позиций, каждый результат позиции и каждое исправление, отмена с причиной (если обязательна), физическая выдача каждой карты, фактическое получение ЦО каждой карты, bulk receipt и завершение. Связанные transport events включаются по явному allowlist; courier dispatch не означает перехода custody к ЦО. События admin/security audit, переназначения автора черновика и независимые события карты не добавляются в пользовательскую историю P-09 автоматически. Обычный просмотр не создаёт DomainEvent.

В истории P-09 для каждого события показываются фактический сотрудник, дата/время в часовом поясе организации, действие и предусмотренные для него причина/комментарий. Сортировка: occurred_at DESC, event_id DESC. До отправки черновик и его история доступны только автору; после submitted вся история заявки доступна сотрудникам той же локации ЦО в режиме чтения. Другая локация ЦО доступа не получает. История P-09 не открывает независимую историю карты.

Для каждой fulfillment batch archive → CO неизменяемый snapshot только её выбранных карт создаётся при shipment.draft_created. На handover и item-level receipt повторный snapshot не создаётся. Снимок содержит только поля манифеста, необходимые для воспроизведения состава; actor/time соответствующего события хранятся в envelope.

Для обычных отправлений branch/CO → archive история содержит создание черновика, подтверждение фактической передачи и полную приёмку. Манифест черновика может изменяться без истории редактирования; на handover фиксируется snapshot окончательного списка коробок, на receipt — snapshot списка коробок, принятого по манифесту. Каждое событие содержит фактического сотрудника и время. Курьер остаётся атрибутом отправления, не actor события. Событие отмены черновика до передачи не показывается сотрудникам архива; история редактирования состава и смены курьера не ведётся.


### 5.9. Границы чтения связанных агрегатов

Связи FK, request_id, shipment manifest и навигационные ссылки не являются механизмом наследования прав. Read-side запросы должны отдельно авторизовать каждый целевой агрегат по текущему principal, роли, location membership, custody, участию в конкретном shipment и состоянию процесса. Чтение shipment manifest/timeline и самостоятельное чтение card/box/timeline — разные разрешения.

Участники каждой транспортной партии сохраняют постоянный read-only доступ к карточке партии, route-specific manifest и истории после завершения партии (P-08), но этот доступ не открывает независимые карточки/истории карт и коробок и не восстанавливает custody. Для обычных branch/CO → archive manifest содержит коробки; отправитель после приёмки сохраняет shipment-доступ, а самостоятельный доступ к коробке возникает у архива в его области после receipt. Для P-09 участники видят карточные манифесты отдельных партий и их timeline в scope заявки; независимая карточка карты требует отдельного актуального разрешения.

P-09 timeline остаётся request-scoped проекцией DomainEvent по allowlist. После submitted её читают сотрудники той же локации ЦО; до submitted — только автор draft. request_id не предоставляет доступ к независимым событиям карты или других агрегатов. Для исходного филиала история карты прекращается после передачи в архив (D-08), независимо от сохраняющегося доступа к собственному shipment.

Эти read-side границы уточняют authorization layer, а не физическую модель данных или custody. Негативные сценарии и критерии проверки закреплены в DB-47/DB-47a матрицы инвариантов и тестов.


### 5.10. Корректировка ошибочного перемещения коробки между архивными полками

Ошибочное перемещение коробки между архивными полками исправляется только отдельной корректирующей операцией. Первоначальное событие перемещения и закрытое размещение сохраняются неизменными; физическое удаление события, переписывание его полок или изменение исторической последовательности запрещены. Корректировка создаёт отдельное событие с датой/временем и исполнителем и новое действующее размещение, отражающее подтверждённое фактическое положение коробки. Предыдущее размещение может быть восстановлено как текущее только после проверки, что коробка фактически находится на соответствующей полке, полка активна и относится к той же архивной области, а восстановление не противоречит последующим реальным перемещениям или другим активным процессам. Если эти условия не выполняются, операция не должна автоматически возвращать коробку на прежнюю полку; фактическое положение исправляется отдельным явно подтверждённым перемещением по обычным правилам. Корректировка не меняет состав коробки, BoxCycle, memberships, custody или учётную локацию. Все проверки, изменение действующего размещения и обязательное событие выполняются атомарно и защищены от конкурентных операций. Причина корректировки обязательна и выбирается из закрытого перечня кодов; свободный комментарий не требуется. Конкретный перечень кодов и полномочие исполнителя определяются в техническом контракте до реализации. Массовая корректировка нескольких коробок одной командой запрещена: каждая коробка исправляется отдельной корректирующей операцией.
### 5.11. Запрет перемещения коробки при незавершённой заявке ЦО → Архив

Коробку, включённую в незавершённую заявку ЦО → Архив, запрещено перемещать между архивными полками до завершения этой заявки. Проверка участия выполняется по актуальному составу/связям заявки, а не по одному только отображаемому статусу коробки. Запрет действует только на операцию перемещения коробки между архивными полками; он не расширяется автоматически на другие операции, для которых предусмотрены самостоятельные правила. При отсутствии незавершённой заявки перемещение выполняется по обычным правилам. Проверка состояния заявки и участия коробки, изменение BoxPlacement и обязательное событие перемещения выполняются атомарно с защитой от конкурентного изменения заявки или состава отправления.
### 5.12. Корректировка фактического размещения коробки при незавершённой заявке ЦО → Архив

Общий запрет на обычное перемещение коробки между архивными полками при её участии в незавершённой заявке ЦО → Архив сохраняется. Для исключительных случаев, когда необходимо исправить фактическое размещение коробки, допускается отдельная корректирующая операция, отличная от обычного перемещения. Она требует обязательную причину из закрытого перечня кодов и создаёт самостоятельное событие с исполнителем и датой/временем; свободный комментарий не требуется. Корректировка не изменяет состав, состояние, историю или сроки заявки, её manifest, факт передачи/приёмки, custody коробки или карт и учётную локацию. Она отражает только подтверждённое фактическое размещение коробки. Проверяются фактическое положение коробки, целевая активная полка в той же архивной области, полномочия и scope исполнителя и отсутствие иных конфликтующих операций. Операция и обязательное событие выполняются атомарно и защищены от конкурентных изменений заявки, состава отправления и размещения. Исполнителем может быть только активный сотрудник архива, которому отдельно предоставлено специальное полномочие на эту корректировку в пределах его scope. Обычное полномочие `box_place` не предоставляет это право; роль администратора сама по себе также не предоставляет его. Сервер проверяет активность учётной записи, роль `archive`, отдельное специальное полномочие и scope непосредственно при выполнении команды. Закрытый перечень причин определяется в техническом контракте до реализации. Корректировка не снимает запрет на обычное перемещение до завершения заявки.


### Деактивация филиала при наличии медицинских карт, числящихся за ним (2026-11-21)

Деактивация филиала запрещена, пока в системе остаются медицинские карты, учётно числящиеся за этим филиалом. До деактивации такие карты должны быть явно переведены по предусмотренному бизнес-процессу в другое действующее подразделение либо в архив. Принадлежность карты не меняется автоматически из-за деактивации филиала. Историческая принадлежность, custody, фактическая локация и события перемещения сохраняются; перевод одного атрибута не должен автоматически переписывать остальные факты. Проверка остатка карт и деактивация филиала выполняются атомарно и защищены от конкурентного изменения принадлежности карт. Остальные предварительные условия деактивации организационной единицы (активные сотрудники и незавершённые операции) сохраняются.

Поисковый ввод должен начинаться с фамилии. Запрос только по имени/отчеству не является допустимым поисковым запросом и не должен сопоставляться с соответствующими полями.


**UX-поведение поиска:** автоматический запуск после изменения поискового ввода с небольшой задержкой (debounce), без обязательной кнопки запуска. Устаревшие ответы не должны заменять результаты для более нового ввода; серверные правила авторизации, scope и фильтрации применяются к каждому запросу.


## 2026-11-21 — сохранение поиска при возврате из карточки медицинской карты

Утверждено владельцем продукта: если сотрудник открывает карточку медицинской карты из результатов поиска и возвращается назад, система сохраняет поисковый запрос и состояние списка результатов, чтобы не требовалось выполнять поиск заново. ## Решение от 2026-11-22 — порядок списания медицинской карты (P-04/D-13)

Владелец продукта подтвердил следующий процесс списания медицинской карты:

1. Центральный офис (ЦО) инициирует запрос на списание конкретной медицинской карты и указывает обязательную причину.
2. Архив проверяет карту и основание запроса.
3. Списание выполняет уполномоченный активный сотрудник архива после проверки.
4. После успешного списания карта получает статус «Списана» и больше не участвует в обычных операциях.

Физическое удаление записи медицинской карты запрещено. Сохраняются сама запись, прежние данные, история перемещений и события; факт списания фиксируется отдельным событием с автором и временем. Филиал и администратор не инициируют и не исполняют списание; ЦО инициирует, архив исполняет. Это решение утверждает общий бизнес-порядок, но не определяет пока закрытый перечень оснований/документов, точные проверки допустимости, возможность и порядок отказа по запросу, а также детальную модель состояний и команд — эти технические детали будут проработаны без изменения утверждённого распределения ролей. Реализация не разрешена.

## 2026-11-22 — уточнение модели единого handover и item-level receipt archive → central_office

Последующие решения владельца продукта supersede более раннюю модель полной приёмки fulfillment P-09 одним действием.

Целевая модель заявки ЦО должна поддерживать несколько карт и независимое состояние каждой позиции. Архив может выдавать позиции частями; невыданные позиции остаются ожидающими и могут быть выданы позднее в рамках той же заявки. Для позиции допускается результат «Не найдена» с обязательной причиной из закрытого справочника и необязательным комментарием; карта при этом не списывается, не удаляется и не получает фиктивного изменения местонахождения. Если карта позднее обнаружена, её можно выдать в рамках той же заявки.

Фактическая выдача архивом и фактическое получение ЦО — разные события. До подтверждения получения карта остаётся под ответственностью архива; после фактического подтверждения ЦО custody переходит ЦО. Подтверждение выполняется по каждой карте. Массовое подтверждение набора фактически поступивших карт допускается одной атомарной командой с отдельной фиксацией actor/time для каждой позиции. Нельзя включать в подтверждение карту, которая ещё не поступила. До первой физической выдачи всю заявку с обязательной причиной может отменить только уполномоченный сотрудник архива. После частичной выдачи активный сотрудник ЦО в пределах локации-заявителя либо сотрудник архива с доступом к заявке может отменить только невыданную часть с обязательной причиной. Уже выданные позиции не затрагиваются; parent остаётся `processing` до terminal outcome всех items.

В модели следует явно разделить как минимум item-level issued/awaiting-receipt/received/not-found/cancelled outcomes и custody. Конкретные enum names, ограничения уникальности, командные блокировки, event payloads и SQL guards уточняются в DB contracts; они не могут возвращать модель к полной приёмке всего набора одним действием.

## 2026-11-22 — коробочное хранение и массовые операции архива

Коробки можно размещать на полках как по одной, так и массово: несколько принятых коробок одной атомарной операцией размещаются на одной активной полке. Уже размещённые коробки можно массово перемещать с одной или нескольких полок на одну целевую полку. В обоих случаях операция all-or-nothing; при невозможности переместить хотя бы одну коробку откатывается весь набор. История placement сохраняется отдельно по каждой коробке с actor/time. Массовое извлечение карт из нескольких коробок не поддерживается.
