# UX-06 — техническое проектирование целевой модели данных

**Статус:** проект технической модели подготовлен на основе статической инвентаризации; требует отдельного согласования перед реализацией.  
**Рабочая ветка:** `docs/ux-audit-project`  
**Бизнес-основание:** D-01…D-18, P-01…P-09 и `UX-06-storage-model-design.md`.  
**Граница:** только проектирование. Этот документ не является разрешением на изменение ORM, SQL, Alembic, сервисов, роутеров или тестов.

## 1. Вывод

Существующая PostgreSQL-модель уже содержит большую часть базовых строительных блоков хранения: `Card`, `Box`, `BoxCycle`, `BoxCardMembership`, `BoxPlacement`, `Shipment`, `ShipmentCard` и `DomainEvent`. Их следует развивать, а не заменять параллельной моделью.

Ключевые архитектурные разрывы:

1. `ArchiveRequest` — сейчас одна строка на одну карту; целевая модель требует родителя и дочерние позиции.
2. В целевой модели нужна явная фиксация состояния извлечённой карты и её связи с позицией заявки до handover.
3. `CardPlacement` противоречит правилу «полка → коробка → карты» и должен перестать быть действующим механизмом, но его исторические данные нельзя удалять или молча преобразовывать.
4. Ограничения, запрещающие менять членство коробки при активном `BoxPlacement`, конфликтуют с двумя разными согласованными сценариями: извлечением последней карты (автоматически снять коробку) и перегруппировкой на полке (не снимать автоматически, пустую коробку оставить с предупреждением).
5. Существующие статусы/ограничения `ArchiveRequest` и `Shipment` отражают старый однокарточный процесс и не выражают групповой жизненный цикл целиком.

Рекомендация: сохранить физические сущности и историю, добавить родительскую модель заявки с позициями и контекстной историей, затем отдельными миграционными шагами переключить workflow и только после проверки данных отключить legacy-поведение.

## 2. Сопоставление предметных понятий и текущей схемы

| Целевое понятие | Текущая таблица / ORM | Решение |
|---|---|---|
| Карта | `cards` / `Card` | Сохранить как главный объект. Не переносить идентичность карты в коробку или заявку. |
| Физическая тара | `boxes` / `Box` | Сохранить. `box_number` — человекочитаемый номер; PK остаётся внутренним UUID. |
| Логистический цикл | `box_cycles` / `BoxCycle` | Сохранить; новый цикл при каждом новом заполнении/перегруппировке, старые записи не переписывать. |
| Членство карты | `box_card_memberships` / `BoxCardMembership` | Сохранить как историю помещения/извлечения карты из цикла. |
| Полочное размещение | `box_placements` / `BoxPlacement` | Сохранить как единственный действующий тип размещения на полке. |
| Индивидуальное размещение карты | `card_placements` / `CardPlacement` | Вывести из целевой операционной модели; сохранить таблицу и историю как legacy read-only до отдельного плана архивирования. |
| Родительская заявка ЦО | Сейчас отсутствует; текущая `archive_requests` однокарточная | Ввести `archive_requests` как родителя групповой заявки после миграции старых строк. |
| Позиция заявки | Сейчас отсутствует | Ввести `archive_request_items`, одна позиция на одну карту. |
| История изменений заявки | Частично `domain_events` | Ввести контекстную append-only историю заявки/позиций либо строго типизированные события с привязкой к request; отображать в карточке заявки, не в глобальном операционном журнале. |
| Отправление | `shipments`, `shipment_boxes`, `shipment_cards` | Сохранить. Для групповой заявки — максимум одно отправление архив → ЦО, связанное с родителем. |
| История событий | `domain_events` | Сохранить append-only; не превращать в доступный всем ролям глобальный операционный журнал. |

### 2.1. Предлагаемая целевая структура связей

```text
ArchiveRequest (1)
  ├── ArchiveRequestItem (N) ── Card (1)
  ├── RequestEvent (N) [контекстная история]
  └── Shipment (0..1, только archive → central_office)

Card (1)
  ├── BoxCardMembership (0..N исторических; максимум 1 активное)
  │     └── BoxCycle ── Box
  ├── ArchiveRequestItem (0..N исторических; максимум 1 активная позиция)
  └── ShipmentCard (0..N исторических; максимум 1 активное отправление)

Box (1)
  ├── BoxCycle (0..N; максимум 1 открытый)
  └── BoxPlacement (0..N исторических; максимум 1 активное)
```

Кардинальности «максимум одна активная» должны обеспечиваться БД, а не только проверками формы.

## 3. Целевая модель групповой заявки

### 3.1. Родитель `ArchiveRequest`

Рекомендуемые поля:

| Поле | Назначение / правило |
|---|---|
| `id` | UUID PK |
| `requested_by` | Автор-инициатор из роли `central_office`; неизменяем |
| `status` | `draft`, `submitted`, `processing`, `completed`, `cancelled` |
| `created_at`, `updated_at` | Системные даты |
| `submitted_at` | Факт отправки заявки в архив |
| `processing_started_at`, `processing_started_by` | Факт явного начала обработки архивом |
| `cancelled_at`, `cancelled_by`, `cancellation_reason` | Обязательные атрибуты отмены |
| `fulfillment_shipment_id` | Nullable FK на единственное отправление; уникальный, если задан |
| `completed_at` | Заполняется только при выполнении критерия завершения |

Не добавлять в родителя дублирующие поля карты, коробки или полки. Состав хранится в дочерних позициях.

Переходы:

- `draft → submitted`: ЦО отправляет заявку; состав фиксируется на момент операции, но может редактироваться ЦО до начала обработки.
- `submitted → processing`: только архив; атомарно извлекает все карты, остающиеся в составе.
- `processing → completed`: только после окончательного результата каждой позиции и полной приёмки единственного отправления, если оно создано.
- `draft/submitted/processing → cancelled`: только уполномоченный участник текущей фазы, с причиной; после handover отмена запрещена.
- Завершённые и отменённые заявки неизменяемы, кроме отдельного административного корректирующего механизма P-07.

### 3.2. Позиция `ArchiveRequestItem`

Рекомендуемые поля:

| Поле | Назначение / правило |
|---|---|
| `id` | UUID PK |
| `request_id` | FK на родителя, ON DELETE RESTRICT |
| `card_id` | FK на карту, ON DELETE RESTRICT |
| `status` | `pending`, `extracted`, `removed_by_central_office`, `removed_by_archive`, `not_found`, `in_shipment`, `completed`, `cancelled` |
| `added_at`, `added_by` | Кто и когда добавил карту в состав |
| `extracted_at`, `extracted_by` | Факт извлечения при старте обработки |
| `resolved_at`, `resolved_by` | Время и автор окончательного результата позиции |
| `resolution_comment` | Обязателен для `removed_by_archive`; для `not_found` необязателен и сохраняется только если предоставлен |
| `source_membership_id` | Ссылка на закрываемое членство, если применимо; FK RESTRICT для трассировки исходной коробки/цикла |
| `returned_membership_id` | Ссылка на новое членство при возврате карты после исключения/отмены |
| `created_at`, `updated_at` | Системные даты |

Для удаления позиции ЦО до начала обработки сохранять факт в контекстной истории; в основном составе заявки такую позицию не показывать. Допустимо физически сохранять её как терминальную `removed_by_central_office` строку, чтобы не терять идентичность и аудит, но UI должен фильтровать её из активного состава. Удаление строки из БД не допускается.

Для `removed_by_archive` позиция остаётся видимой в теле заявки с комментарием; карта должна быть возвращена архивом в коробку в той же транзакции, что и фиксация результата.

### 3.3. Индексы и ограничения

Целевые ограничения (названия условные, SQL не фиксируется этим документом):

- CHECK для допустимых статусов родителя и позиции.
- CHECK согласованности метаданных: `cancelled` требует actor/time/nonblank reason; `removed_by_archive` требует actor/time/comment; `not_found` требует actor/time.
- UNIQUE partial на `card_id` для активных позиций `pending`, `extracted`, `in_shipment` — карта не может одновременно находиться в двух незавершённых заявках.
- UNIQUE partial на `fulfillment_shipment_id`, если FK расположен на родителе.
- UNIQUE partial на `request_id` в Shipment, если связь хранится на стороне Shipment. Выбрать только один источник истины, не дублировать оба указателя без deferred FK/trigger проверки.
- FK всех actor полей на users с RESTRICT; при деактивации пользователя история остаётся.
- Исторические строки и события запрещено удалять; переходы статусов — только по whitelist, без повторного открытия терминальных состояний.

**Важно:** обычный partial index не может проверять статус родителя через JOIN. Поэтому уникальность активной заявки на карту должна выражаться состоянием позиции, либо отдельным денормализованным признаком с DB trigger. Нельзя проектировать индекс по условию, которое требует чтения родительской таблицы.

### 3.4. Единый источник связи с отправлением

Рекомендуется хранить ссылку на отправление на родителе `ArchiveRequest.fulfillment_shipment_id` с UNIQUE и FK. Тогда все позиции `in_shipment` принадлежат этому одному манифесту через родителя; дополнительный `shipment_id` в каждой позиции не нужен, если DB trigger проверяет, что манифест отправления действительно содержит каждую карту из позиции и не содержит чужие карты.

Альтернатива — `Shipment.archive_request_id` UNIQUE FK. Выбрать один вариант при подготовке DDL с учётом циклических FK и порядка вставки. В любом варианте обязательны DB-level проверки маршрута archive → central_office, единственности отправления и полного соответствия состава.

## 4. Целевые состояния карты и коробки

### 4.1. Карта

Не добавлять отдельный дублирующий enum `card.storage_status`, если текущее состояние однозначно выводится из отношений. Предлагаемая интерпретация:

| Состояние | Учётная локация / связь |
|---|---|
| В филиале или ЦО | `cards.current_location_id` указывает на соответствующую локацию; членства архива нет |
| Обычное архивное хранение | `current_location_id = archive`, `current_shipment_id IS NULL`, одно активное членство в открытом BoxCycle |
| Извлечена по заявке | Та же архивная локация, нет активного членства, ровно одна позиция `extracted` |
| В отправлении | `current_shipment_id` задан, членства в обычном хранении нет, позиция `in_shipment` |
| В ЦО после приёмки | `current_location_id = central_office`, отправление принято, позиция `completed` |
| Внешнее хранение ЦО | Текущая модель `custody_status` и атрибуты внешней организации; это не маршрут отправления |

Должен существовать deferred DB-инвариант: активная карта в архивной локации без отправления и без отдельного утверждённого состояния внешнего хранения имеет ровно одно из двух взаимоисключающих состояний: активное членство в коробке ИЛИ одна активная позиция заявки `extracted`. Нельзя допускать «потерянную» свободную карту в архиве или одновременное членство и извлечение.

### 4.2. Коробка

- Открытый `BoxCycle` — текущее заполнение физической тары.
- Активное `BoxPlacement` обычно относится к активной непустой коробке в архиве. Исключение: после перегруппировки коробка может остаться пустой на полке с сохранённым placement до решения пользователя; это допустимое предупреждаемое состояние по D-11/P-03. Пустая коробка, опустевшая вследствие extraction по заявке, напротив, должна быть снята с полки в той же транзакции.
- При извлечении последней карты по заявке закрытие `BoxPlacement` обязательно в той же транзакции.
- При перегруппировке на полке автоматического снятия нет. Если коробка опустела, она остаётся на полке; UI показывает предупреждение. Решение о дальнейшей судьбе принимает пользователь.
- Следовательно, нельзя вводить общий trigger «запрещено менять membership, пока коробка размещена». Проверка должна различать контекст операции и разрешённые атомарные сценарии; прямой произвольный SQL по-прежнему должен быть закрыт DB guard.

## 5. Транзакционные сценарии и порядок блокировок

Все перечисленные операции должны исполняться в одной транзакции PostgreSQL. Любая ошибка — полный rollback. Рекомендуемый единый порядок блокировок для предотвращения deadlock:

1. Родительская заявка (если операция относится к заявке).
2. Карты по UUID в стабильном сортированном порядке.
3. Коробки по UUID в стабильном сортированном порядке.
4. BoxCycle по UUID в стабильном сортированном порядке.
5. Активные memberships и placements в стабильном порядке.
6. Отправление/строки манифеста.
7. Добавление append-only событий в той же транзакции.

Для перегруппировки, не связанной с заявкой, порядок начинается с локации, затем карты, коробки, циклы, членства и размещения. Все workflow должны соблюдать один согласованный порядок.

### 5.1. Начало обработки заявки

1. Заблокировать родителя; проверить `submitted`, роль archive и отсутствие handover.
2. Заблокировать все карты состава в стабильном порядке.
3. Проверить, что каждая карта активна, находится в archive, не в отправлении, имеет ровно одно активное членство в открытом цикле и не конфликтует с другой активной заявкой.
4. Заблокировать коробки/циклы/членства/размещения.
5. Закрыть членства всех карт, создавая позициям ссылки на исходные membership.
6. Для каждой затронутой коробки проверить остаток карт после пакетного извлечения. Если остаток нулевой — закрыть активное BoxPlacement; коробка остаётся в archive без полки. Если остаток положительный — placement не менять.
7. Перевести позиции в `extracted`, родителя в `processing`, заполнить actor/time.
8. Записать события; commit.

Нельзя извлекать карты по одной отдельными HTTP-запросами или фиксировать `processing` до успешного извлечения всего состава.

### 5.2. Исключение позиции архивом

1. Заблокировать родителя, позицию, карту и целевую коробку/цикл.
2. Проверить `processing`, отсутствие handover и статус позиции `extracted`.
3. Закрыть состояние извлечения; включить карту в допустимую коробку в новом/актуальном цикле, создав новое membership.
4. Зафиксировать `removed_by_archive`, actor/time/comment, ссылки на исходное и возвратное membership.
5. Если коробка размещена на полке, разрешить атомарное добавление только в рамках этой операции без снятия коробки, при соблюдении согласованных правил упаковки.
6. Записать контекстное событие; commit.

### 5.3. Отмена до handover

- До начала обработки: инициатор ЦО может отменить заявку; физические членства/размещения не меняются.
- После начала обработки: только архив. Заблокировать родителя и все карты со статусом `extracted`; вернуть каждую карту в коробку и создать новое membership; перевести все незавершённые позиции в `cancelled`; сохранить `not_found`, `removed_by_archive` и `removed_by_central_office`; заполнить причину/actor/time родителя.
- Все возвраты, статусы и родительская отмена атомарны.
- Если существует отправление с фактическим handover, отмена запрещена на уровне сервиса и DB guard.

### 5.4. Единый handover

1. Заблокировать родителя; убедиться, что он `processing`, shipment ещё не создан и нет незавершённых проверок.
2. Проверить, что каждая позиция имеет итог `extracted`, `removed_by_archive`, `not_found` или `removed_by_central_office`; к отправке остаются только `extracted`.
3. Создать одно отправление archive → central_office и полный ShipmentCard manifest на все и только карты `extracted`.
4. В одной транзакции выполнить handover, назначить картам `current_shipment_id`, перевести позиции в `in_shipment`, связать shipment с родителем.
5. Если отправляемых карт нет, shipment не создавать; родитель завершить, если все позиции терминальные.
6. Commit. Никакого частичного handover или второго shipment для того же request.

### 5.5. Полная приёмка

- Получатель принимает отправление целиком по D-02.
- В одной транзакции shipment переходит в `received`, карты — в локацию ЦО, позиции `in_shipment → completed`.
- Родитель становится `completed` только если все позиции терминальные и shipment принят.
- Несоответствие манифеста не должно автоматически менять местоположение; действуют уже согласованные правила D-02, без введения сущности «инцидент».

### 5.6. Перегруппировка

- Операция перемещает набор карт между коробками атомарно, закрывает старые memberships и циклы, создаёт новые циклы и memberships.
- Разрешена для коробок на полке без предварительного снятия.
- Не смешивать с извлечением по заявке: если коробка стала пустой именно из-за перегруппировки, placement остаётся активным, UI предупреждает пользователя.
- Коробка, участвующая в активном shipment, либо карта в активной заявке/отправлении, не может участвовать в перегруппировке.
- Нельзя использовать общий триггер, который автоматически снимает пустую коробку во всех сценариях.

## 6. Миграционный план: additive-first, история сохраняется

Миграции должны быть отдельными, последовательными и проверяемыми. Не переписывать старые revisions и не пытаться удалить необратимую `0003_card_placements`.

### Этап M0 — preflight и отчёт данных

До DDL собрать read-only отчёт:
- число карт с активным CardPlacement;
- число карт с активным BoxCardMembership;
- пересечение двух множеств;
- карты в archive без membership и без активной заявки;
- карты в archive с несколькими/несогласованными активными связями;
- коробки с активным placement без карт и с картами;
- активные ArchiveRequest по статусам, связанные shipment и фактический handover;
- дубликаты активных заявок на одну карту;
- расхождения current_location/current_shipment/manifest.

Не исправлять автоматически. Каждый конфликт должен иметь классификацию и план разрешения.

### Этап M1 — расширение схемы

- Добавить таблицу `archive_request_items` и новые поля родителя/истории без удаления старых колонок.
- Сохранить прежнюю `archive_requests` как источник legacy-записей; выбрать стратегию преобразования старых строк в родитель + одну позицию с сохранением исходного UUID (например, UUID прежней строки становится ID родителя, позиция получает новый UUID).
- Добавить nullable actor/time/reason и новые поля состояния, индексы и FK; constraints включать после backfill/валидации.
- Сохранить старые статусы/поля на период перехода, не менять их смысл на лету.
- Добавить append-only историю изменения состава заявки, чтобы удалённые ЦО позиции оставались аудируемыми, но скрытыми из активного состава.

### Этап M2 — backfill и сверка

- Перенести каждую старую однокарточную заявку в родителя с одной дочерней позицией; сохранить created_at, requested_by, результат, fulfillment shipment, fulfilled_by и completed_at.
- Сопоставить старые статусы `new`, `in_progress`, `completed`, `not_found`, `cancelled` с новыми состояниями по фактическому наличию shipment/handover и текущему местонахождению карты; не делать механическое соответствие без проверки.
- Сформировать контрольные суммы/счётчики до и после миграции: число заявок, карт в заявках, завершённых/отменённых результатов, shipment links.
- Backfill должен быть идемпотентным и возобновляемым; отдельный отчёт — для строк, которые нельзя однозначно преобразовать.

### Этап M3 — legacy CardPlacement

- Не удалять таблицу, записи, trigger-функции или revision 0003 из истории миграций.
- Сначала перевести UI/API и сервисы на запрет новых CardPlacement и чтение legacy-записей только для админской диагностики/исторического контекста.
- Не конвертировать CardPlacement в BoxPlacement автоматически: у индивидуального размещения карты нет гарантированного соответствия конкретной коробке.
- Карты с активным CardPlacement без членства должны попасть в отчёт ручной сверки и быть размещены в коробки уполномоченным архивным пользователем с записью нового события.
- После нулевого количества активных CardPlacement и подтверждения отсутствия обращений к legacy-пути можно отдельной миграцией удалить только действующие write triggers/guards, мешающие целевой модели. Историческую таблицу сохранить read-only.
- Физическое удаление таблицы возможно только отдельным будущим решением после периода хранения и проверки требований к аудиту.

### Этап M4 — переключение ограничений и workflow

- Добавить deferred constraints/triggers для инварианта «архивная карта либо в коробке, либо извлечена активной заявкой».

## 7. Обязательные DB-инварианты целевой модели

1. Одна активная membership на карту максимум.
2. Одна открытая BoxCycle на физическую коробку максимум.
3. Одно активное BoxPlacement на коробку максимум.
4. Активное BoxPlacement обычно относится к непустой коробке в архиве; пустая коробка с активным placement допустима только как результат regroup до решения пользователя. После extraction последней карты по заявке placement должен быть закрыт атомарно.
5. Карта в архиве без shipment — ровно в одном из состояний: активная membership либо активная позиция `extracted`.
6. Карта не может одновременно иметь membership и активную extracted-позицию.
7. Карта не может одновременно иметь две активные позиции разных заявок.
8. Позиция `in_shipment` обязана входить в единственный shipment родителя; shipment manifest содержит все и только отправляемые позиции.
9. Один родитель — не более одного fulfillment shipment; маршрут строго archive → central_office.
10. Родитель не может стать `completed`, пока все позиции не терминальны и shipment, если создан, не `received`.
11. Родитель не может быть `cancelled` после handover.
12. При `cancelled` родителе все незавершённые позиции `cancelled`; `not_found`, `removed_by_archive` и `removed_by_central_office` сохраняются.
13. Терминальные статусы и исходные actor/time/reason/comment неизменяемы.
14. Исторические memberships, placements, cycles, requests, items, shipments и events не удаляются и не переписываются.
15. Прямое изменение локации карты/коробки в обход shipment workflow запрещено.

## 8. Пробелы и риски, требующие учёта до DDL

- **Циклические FK:** текущие Card/Shipment/ShipmentCard уже используют deferred composite FK. Новая связь parent ↔ shipment должна иметь один источник истины и явный порядок вставки.
- **DB-инвариант архива:** простой CHECK не может проверить membership/request item в других таблицах; понадобится deferred constraint trigger или контролируемая процедура с защитой прямого DML.
- **Уникальность активной заявки:** partial index по item status проще и надёжнее, чем условие по родителю через JOIN.
- **Различие двух сценариев пустой коробки:** один общий trigger не должен автоматически закрывать placement; причина операции должна быть явно проверяема сервером и БД.
- **Старые данные CardPlacement:** автоматическое преобразование в коробочное размещение опасно и недостоверно.
- **Текущие тесты:** часть проверок закрепляет legacy CardPlacement и запрет изменения membership при placement; тесты потребуется переработать вместе с новым контрактом, а не механически обновить ожидания.
- **Текущий статус ArchiveRequest:** legacy CHECK требует fulfillment shipment для in_progress/completed; он несовместим с родительской заявкой, у которой позиции могут завершиться без отправления. Ограничения нужно заменить только после backfill.
- **История удаления ЦО:** физическое удаление строки позиции недопустимо, даже если UI скрывает её; требуется сохранение события/терминальной записи.
