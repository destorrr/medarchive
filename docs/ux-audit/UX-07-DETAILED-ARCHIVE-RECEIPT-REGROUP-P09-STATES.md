# UX-07 — детальные low-fi состояния: приёмка, перегруппировка, P-09

**Дата:** 2026-11-23. **Статус:** второй визуально-сценарный проход. Дополняет WF-02, WF-03, WF-07 и screen map. **Не** меняет бизнес-правила, API или код. Иллюстративные числа и номера не являются данными системы.

## R1. Архив: карточка входящего коробочного отправления

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Приёмка → Отправление №…                          В пути / Частично принято │
│ Филиал/ЦО → Архив                              Принято 2 из 5 коробок     │
├───────────────────────────────────────────────────────────────────────────┤
│ Коробки манифеста                                                       │
│ BX-01  ✓ Принята           [Событие]                                    │
│ BX-02  ✓ Принята           [Событие]                                    │
│ BX-03  ○ Ожидается        [Подтвердить приёмку]                         │
│ BX-04  ○ Ожидается        [Подтвердить приёмку]                         │
│ BX-05  ○ Ожидается        [Подтвердить приёмку]                         │
├───────────────────────────────────────────────────────────────────────────┤
│ Расхождения: [Недостающая коробка] [Лишняя коробка] [История]            │
│ Хронология: передано → BX-01 принята → BX-02 принята                     │
└───────────────────────────────────────────────────────────────────────────┘
```

- **Одна кнопка = приёмка одной коробки.** Не добавлять «Принять всё», сканирование каждой карты, сверку количества карт или пломб.
- Шапка не показывает ФИО создателя/курьера; в истории — только согласованные исполнители событий.
- Недостающая коробка остаётся в исходном манифесте как ожидаемая. Лишняя — отдельная запись расхождения; не вставлять её молча в манифест.
- После приёмки показывать **«Перейти к размещению»**, но **не размещать** коробку автоматически. Ответственность архива возникает при приёмке, а не при размещении.

### R2. Подтверждение одной коробки и результат

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Подтвердить фактическое получение коробки BX-03?                        │
│ Отправление №… / Филиал → Архив                                          │
│ После подтверждения коробка будет принята архивом, без размещения.       │
│ [Отмена]                                  [Подтвердить приёмку BX-03]     │
├───────────────────────────────────────────────────────────────────────────┤
│ Успех: ✓ BX-03 принята · Принято 3 из 5                                  │
│ [Принять следующую коробку] [Разместить BX-03] [Вернуться к отправлению] │
└───────────────────────────────────────────────────────────────────────────┘
```

Подтверждение требует актуального статуса коробки и права приёмки. При конкурентной приёмке другой сменой — перечитать состояние и показать «Уже принята», не создавать второе событие. При ошибке сети — не показывать успешную приёмку без подтверждения сервера.

### R3. Расхождение и ошибочная приёмка

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Расхождение по отправлению №…                                           │
│ Тип: [Недостающая коробка / Лишняя коробка]                              │
│ Коробка: [Номер, если известен]                                         │
│ [Сохранить запись расхождения]                                          │
│                                                                           │
│ История расхождений: тип · коробка · дата/время · исполнитель            │
│ Ошибочная приёмка: [Исправить] → [Причина из закрытого списка]          │
└───────────────────────────────────────────────────────────────────────────┘
```

Исправление ошибочной приёмки — отдельная корректирующая операция WF-X04 с обязательной причиной и append-only историей. **Не** отменять автоматически последующие placement/custody и не переводить коробку обратно в «Ожидается» автоматически.

## G1. Архив: перегруппировка карт между коробками, стоящими на полках

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Хранение → Коробка BX-001 → Перегруппировать карты                       │
│ Источник: BX-001 · Секция A / Полка 01 · 12 карт                          │
│                                                                           │
│ Выберите карты (доступные по правам)                                     │
│ [✓] Карта №…     ФИО…                                                    │
│ [✓] Карта №…     ФИО…                                                    │
│ [ ] Карта №…     ФИО…                                                    │
│                                                                           │
│ Цель: (●) существующая коробка  ( ) новая коробка                        │
│ BX-002 · Секция A / Полка 02 · 8 карт                                     │
│                                                                           │
│ Предпросмотр: BX-001 12 → 10; BX-002 8 → 10                               │
│ Полки обеих коробок останутся прежними                                   │
│ [Назад]                         [Подтвердить перенос двух карт]          │
└───────────────────────────────────────────────────────────────────────────┘
```

**Не путать:** «Переместить коробку» изменяет placement целой коробки, «Перегруппировать карты» изменяет membership/BoxCycle. Нет требования снимать коробки с полок перед переносом. Если выбранная карта занята заявкой, отправлением или уже перемещена — **вся операция отклоняется атомарно**, показывается обновлённый состав. Не обещать многокоробочное массовое извлечение, пока не сверено позднее ограничение.

### G2. Последняя карта: коробка опустела

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ ✓ Карты перенесены в BX-002                                             │
│ ⚠ BX-001 теперь пуста, но остаётся на полке A / 01                       │
│ Текущий BoxCycle BX-001 завершён; placement сохранён.                   │
│ [Оставить на полке] [Снять с полки] [Открыть BX-001] [Открыть BX-002]    │
└───────────────────────────────────────────────────────────────────────────┘
```

«Снять с полки» — **отдельная команда** `box_unplace`; списание пустой коробки по P-05 возможно только при соблюдении всех условий. Повторное заполнение размещённой пустой коробки создаёт новый BoxCycle, не требует повторного placement.

## P1. Архив: полная обработка групповой заявки ЦО

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Заявки ЦО → №…                                         Processing        │
│ Всего позиций: 5 · extracted: 3 · not_found: 1 · removed_by_archive: 1   │
│                                                                           │
│ Карта 1    extracted                 [Исключение ▾]                     │
│ Карта 2    extracted                 [Исключение ▾]                     │
│ Карта 3    extracted                 [Исключение ▾]                     │
│ Карта 4    not_found                 [Исправить ▾]                      │
│ Карта 5    removed_by_archive        [Исправить ▾]                      │
│                                                                           │
│ Все позиции имеют результат. [Подготовить одно отправление]              │
└───────────────────────────────────────────────────────────────────────────┘
```

После «Начать обработку» все позиции атомарно `extracted` по умолчанию; затем архив может фиксировать допустимые исключения до создания draft. Для `not_found` используется согласованная причина из закрытого списка; комментарий необязателен. Для первого `removed_by_archive` комментарий обязателен. При X=0 заявка завершается без отправления. **Нельзя отправить часть готовых карт, а остальные обработать позднее.**

### P2. Единственный fulfillment: freeze и передача

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Заявка №… → Единое отправление                                           │
│ Готовы к отправке: 3 из 5 позиций (остальные — исключения)               │
│ Манифест: ВСЕ 3 extracted, без возможности снять галочки                 │
│ Курьер * [Выбрать активного курьера]                                      │
│ [Создать draft]                                                          │
│                                                                           │
│ После создания draft: результаты и manifest неизменяемы                 │
│ [Подтвердить передачу всех 3 карт]                                      │
└───────────────────────────────────────────────────────────────────────────┘
```

Draft и handover — **две разные операции**. Только автор draft может передать его, кроме согласованного admin reassignment после деактивации автора. Поздняя деактивация ранее выбранного курьера сама по себе не блокирует handover. До handover архив может отменить **всю** заявку с обязательной причиной и атомарным возвратом карт; после — нет.

### P3. ЦО: получение карт после одной полной отправки

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ ЦО → Входящее отправление №…         Частично получено                   │
│ Переданы ВСЕ 3 карты одним отправлением; получено 1 из 3                 │
│                                                                           │
│ [✓] Карта 1   Получена           [Событие]                              │
│ [ ] Карта 2   Ожидается          [Подтвердить получение]                │
│ [ ] Карта 3   Ожидается          [Подтвердить получение]                │
│                                                                           │
│ [Подтвердить получение выбранных фактически поступивших карт]           │
└───────────────────────────────────────────────────────────────────────────┘
```

Здесь **частичная приёмка**, а не частичная отправка. Получение одной карты меняет custody только этой карты; курьер сохраняет ответственность за остальные до их подтверждённого получения ЦО. Пакетное подтверждение выбранных карт атомарно. После получения всех карт shipment `received`, parent `completed`.

## Общие состояния ошибок и компактный экран

| Экран | Состояние | UI-реакция |
|---|---|---|
| R1/R2 | Коробка уже принята другим сотрудником | Перечитать статус, не дублировать событие |
| R1 | Недостающая коробка | Остаётся в манифесте; отдельная запись расхождения |
| R2 | Приёмка успешна, полка не выбрана | «Принята, не размещена», переход к размещению |
| G1 | Конкурентно изменился membership | Отказ всей операции, актуализировать обе коробки |
| G2 | Источник стал пустым | Предупреждение, BoxCycle закрыт, placement сохранён |
| P1 | Результаты не финализированы | Нет перехода к единому draft до выполнения условий |
| P2 | X=0 | Завершение без отправления |
| P2 | Handover уже выполнен | Никакой повторной передачи |
| P3 | Часть карт не поступила | Не отмечать их полученными; parent остаётся processing |
| Все | Нет прав | Безопасный отказ без раскрытия чужих карт/PII |
| Все | Ошибка сети | Не отображать успешное событие без подтверждения commit |

**Компактная ширина:** шапка с объектом/статусом → первичное действие → список карточек вместо широкой таблицы → контекстная история в раскрываемом блоке. При G1 показывать источник и цель последовательно, но **одновременно в явном виде** в блоке подтверждения. При P3 не скрывать факт единственной полной передачи за словом «частично».

## Итоговая матрица для product-review

- [ ] В R1 сотрудник не путает приёмку коробки с её размещением.
- [ ] В R3 исправление ошибочной приёмки не стирает исходное событие и не откатывает placement автоматически.
- [ ] В G1 сотрудник различает «перенести карты» и «переместить коробку».
- [ ] В G2 пустая коробка остаётся на полке и может быть повторно заполнена.
- [ ] В P1 все позиции обработаны до создания единственного fulfillment.
- [ ] В P2 нет выбора подмножества extracted для отправки.
- [ ] В P3 частичное получение не трактуется как частичная отправка.
- [ ] При переходах между реестром, карточкой и операцией сохраняется контекст и повторно проверяются права.
- [ ] Пустое состояние, нет прав, ошибка сети, конфликт конкурентного изменения визуально различимы.
- [ ] На компактной ширине основные действия и объект операции остаются видимыми.
