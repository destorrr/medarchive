# UX-07 / WF-03 — групповая заявка ЦО P-09: от запроса до получения

Дата: 2026-11-22. Статус: **low-fidelity wireframes v1, для проверки владельцем продукта**. Только проектирование; не реализация.

## 0. Источники и границы

Контрольные документы: `UX-04-information-architecture-and-navigation.md` §§3.2–3.3, 6.2–6.3 и 7.1; `UX-06-SHIPMENT-ROUTE-AND-STATE-AUDIT.md` §6; `UX-06-OBJECT-DETAIL-AND-TIMELINE-CONTRACT.md` §§28–45; `UX-06-DB-COMMAND-CONTRACTS.md` §§2.6b–2.8; `UX-06-ROLE-TRANSITION-DESIGN-EXIT-MATRIX.md`. При противоречиях исторических записей использовать действующий one-parent/one-shipment baseline P-09.

**Обязательные ограничения:**

- Только ЦО создаёт групповую заявку на медицинские карты из архива. Заявка не нужна для отправления коробок ЦО → архив.
- ЦО: свой `draft` видит/редактирует/отправляет/отменяет только автор; не более одного незавершённого собственного черновика. `submitted` и последующие состояния доступны для просмотра сотрудникам той же локации ЦО; состав уже неизменяем, ЦО не отменяет отправленную заявку.
- Архив: рабочая очередь только `submitted` и `processing`; общий счётчик новых — только `submitted`. Открытие карточки не начинает обработку.
- Отдельное действие «Начать обработку» атомарно извлекает карты; по умолчанию всем позициям присваивается `extracted` — «Найдена, готова к передаче». Сотрудник **не** подтверждает каждую найденную карту отдельной кнопкой.
- Архив вручную отмечает исключения: `not_found` (комментарий необязателен), `removed_by_archive` (при первом исключении комментарий обязателен; карта возвращается в коробку). Исправления до создания fulfillment-черновика сохраняются в истории.
- **Обрабатываются все позиции до создания отправления.** Отправление содержит все и только `extracted` карты, одну заявку и один manifest; коробки в архиве остаются. Если `extracted` нет — `completed` без отправления.
- Курьер обязателен при создании fulfillment-черновика; автор черновика выполняет один handover всего manifest. Изменять состав после создания черновика нельзя. Admin вправе переназначить автора после деактивации исходного автора по согласованной процедуре.
- После handover отмена заявки запрещена. Получение подтверждает ЦО **поштучно** или **атомарным выбранным набором**, только для реально полученных карт. До подтверждения каждой карты её custody остаётся у архива. Shipment может быть `partially_received`, parent остаётся `processing` до receipt всех отправленных карт.
- Отмена всей `submitted` или `processing` заявки **до handover** — уполномоченный сотрудник архива с обязательной причиной, при необходимости с атомарной отменой draft shipment и возвратом `extracted` карт в коробки. У ЦО доступна только отмена собственного draft без причины.
- Манифест/история заявки или отправления **не** открывают самостоятельную карточку/историю каждой карты без отдельного права.

## 1. UX-концепция: одна заявка — один рабочий контекст

Не делать сотрудника ЦО участником внутренней подготовки архива. ЦО создаёт и отслеживает заявку, затем подтверждает фактически полученные карты. Архив видит в **одной карточке заявки** последовательные режимы: «Начать обработку» → «Проверить исключения» → «Подготовить отправление» → «Передать» → «Ожидать получение». Отдельная карточка отправления существует как самостоятельный объект с manifest и timeline, но связана с заявкой прямой контекстной ссылкой.

Это **проектное решение организации интерфейса**, а не объединение доменных объектов P-09 и Shipment.

## WF-C01. ЦО — список заявок

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ ЦО / Заявки в архив                                [+ Создать заявку] │
│ [Все доступные] [Черновики] [В работе] [Завершённые]                  │
│ [Номер ______] [Статус ▾] [Дата создания ▾]                           │
├─────────────────────────────────────────────────────────────────────────┤
│ № заявки   Дата создания   Карт   Статус                   Действие     │
│ 001        ...             3      Отправлена в архив       [Открыть]   │
│ 002        ...             5      Обрабатывается          [Открыть]   │
│ 003        ...             2      Черновик (мой)          [Продолжить]│
└─────────────────────────────────────────────────────────────────────────┘
```

В строках нет ФИО пациентов и номеров карт. Автор видит свой draft, другие сотрудники ЦО не видят этот draft. Если собственный незавершённый draft уже есть, «Создать заявку» ведёт к продолжению своего черновика (предложение UX), а не пытается создать второй. Отменённый автором draft исключён из пользовательского реестра, но сохраняется в аудите.

## WF-C02. ЦО — набор карт в черновике заявки

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ ← Заявки     Новая заявка на карты из архива             [Черновик]   │
│ Поиск карт по ФИО: [____________________]                            │
│ [Доступные результаты поиска → добавить в заявку]                   │
├─────────────────────────────────────────────────────────────────────────┤
│ ВЫБРАННЫЕ КАРТЫ                                                       │
│ № карты        ФИО                 Дата рождения          [Убрать]    │
│ ...                                                                     │
│ Итого карт: [N]                                                        │
├─────────────────────────────────────────────────────────────────────────┤
│ [Отменить черновик]   [Сохранить черновик]   [Отправить в архив]       │
└─────────────────────────────────────────────────────────────────────────┘
```

Общий поиск медицинских карт — по ФИО; не переносить сюда фильтр номера/телефона из контекста наполнения коробки филиала. Результаты ограничиваются разрешённой областью; дата рождения и телефон видны активному сотруднику при наличии самостоятельного доступа к карте, **без отдельных read permissions**; это не расширяет scope и не разрешает поиск по этим полям. Отправка — **явный переход** `draft → submitted`, окончательно фиксирующий позиции; до него никаких архивных операций не происходит. Только автор может редактировать, отправить и отменить свой draft; отмена без причины.

## WF-C03. ЦО — карточка отправленной заявки

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ ← Заявки / №...                                      [Processing]     │
│ Создана: ...   Позиции: N                                             │
│ Состояние: [Отправлена] → [Обрабатывается] → [Передана] → [Получена]   │
├─────────────────────────────────────────────────────────────────────────┤
│ КАРТЫ В ЗАЯВКЕ                                                        │
│ № карты       ФИО          Результат архива         Получение ЦО     │
│ ...                                                                     │
├─────────────────────────────────────────────────────────────────────────┤
│ СВЯЗАННОЕ ОТПРАВЛЕНИЕ                                                 │
│ [№... / Открыть приёмку]  или «Пока не сформировано»                  │
├─────────────────────────────────────────────────────────────────────────┤
│ ИСТОРИЯ ЗАЯВКИ (новые события сверху)                                  │
│ [Дата/время] [Событие] [Исполнитель] [Причина/комментарий при наличии] │
└─────────────────────────────────────────────────────────────────────────┘
```

Это визуальные фазы, **не дополнительные состояния parent**. Parent остаётся `processing` во время перевозки и частичного receipt; `completed` наступает только после receipt всего manifest либо без отправления при нуле `extracted`. После `submitted` ЦО не редактирует и не отменяет заявку. Отдельная карточка карты открывается только по самостоятельному праву.

## WF-A07. Архив — рабочая очередь заявок

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Архив / Заявки ЦО                 [Новых: N]                          │
│ [Новые] [В обработке]       [Номер __] [Дата __] [Инициатор ▾]        │
├─────────────────────────────────────────────────────────────────────────┤
│ № заявки    Дата     Инициатор ЦО       Карт   Статус      Действие    │
│ ...         ...      ...                4      Submitted   [Открыть]  │
│ ...         ...      ...                2      Processing  [Открыть]  │
└─────────────────────────────────────────────────────────────────────────┘
```

В очереди нет ФИО пациентов и номеров карт. Счётчик `submitted` — **общий для архива**, а не персональные непрочитанные уведомления; открытие карточки не уменьшает счётчик. Завершённые/отменённые — отдельный исторический просмотр. `processing` после handover остаётся в рабочей очереди до подтверждения ЦО всех полученных карт, но архивные операции передачи повторно не предлагаются.

## WF-A08. Архив — карточка и начало обработки

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ ← Заявки ЦО / №...                                  [Submitted]       │
│ Инициатор: ...       Всего карт: N                                     │
│                                                                         │
│ ПОЗИЦИИ ЗАЯВКИ (не редактируются)                                      │
│ № карты    ФИО        Текущее место/коробка (если доступно)           │
│ ...                                                                     │
├─────────────────────────────────────────────────────────────────────────┤
│ [Начать обработку]   [Отменить заявку (причина обязательна)]           │
└─────────────────────────────────────────────────────────────────────────┘
```

После нажатия «Начать обработку» — отдельное подтверждение последствий: все позиции атомарно извлекаются из коробок в учётном смысле, коробки остаются на месте; результат всех позиций — `extracted`. Если команда не выполнена, ни одно состояние не должно быть показано как частично успешное. Обработка не закрепляется за конкретным сотрудником; её может продолжить другой уполномоченный сотрудник архива.

## WF-A09. Архив — проверка результатов всех позиций

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Заявка №...                                              [Processing] │
│ Готовы к передаче: X / Всего: N                                       │
│                                                                         │
│ № карты   ФИО       Результат                         Действие         │
│ ...       ...       Найдена, готова к передаче       [Исключение ▾]  │
│ ...       ...       Не найдена                       [Исправить ▾]    │
│ ...       ...       Исключена архивом                [Исправить ▾]    │
├─────────────────────────────────────────────────────────────────────────┤
│ [История изменений]            [Подготовить единое отправление →]     │
└─────────────────────────────────────────────────────────────────────────┘
```

Каждая позиция после начала обработки уже считается `extracted`; кнопки «Подтвердить найденную» **нет**. Действия:
- «Не найдена» → `not_found`, комментарий необязателен.
- «Исключена архивом» → `removed_by_archive`, **при первой фиксации** комментарий обязателен, карта возвращается в коробку в составе атомарной операции.
- «Исправить на готова к передаче» для `not_found` или `removed_by_archive` — только при фактическом обнаружении/повторном извлечении из конкретной коробки; отдельное объяснение не требуется.
- Повторные согласованные изменения до draft shipment возможны, фиксируются событиями и не переписывают историю.

**Граница freeze:** перед созданием единственного fulfillment-черновика сотрудник видит итог: X `extracted`, Y `not_found`, Z `removed_by_archive`, X+Y+Z=N. Все позиции уже обработаны, после создания черновика исправлять результаты нельзя. Если X=0, кнопка отправления отсутствует; заявка завершается `completed` без отправления.

## WF-A10. Архив — единое fulfillment-отправление и handover

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Заявка №... / Подготовка отправления                                  │
│ Маршрут: Архив → ЦО    Манифест: ВСЕ готовые карты (X)                │
├─────────────────────────────────────────────────────────────────────────┤
│ № карты        ФИО                   Включена в manifest              │
│ ...                                                                     │
│ [Нет кнопки удалить позицию и нет выбора подмножества]                │
│ Курьер * [Активный курьер ▾]                                          │
│                                                                         │
│ [Назад к результатам]                 [Создать черновик отправления]   │
├─────────────────────────────────────────────────────────────────────────┤
│ ПОСЛЕ СОЗДАНИЯ: [№ отправления] [Draft]                               │
│ Курьер: [ФИО]  [Заменить на активного курьера]                        │
│ [Отменить всю заявку до handover*]   [Подтвердить передачу ВСЕХ карт] │
└─────────────────────────────────────────────────────────────────────────┘
```

Создание draft и handover — **разные действия**. Черновик с неизменяемым manifest содержит все `extracted`; курьер обязателен при создании. Подтвердить единую фактическую передачу вправе только активный автор draft или назначенный admin новый автор после деактивации прежнего. При наличии уже назначенного, но позднее деактивированного курьера существующее назначение **не блокирует handover**; новый выбор деактивированного курьера запрещён. В истории не добавлять отдельное подтверждение личности курьера.

`* ` Отмена до handover — **всей заявки**, только архивом при соответствующем полномочии и обязательной причине: атомарный возврат извлечённых карт в коробки и отмена связанного draft shipment. Не проектировать отмену отдельной позиции/остатка. После handover отмена недоступна.

## WF-C04. ЦО — поштучная приёмка медицинских карт

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ Приёмка / Отправление №...   [In transit / Partially received]        │
│ Заявка №... →       Всего в manifest: N       Получено: R из N        │
├─────────────────────────────────────────────────────────────────────────┤
│ КАРТЫ ОТПРАВЛЕНИЯ                                                     │
│ [ ] №... ФИО...   [Ожидается]      [Подтвердить получение]            │
│ [✓] №... ФИО...   [Ожидается]      [Подтвердить получение]            │
│ [—] №... ФИО...   [Получена]       [Просмотр события]                 │
│                                                                         │
│ [ Подтвердить получение выбранных фактически поступивших карт ]       │
├─────────────────────────────────────────────────────────────────────────┤
│ История: передача всего manifest → receipt одной карты → ...         │
└─────────────────────────────────────────────────────────────────────────┘
```

**Физическая передача** всего manifest — единая, **фактическое получение** может быть частичным. Нельзя отмечать не поступившие карты только для ускорения закрытия. Каждое receipt меняет custody **только выбранной карты**. Набор выбранных карт подтверждается атомарно (всё или ничего). При receipt части manifest — `partially_received`, parent всё ещё `processing`; последняя receipt — `received` и `completed`. История и манифест сохраняются и после закрытия.

## 2. Связи экранов (wireflow)

```text
ЦО:   Заявки → [Мой draft] → Отправить в архив ────────────────────────┐
      [Список submitted/processing] → Карточка заявки                 │
                                                                     ↓
Архив:                               Очередь новых → Начать обработку
                                                ↓
                              Автоматически extracted для всех позиций
                                                ↓
                             Исключения / исправления результатов (все)
                                                ↓
                   ┌────────────────────────────┴────────────────────────┐
                   │ X=0: completed без отправления                      │
                   │ X>0: Один draft со ВСЕМИ extracted                  │
                   └────────────────────────────┬────────────────────────┘
                                                ↓
                              Автор draft → один полный handover
                                                ↓
ЦО:               Приёмка фактически полученных карт (1 или выборка)
                                                ↓
                              Последняя карта → shipment received
                                                ↓
                               Parent completed; история доступна
```

Архив может отменить **всю заявку до handover** с причиной, в том числе при уже созданном draft shipment. После handover — только ожидание подтверждения ЦО, а не новые выдачи.

## 3. Матрица действий по роли и фазе

| Фаза | ЦО | Архив | Что принципиально запрещено |
|---|---|---|---|
| Draft P-09 | Автор меняет набор, отправляет или отменяет без причины | Не видит | Чужой draft; два одновременных своих draft |
| Submitted | Читает заявку (сотрудники той же локации) | Начинает обработку либо отменяет с причиной | Изменять состав; автоматический старт обработки при просмотре |
| Processing, draft shipment ещё нет | Читает результаты | Фиксирует исключения/исправления; готовит **все** позиции | Частичная отправка, «найдена» по одной кнопке |
| Processing, draft shipment создан | Только просмотр | Автор отправления подтверждает весь manifest; уполномоченный архив может отменить всю заявку до handover | Редактировать item results или manifest |
| In transit / partially received | Подтверждает только реально полученные карты | Следит за заявкой/историей | Отмена, дополнительное отправление, повторный handover, перенос custody неполученных карт |
| Completed / cancelled | Просмотр разрешённой истории | Исторический просмотр | Любые повторные операционные действия |

## 4. Ошибочные, пустые и конкурирующие состояния

| Событие | Поведение UX |
|---|---|
| Нет заявок ЦО или новых заявок архива | Пустая очередь, без фиктивного действия |
| ЦО пытается создать второй свой draft | Открыть существующий draft / объяснить ограничение, не создавать второй |
| Автор ЦО потерял право/деактивирован | Не разрешать изменения; безопасная ошибка без расширения доступа |
| В результатах поиска карты отсутствуют/не доступны | Не раскрывать чужие данные; показать отсутствие доступных совпадений |
| Начало обработки архивом не прошло атомарно | Показать отказ, обновить заявку, не рисовать частичный успех |
| Исключение `removed_by_archive` без первого комментария | Не сохранять; подсказать обязательный комментарий |
| Коррекция результата после создания fulfillment draft | Запретить и показать статус «Результаты зафиксированы» |
| Конкурирующий сотрудник создал draft раньше | Обновить карточку, запретить второй shipment |
| Отмена против handover | Перечитать серверный итог; либо отменено, либо передано; одновременно не бывает |
| Все позиции не подлежат отправке | Completed без пустого shipment, показать результаты |
| ЦО пытается подтвердить не полученную карту | Не предлагать массовую автоприёмку; требовать осознанного выбора реально поступивших |
| Повторное receipt или конфликт выбранного набора | Обновить актуальные статусы; не создавать повторных событий, атомарный набор не принимать частично |
| Доступ к карточке карты только через ссылку манифеста | Проверить самостоятельное право; при отсутствии не раскрывать данные/историю |

## 5. Критерии приёмки WF-03 для UX-07

1. Два чётких пользовательских контекста: ЦО инициирует и принимает; архив исполняет и передаёт, без курьерской роли.
2. В UI отсутствуют partial dispatch, multiple shipments, cancel remainder, «найдена» как ручная операция на каждую карту, и автоматическое изменение custody при handover.
3. У каждой карточки есть понятное главное действие для своей фазы, а недоступные действия исчезают/объясняются без нарушения серверных guards.
4. Списки и история минимизируют PII, остаются scope-aware; связанная заявка/отправление не расширяет независимый доступ к картам.
5. Wireframes UX-08 должны проверить, различают ли сотрудники ЦО «заявка отправлена», «карты переданы» и «карты фактически получены».
6. Следующий блок: **WF-04 — ЦО → архив (коробки), внешнее хранение ЦО; затем WF-05 — admin**.

**Примечание:** это текстовые low-fidelity wireframes, а не интерактивный прототип и не доказательство реализации контрактов.
