## WF-X01. ЦО — инициирование списания медицинской карты (P-04)

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Карта / [Доступная карта] / Списание                                  │
│ Текущее состояние, локация, ответственность (только доступные поля)    │
├──────────────────────────────────────────────────────────────────────┤
│ [Инициировать списание]                                                │
│ Основание *  [Потеря карты / Порча / Прочие причины ▾]                  │
│ Комментарий [необязательно________________________]                    │
│ Реквизиты внешнего документа [необязательно]                           │
│ [Отмена]  [Отправить запрос на списание]                               │
├──────────────────────────────────────────────────────────────────────┤
│ После отправки: «Ожидает обработки архивом»                            │
│ [Смотреть статус и историю запроса]                                    │
└──────────────────────────────────────────────────────────────────────┘
```

- Инициирует только уполномоченный сотрудник ЦО; **инициирование не списывает карту и не меняет custody**.
- Закрытый код основания: `lost`, `damaged`, `other`; комментарий необязателен даже для `other`. Акт, номер и вложение не требуются; **загрузка файлов как функциональность не утверждена**. Не рисовать обязательную загрузку.
- Отдельный запрос списания не является заявкой на выдачу P-09, транспортным отправлением или внешним хранением.
- Конфликт с активным отправлением, несовместимой ответственностью или другой операцией блокируется сервером. Показать причину запрета без раскрытия чужой истории.

## WF-X02. Архив — обработка запроса списания (P-04)

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Архив / Запросы списания [Ожидают] [В работе] [История]                │
│ Запрос №…   Карта №… (при наличии права)   Основание   Статус          │
├──────────────────────────────────────────────────────────────────────┤
│ Карточка запроса: инициатор ЦО, дата, основание, комментарий          │
│ Проверки: состояние карты, custody, конфликтные операции              │
│ [Начать обработку]                                                     │
│ [Выполнить списание]  [Отменить запрос с обязательной причиной]        │
├──────────────────────────────────────────────────────────────────────┤
│ После исполнения: сотрудник, время, неизменяемая история              │
└──────────────────────────────────────────────────────────────────────┘
```

- Исполняет **один** уполномоченный сотрудник архива, второго подтверждающего нет. Исполнение атомарно фиксирует результат, actor/time и историю.
- До начала обработки ЦО может отменить свой запрос с **обязательной причиной**; после начала — отменить вправе только архив с обязательной причиной; после фактического списания отмена недоступна.
- Ошибочное исполненное списание исправляется отдельной типизированной P-07 коррекцией admin с обязательной причиной и ссылкой на исходное событие; **не удалением истории**.
- Конкретные значения нового request state machine и точные DB-команды **не утверждать по одному UX-макету**: проектирование/тестирование требуется до UX-10.

## WF-X03. Архив — массовое размещение / перемещение коробок

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Хранение / [Коробки без размещения] [Коробки на полках]               │
│ [□ Коробка №…] [□ Коробка №…] [□ Коробка №…]                           │
│ Выбрано: N                                                            │
├──────────────────────────────────────────────────────────────────────┤
│ Действие: [Разместить выбранные] / [Переместить выбранные]             │
│ Целевая активная полка * [Секция / Полка ▾]                           │
│ Проверка состава набора и доступности полки                            │
│ [Отмена]  [Подтвердить N коробок]                                      │
├──────────────────────────────────────────────────────────────────────┤
│ Результат: все N успешно либо ни одна; ошибка → обновить список       │
└──────────────────────────────────────────────────────────────────────┘
```

- Только активный сотрудник архива с нужным полномочием. Пустые и заполненные коробки допустимы, если остальные инварианты соблюдены.
- **Обычное перемещение не требует причины.** История перемещений хранит прежнюю/новую полки, сотрудника и время. Состав коробок и их custody не меняются.
- Для обычного перемещения коробки, связанной с незавершённой заявкой, действует запрет; исключительная корректировка фактического размещения — **другая команда** с отдельными проверками.
- Массовая операция атомарна: если одна коробка недоступна, вся операция отклоняется. Не допускать частичного «успеха» и повторного применения без проверки актуальной версии.

## WF-X04. Архив — исправление ошибочной приёмки и размещения

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Отправление / Коробка / История                                        │
│ Исходная приёмка: [событие, сотрудник, время]                         │
│ [Исправить ошибочную приёмку]                                          │
│ Причина * [Код из закрытого списка ▾]                                  │
│ Влияние на placement/custody: [расчёт и предупреждение]                │
│ [Подтвердить корректировку]                                            │
├──────────────────────────────────────────────────────────────────────┤
│ Коробка / История размещений                                           │
│ [Исправить ошибочное перемещение] [Причина * ▾]                       │
│ Исходное событие сохранено; новое корректирующее событие добавлено     │
└──────────────────────────────────────────────────────────────────────┘
```

- Не подменять корректировку кнопкой «Редактировать историю». Причина обязательна, для исправления ошибочной приёмки — **закрытый список**, свободный комментарий не обязателен.
- Исправление ошибочной приёмки **не должно автоматически** возвращать коробку в «Ожидается», закрывать действующий placement или стирать последующие реальные перемещения. Система обязана показать фактическое положение и отдельно определить допустимый компенсирующий результат.
- Обычное перемещение без причины и **коррекция ошибочного перемещения с обязательной причиной** — разные UX-сценарии.
- При незавершённой заявке обычное перемещение запрещено; отдельная коррекция фактического размещения с обязательной причиной из закрытого списка не меняет заявку, custody, состав коробки и историю.
- Конкретная матрица полномочий этих корректирующих команд берётся из действующих контрактов; не предоставлять право всем сотрудникам архива только потому, что кнопка есть в wireframe.

## WF-X05. Admin — разрешённые P-07 коррекции без общего редактора

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Администрирование / Глобальный просмотр объекта                       │
│ [Открыть историю] [Доступные типизированные коррекции ▾]              │
├──────────────────────────────────────────────────────────────────────┤
│ Тип: [исправление custody/location / BoxCycle / placement /           │
│       ошибочного завершённого списания карты]                         │
│ Исходный факт/событие [ссылка]                                        │
│ Причина * [обязательное непустое обоснование]                          │
│ Предыдущее → исправленное значение (только разрешённые поля)          │
│ [Подтвердить]                                                         │
├──────────────────────────────────────────────────────────────────────┤
│ Результат: append-only DomainEvent + атомарный AdminSecurityAudit     │
└──────────────────────────────────────────────────────────────────────┘
```

- **Нет универсального PATCH**, редактирования исторического actor/time/payload, manifest/route/receipt, состава или результата P-09.
- P-07 **не разрешает** исправлять `Card.phone`, `card_number`, `full_name`, `date_of_birth` через «коррекцию метаданных»; field-level allowlist обычных карточных полей пуст. Отдельные специализированные команды, если утверждены в других документах, не смешивать с P-07.
- Custody/location correction только при отсутствии активного отправления, незавершённой заявки, внешнего хранения или несовместимого placement. BoxCycle/membership — при соблюдении последовательности циклов и запрета двойного активного membership. Placement — только на активную полку.
- Ошибочное завершённое списание карты — **отдельный тип** коррекции со ссылкой на исходное событие; не «вернуть статус» прямым редактированием.
- Историческое событие не переписывается; admin/security audit и бизнес-коррекция атомарны. Admin не получает приёмку, упаковку, обычную выдачу и размещение.

## WF-X06. Пустая коробка: снять с полки → списать (P-05)

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Коробка №…  Сейчас пуста   Полка: A-01                                 │
│ [Снять с полки]                                                       │
│ После снятия: «Без размещения»                                        │
│ [Списать пустую коробку]                                              │
│ Причина: НЕ требуется                                                 │
│ [Подтвердить списание]                                                │
└──────────────────────────────────────────────────────────────────────┘
```

- Коробка может быть пустой **без текущего BoxCycle**; прошлые циклы сохраняются. Снять с полки вправе сотрудник архива с разрешённым действием `box_unplace`; списание — отдельная команда `box_write_off`.
- Списывать пустую коробку могут все четыре роли в своей согласованной области, а admin — как узкое исключение P-05 в любой локации. Условия: нет карт, открытого цикла, активного отправления и активного placement. **Причина не требуется.**
- Удаление последней карты при обычной перегруппировке не снимает коробку с полки автоматически; P-09 extraction последней карты, напротив, автоматически закрывает placement по отдельному правилу. Не смешивать.
- Списание не удаляет коробку, завершённые циклы, историю или события.


## WF-X07. Архив — оптимизация хранения: переложить карты между коробками на полках

**Согласованный процесс P-03/D-10/D-11, а не новая продуктовая гипотеза.** Источники: `UX-06-storage-model-design.md` §6, `UX-06-INVARIANTS-DB-TEST-MATRIX.md` §3.2, DB-56/57/61, `UX-06-OBJECT-DETAIL-AND-TIMELINE-CONTRACT.md` §47.10, `UX-04-information-architecture-and-navigation.md` §3.3 и `PROGRESS.md` (2026-11-20). Отдельный сценарий добавлен после замечания владельца продукта: WF-X03 **перемещает коробки целиком** и не заменяет WF-X07 **изменения состава коробок**.

### Задача сотрудника

Уменьшить число частично заполненных коробок на архивных полках: выбрать карты из одной или нескольких исходных коробок и переложить в существующую (в том числе уже стоящую на полке) или новую коробку **в пределах разрешённой архивной области**. Это физическая перегруппировка, не отправление и не выдача по заявке ЦО. Предварительное снятие коробок с полок не требуется.

### WF-X07a. Вход из хранения / карточки коробки

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Хранение / [Секция ▾] [Полка ▾] [Коробки]                          │
│ Полка A-01: BX-001 [12 карт]   BX-002 [8 карт]                     │
│ Полка A-02: BX-003 [15 карт]                                      │
│ [Открыть коробку] → [Перегруппировать карты]                      │
│ Источник: BX-001, секция A, полка A-01                            │
│ Выбранные карты: [□ карта №…] [□ карта №…] [□ карта №…]           │
│ [Выбрать целевую коробку]                                         │
└─────────────────────────────────────────────────────────────────────┘
```

Числа и обозначения — **только иллюстративные**, не реальные данные. Не выводить проценты «заполненности» без инвентаризированной вместимости (D-12). Вход также возможен из карточки коробки в WF-A06 и из визуального/табличного хранения WF-M02/M03; самостоятельные права на содержимое коробки проверяются сервером.

### WF-X07b. Выбор целевой коробки и подтверждение

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Перегруппировка карт                                                │
│ Исходная коробка: BX-001, полка A-01                                │
│ Выбрано карт: 3                                                     │
│ Куда: (●) существующая коробка   ( ) новая коробка                 │
│ Целевая: [BX-002, секция A / полка A-01 ▾]                         │
│ Состав до: BX-001 — 12; BX-002 — 8                                  │
│ После операции: BX-001 — 9; BX-002 — 11                             │
│ Размещение коробок на полках НЕ меняется                            │
│ [Назад] [Подтвердить перегруппировку]                               │
└─────────────────────────────────────────────────────────────────────┘
```

Числа — условный пример. Выбор целевой коробки **не означает её перемещение**. Вариант новой коробки использует согласованный жизненный цикл физической тары; создание и placement не следует объединять в одну скрытую операцию. Если для новой коробки требуется полка, размещение выполняется отдельно по WF-A05.

### WF-X07c. Если исходная коробка опустела

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Перегруппировка завершена                                          │
│ Все выбранные карты перенесены в BX-002                            │
│ Внимание: BX-001 теперь пуста, но остаётся на полке A-01           │
│ [Оставить на полке] [Снять с полки] [Открыть коробку]               │
│ Повторно заполнить коробку можно без предварительного снятия      │
└─────────────────────────────────────────────────────────────────────┘
```

После переноса последней карты текущий `BoxCycle` исходной коробки закрывается атомарно, **активный `BoxPlacement` остаётся**. Пользователь решает: оставить пустую коробку для последующего заполнения либо отдельно выполнить `box_unplace`. Списание по P-05 возможно только позднее, при отсутствии активного placement и остальных конфликтов. **Ни автоматического снятия, ни автоматического списания нет.**

### Проверки и история

- Действие доступно уполномоченному активному сотруднику архива в своём scope. Исходные и целевые коробки/карты повторно проверяются по актуальной локации, custody, активным membership, состояниям и отсутствию конфликтующих shipment/заявок.
- Операция `box_repack` **атомарно** закрывает прежние membership и создаёт допустимые новые membership/циклы; прежняя история циклов и составов не стирается. Не возникает двух активных коробок для одной карты.
- Целевая коробка, уже размещённая на полке, может принимать карты без предварительного снятия. При первом заполнении пустой коробки без текущего цикла создаётся новый `BoxCycle`, но её placement сохраняется (DB-57).
- В архиве допускаются карты происхождением из разных филиалов в одной коробке, при соблюдении scope и остальных инвариантов. Филиальное ограничение по происхождению не переносить на архив.
- Если одна карта или коробка недоступна либо конкурентно изменилась, **вся перегруппировка отклоняется**; UI показывает конфликт и предлагает перечитать актуальный состав. Не предлагать фиктивный частичный успех.
- Не смешивать с **массовым извлечением карт из нескольких коробок**: такое отдельное массовое извлечение не утверждено и в позднем PROGRESS отмечено как запрещённое. Основной интерфейс выполняет контролируемую перегруппировку из конкретной исходной коробки; расширенный многоисточниковый сценарий §6 модели хранения требует отдельного сопоставления с поздним ограничением перед UX-10.
- В истории карты и обеих коробок отображается корректное перемещение membership/смена цикла и исполнитель/время в пределах прав. Переход к карте не должен обходить самостоятельную авторизацию.
- **Отличие от P-09:** при извлечении последней карты по заявке ЦО placement закрывается автоматически; при обычной перегруппировке — сохраняется. В UI эти действия нельзя объединять в одну кнопку.

### UX-08: контрольные сценарии

| Случай | Ожидаемый результат |
|---|---|
| Переложить часть карт между двумя коробками, обе на полках | Карты перенесены; обе полки и placement без изменений |
| Переложить последнюю карту | Исходная коробка пуста, BoxCycle закрыт, placement сохранён, показано предупреждение |
| Повторно заполнить оставшуюся на полке пустую коробку | Новый BoxCycle, прежний BoxPlacement сохраняется |
| Переложить карты разных филиалов в архивную коробку | Допустимо при прочих выполненных проверках |
| Карта в активной заявке/отправлении | Сервер отклоняет конфликтующую операцию |
| Сбой одной из операций membership/истории | Полный rollback |
| Снять пустую коробку после перегруппировки | Отдельная явная команда `box_unplace`, не побочный эффект перегруппировки |
| Перегруппировка vs P-09 | Разное поведение placement при последней карте |


## Сквозные UX-проверки

| Сценарий | Критерий |
|---|---|
| ЦО пытается списать карту напрямую | Нет такой команды; только запрос |
| Запрос P-04 без кода основания | Ошибка; `other` без комментария допустим |
| Отмена P-04 после старта архива | Только архив, обязательная причина |
| Ошибочное исполненное списание | P-07 отдельной командой; исходное событие остаётся |
| Массовое перемещение: одна коробка изменилась | Вся операция отклонена, частичного результата нет |
| Коробка в активной P-09 | Обычное перемещение заблокировано |
| Коррекция placement | Отдельная причина и append-only событие |
| Исправление приёмки | Не стирает последующее фактическое размещение |
| Admin пытается редактировать ФИО/телефон карты через P-07 | Нет соответствующей формы/команды |
| Пустая коробка на полке | Сначала отдельное снятие, затем списание |
| Утрата доступа/конкурентное изменение | Сервер отклоняет команду без частичного результата |

## Связь с существующими WF

- WF-01 / WF-04: списание коробки из контекста собственной коробки; P-04 инициируется только ЦО.
- WF-02: поштучная приёмка остаётся основной; исправление приёмки — отдельное контекстное действие; массовые placement/move не заменяют историю каждой коробки.
- WF-03: P-09 не является P-04; один shipment после полной обработки всех позиций.
- WF-05: P-07 добавляет **узкие типизированные действия** к глобальному read, не общую кнопку «Исправить всё».
- WF-06: схема/реестр дают контекст перехода к полке/коробке, но не расширяют полномочия на действия.

**Оставшаяся зависимость:** перед UX-10 технические контракты P-04/P-07 и исправлений должны быть доведены до проверяемых DB-команд и состояния, с учётом конфликтов и аудита. Это не основание заново спрашивать уже принятые основания, роли, комментарии и правила отмены. UX-07 ещё требует общей карты экранов и визуального review; UX-08 не начат.
