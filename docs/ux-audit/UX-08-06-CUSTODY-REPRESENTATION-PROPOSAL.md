# UX-08-06 — представление ответственности (техническое предложение)

Проверен src/medarchive/adapters/postgresql/models.py: Card имеет взаимоисключающие current_location_id/current_shipment_id, FK членства в manifest; Shipment имеет courier FK, Courier — отдельный справочник. Старый custody_status описывает внешнее хранение, не ответственного субъекта.

Предпочтительный вариант: не дублировать courier ID в Card. Для обычной стационарной карты ответственный субъект определяется учётной локацией; для карты в пути — неизменяемым courier FK активного отправления с подтверждённым handover и отсутствующим receipt этой карты (для коробочного маршрута — receipt её коробки). Внешнее хранение сохраняет отдельную семантику. Не выводить custody из одного лишь статуса родительской заявки. Не использовать courier active как условие сохранения исторической ответственности.

Вариант требует проверки всех исключений, scope, текущих DB guards, миграций и legacy данных. До завершения проверки не утверждать отказ от custody_location_id и не добавлять NOT NULL FK, несовместимый с courier custody. Альтернатива — явный дискриминатор и взаимоисключающие FK, если выявится необходимость независимой ответственности. Не вводить роль courier.

Регрессии: draft не меняет ответственность; handover полного manifest атомарно передаёт её курьеру; частичный receipt меняет только принятые карты/коробки; отмена до handover сохраняет отправителя; повторный handover/receipt не создаёт дублей; деактивация курьера не меняет custody; внешний custody не смешивается с перевозкой. Проверить авторизацию standalone объектов и исторических manifest отдельно.

Статический анализ, не реализация. DDL и тесты не запускались. Полная междокументная сверка не завершена.
